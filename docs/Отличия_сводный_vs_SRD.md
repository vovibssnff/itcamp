# Детальные отличия: документ Рухшоны vs документ Влада

Сравнение двух документов одного проекта КТК для ЭЛОУ-АВТ:
- **Рухшона** — `1KTK_ELOU_AVT_svodny_dokument.docx` (сводный документ требований, охватывает всю установку);
- **Влад** — `SRD-КТК-ЭЛОУ-АВТ.md` (SRD в формате MVP, охватывает только блок ЭЛОУ).

Пункты отличий сгруппированы по темам.

## 1. Назначение и охват документа

- Рухшона — **сводный документ требований** на всю установку ЭЛОУ-АВТ (все блоки), версия бизнес/функциональных/НФТ/архитектуры/инфраструктуры.
- Влад — **SRD в формате MVP** (материал для реализации/защиты чемпионата) только на блок **ЭЛОУ** (электрообессоливание/обезвоживание).
- Рухшона: роль обучению — **оператор установки в целом**; Влад: роль — **консольный оператор блока ЭЛОУ**.
- Влад содержит явные приоритеты требований (Must/Should/Could/Won’t) и идентификаторы (FR-*, NFR-*, UI-*, DATA-*, ARCH-*, AC-*). В Рухшона приоритизации **нет** (100 пунктов без must/should/could).

## 2. Блоки моделирования (принципиальное расхождение)

- Рухшона моделирует **всю установку**: ЭЛОУ + Атмосфера (АВТ) + **ГДМ** (гидродемеркаптанизация) + общеустановочные системы (печи, насосы, теплообмен) — 10 блоков функциональных требований.
- Влад моделирует **только ЭЛОУ**; атмосферный и вакуумный блоки АВТ в MVP **не входят** (Won’t/Could).
- Рухшона заменил блок «Вакуумная колонна» на «Гидродемеркаптанизация (ГДМ)» (по регламенту установки вакуумного блока нет; есть реальный блок К-12/2,3,4 с ВСГ).
- Влад вообще не рассматривает ГДМ/вакуум: фокус на 1-2 ступенях электродегидраторов Э-1…Э-6 и связанном оборудовании ЭЛОУ.

## 3. Объём и структура функциональных требований

- Рухшона: **100 функциональных требований** в 10 блоках (оркестрация, ЭЛОУ, Атмосфера, ГДМ, общ. системы, аварии, UI, оценка/квалификация, ИИ, тех. ограничения).
- Влад: **детальные, но более узкие** требования по ЭЛОУ: аутентификация/роли, симуляция ЭЛОУ (FR-SIM-*), аварии (FR-AV-01…03), HMI (FR-HMI-*), оценка (FR-ASSESS-*), ИИ (FR-AI-*), изоляция OT (FR-ISO-*).
- Рухшона: 3 режима + демонстрация + снапшоты; Влад: 4 режима (тренировка с инструктором, самостоятельная, экзамен, демонстрация) с приоритетами.

## 4. Аварийные сценарии

- Рухшона: широкий перечень аварий по всем блокам (прорыв воды, замерзание пара, разгерметизация теплообменника, пожар на насосной, потеря энергоснабжения, обрыв факела, обводнение сырья, коррозия печи, разгерметизация ГДМ и др.).
- Влад: **3 подтверждённые аварии** с детализацией симптомов и эталонных действий:
  - FR-AV-01 — КЗ/пробой электродов;
  - FR-AV-02 — срыв уровня раздела фаз / обводнение;
  - FR-AV-03 — отказ сырьевого насоса Н-1 / потеря расхода.
- Влад подчёркивает «3 аварии» как ключ для MVP; Рухшона — гораздо больше сценариев без приоритизации.

## 5. Ролевая модель

- Рухшона: **3 роли** — Обучаемый, Инструктор, Администратор (зафиксировано как финальное).
- Влад: **4 роли** — **Admin, Instructor, Operator, Observer** (наблюдатель добавлен).
- Влад аутентификация — **локальная (логин/пароль) на MVP**; Рухшона — корпоративный **LDAP** сразу.
- Рухшона фиксирует LDAP как обязательный; Влад выносит LDAP/AD в Target без MVP.

## 6. Модель и глубина симуляции

- Рухшона: описание строгого физического моделирования (тепловой баланс, покомпонентное разделение, электрическое поле, кавитация), для прототипа допустима упрощённая модель.
- Влад: формализованные уровни зрелости модели **L1 (правила/упрощённые ODE — MVP) → L2 → L3 (Target)**; чёткая граница физической точности MVP.
- Влад вводит **Model API** (`step`, `get_state`, `set_state`, `inject_fault`, `set_speed`) для заменяемости движка (L1→L3) — в Рухшона аналог описан менее формально (Plug-and-Play подмодели).

## 7. Инфраструктура и площадка развёртывания

- **Площадка:** Рухшона — on-premise учебный класс с удалённым доступом через отечественное облако (**VKCloud / Zvirt / Yadro**); Влад — **VK Cloud** (on-prem заказчика — Target).
- **ОС:** Рухшона — **Astra Linux SE 1.8** как обязательная; Влад — на MVP Linux-образы **VK Cloud**, Astra Linux SE 1.8 — для категорированных КИИ (Target).
- **СУБД:** Рухшона — **PostgreSQL 14**; Влад — отечественная **Tantor Ordinary + Patroni** (кластер), Tantor Certified — Target.
- **Мониторинг:** Рухшона — **Astra Monitoring (SNMP)**/Glaber/Пульт/UDV ITM; Влад — **Пульт + Графиня** (+ SIEM KUMA/MaxPatrol — Target).
- **Крипто:** Рухшона — ГОСТ-криптопровайдеры обязательны; Влад — на MVP **HMAC**, переход на СКЗИ (КриптоПро) — Target.

## 8. Технологический стек

- Рухшона — **open-source стек** с обоснованием лицензий: React+TS+Ant Design, Konva/Plotly, FastAPI, Celery/RabbitMQ, Valkey, NumPy/SciPy, DWSIM (опц.), scikit-learn/XGBoost, PyTorch+River, LangChain+Ollama(mistral:7b), ChromaDB/FAISS, MLflow, PostgreSQL, MinIO, OpenSSL+GOST-engine, ldap3, ClamAV, OpenSearch, Prometheus/Grafana, WeasyPrint, Docker+Compose, Nginx.
- Влад — более узкий MVP-стек: React+TS+Vite, Redux/Zustand, FastAPI+Uvicorn, SQLAlchemy async+asyncpg+Alembic, NumPy/SciPy, _vLLM/Ollama_, Redis-совместимый кэш / рассматривается **Tarantool**, S3 (VK Cloud/MinIO), uPlot, Nginx (форк **Angie** — Target).
- Влад нацелен на **monorepo + Ansible (IaC)** и **Docker Compose → Swarm** (Target: Deckhouse / Managed K8s). В Рухшона оркестрация — Docker+Compose, Kubernetes при росте >10 сессий (без Ansible).

## 9. ИИ-модуль

- Рухшона: ИИ — классификация/локализация ошибок, прогноз риска до совершения, генерация обратной связи, адаптивный подбор сценариев; отдельные НФТ (AI-01…08, PERF-AI-01…03): точность ≥85%, предсказание за 10 мод. сек, ответ ≤3 сек, отдельный контейнер с лимитом CPU/RAM (≤2 ГБ), версионирование моделей.
- Влад: ИИ на **отдельном GPU-хосте**; 4 функции — Explain / Predict(physics) / Predict(behaviour) / Adaptive; **деградация** (падение ИИ не останавливает симуляцию и rule-based оценку); минимизация/псевдонимизация ПДн в промптах; mTLS к AI API.
- Влад явно: ИИ stateless относительно сессии и **не входит в снапшот**; в Рухшона это не отражено.

## 10. Безопасность

- Рухшона: транспорт TLS 1.2+, ГОСТ-провайдеры, RBAC (3 роли), антивирус загружаемых файлов (ClamAV), CSP/изоляция Docker, валидация JSON Schema/защита SQLi/XSS/CSRF, разделение узлов управления.
- Влад: **развёрнутая модель ИБ**: категории данных/уровень требований (ПДн — ФЗ-152, УЗ-3/4), **8 актуальных угроз с мерами** (NFR-SEC-01…08), криптография протокола экзамена (HMAC, NFR-SEC-09…14), append-only аудит, **контроль целостности таблиц БД (SHA-256)**, rate-limit авторизации/API, mTLS к AI, инцидент-playbooks.
- Влад принципиально: КТК **не является АСУ ТП**, полная изоляция от OT-контура (FR-ISO-*), Server authoritative state, RBAC на сервере (клиент не считает «истину»).

## 11. Оценка и квалификация

- Рухшона: оценка по времени реакции, последовательности действий, экономическому ущербу (методика расчёта — открытый вопрос), «идеальный алгоритм»/эталон, тепловая карта ошибок, Replay, рейтинг операторов, критические ошибки.
- Влад: то же принципиально, но детальнее и с приоритетами: фиксация реакции (FR-ASSESS-01), сравнение с эталоном (02), штрафы/итог (03), критические ошибки (04), **переопределение оценки инструктором с аудитом** (05), Replay (Should), PDF-отчёт (Should), **HMAC-подпись протокола экзамена**.
- Рухшона: экономический ущерб как обязательный показатель; Влад — акцент на правил/штрафах + ИИ, экономический ущерб не обязателен на MVP.

## 12. Снапшоты и детерминизм

- Рухшона: снапшот состояния режима для возврата; компактность для восстановления; лимит объёма — открытый вопрос («не более 50 Мб»).
- Влад: **глубокая проработка снапшотов** (FR-SNAP-01…08, ARCH-11…14):
  - полное состояние: модель/теги/ОДУ/интеграторы ПИД, арматура, активные аварии, **модельное время, скорость, состояние ГПСЧ** (детерминизм);
  - метаданные в БД (Tantor) + иммутабельный payload в object storage, **SHA-256**;
  - барьер на границе тика, версионирование (`schema_version`), рассылка свежего состояния по WebSocket, запрет restore в экзамене (антифрод);
  - ориентир размера ≤50 МБ (DATA-05).

## 13. Нагрузка и масштабирование

- Рухшона: рабочая оценка — **10 одновременных активных сессий** (5–10 обучаемых + до 3 инструкторов); линейное масштабирование без переработки.
- Влад: MVP — **1–5 сессий**, Target — **до 50**; горизонтальное масштабирование app-узлов Docker **Compose → Swarm**; API-деградация (инструкции).

## 14. Требования к данным (у Влада детальнее)

- Влад выделяет отдельный раздел «Требования к данным»: сущности (User, Role, Scenario, Session, TagSnapshot, AlarmEvent, OperatorAction, Assessment, ExamProtocol, AIInsight), версионируемый **словарь тегов**, право на забвение, ежесуточный бэкап. В Рухшона требования к данным растворены в НФТ (DATA-01…03).
- Рухшона: добавляет детали NTP (timestamp), резервное копирование вне основного ЦОД, полное удаление ПДн по запросу ОК.

## 15. Испытания и приёмка

- Рухшона: раздел «Открытые вопросы» + критерии успеха (KPI) в бизнес-требованиях.
- Влад: **отдельный раздел тестирования** (TEST-01…10) и **критерии приёмки/трассировки на кейс** (Таблица AC-01…03), включая детерминизм снапшотов, двухэкранный АРМ, Аnsible-деплой. В Рухшона такого структурирования нет.

## 16. Разное / отсутствующее в другом документе

- **В Рухшона отсутствует:** формальные приоритеты Must/Should/Could, идентификаторы требований, Tag dictionary, механика снапшотов, карта экранов UI, детальные эталонные алгоритмы, история изменений (версии), уровни зрелости L1–L3, матрица угроз ИБ, явный изоляционный контур OT.
- **У Влада отсутствует/не в фокусе:** ГДМ и атмосферный блоки, экономический ущерб как обязательный показатель, общеустановочные системы (печи/насосы/теплообмен в масштабе всей установки), Astra Monitoring/SNMP (иная схема мониторинга), бизнес-цели/KPI в развёрнутом виде.
- Рухшона дополняет: бизнес-требования (проблематика, цели, заинтересованные стороны, критерии успеха, границы, допущения) и глоссарий/сокращения; Влад — свой глоссарий (приложение E).

## 17. Итоговое резюме

Документы расходятся **по охвату** (вся установка vs только ЭЛОУ), **по целевому назначению** (сводный бизнес-документ vs реализуемый SRD MVP) и **по ряду технических решений** (СУБД: PostgreSQL vs Tantor; крипто: ГОСТ vs HMAC на MVP; площадка: VKCloud/Zvirt/Yadro vs VK Cloud; мониторинг: Astra Monitoring/SNMP vs Пульт+Графиня; ОС: Astra всегда vs Astra только для КИИ; роли: 3 vs 4; аутентификация: LDAP vs локальная + LDAP в Target).

Для сведения обеих версий необходимо либо **расширить Влад** до полной установки (добавив Атмосферу/ГДМ, экономический ущерб, ГОСТ/мониторинг по Рухшона), либо **зафиксировать охват MVP только по ЭЛОУ** и явно продолжить наведение соответствия с Рухшона по остальным блокам.
