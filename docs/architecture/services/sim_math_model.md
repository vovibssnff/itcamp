# Техническое решение: математическая модель `sim-worker`

> Слой: Вычислительный | Namespace: `ktc-sim` | Компонент: `sim-worker` (инстанс движка на сессию)
> Смежно: `sim_worker.md` (сервис/контракты), `sim_manager.md` (жизненный цикл инстанса), `snapshot.md` (снапшоты/restore), `Simulation_Engine_модель_namespace_k8s.md`

## 1. Назначение и место в системе

`sim-worker` — **цифровой двойник техпроцесса ЭЛОУ-АВТ** и единственный источник истины о технологическом состоянии (`FR-ISO-03`). Все теги, алармы и значения, которые видит оператор и оценивает `assessment`, порождаются именно здесь. На каждую сессию создаётся **изолированный инстанс** движка (`1 сессия = 1 инстанс`, `ARCH-08`), чтобы:

- сбой одной сессии не влиял на другие;
- гарантировать одинаковую «истину» для всех потребителей (HMI, assessment, snapshot, ИИ);
- обеспечить детерминизм при save/restore и replay.

Этот документ описывает **внутреннюю математику и алгоритмику** движка: модель, численное интегрирование, детерминизм, тик-цикл, теги/алармы, снапшоты. Контракты (`Model API`) и жизненный цикл инстанса — в смежных документах.

## 2. Домен: технологическая схема ЭЛОУ-АВТ

Движок моделирует ключевые блоки установки (базовая библиотека Л1):

| Блок | Узлы/объекты |
|---|---|
| Электрообессоливание (ЭЛОУ) | электродегидраторы, смесители, клапаны, расходы |
| Атмосферная перегонка | колонны К-1/К-2, кипятильники, орошение, отборы |
| Нагрев | печи (подогреватели сырья) |
| Гидроочистка (ГДМ) | реакторы, сепараторы, компрессоры |

Каждый компонент — набор **параметров** (давление, температура, расход, уровень, состав) и **тегов** типов `PV` (текущее значение), `SP` (уставка), `OUT` (выход регулятора), `MODE` (Auto/Manual).

Топология (граф-шаблон установки) приходит из `constructor` как `init_state` при старте сессии. **Движок не знает домен заранее** — он строит систему уравнений по переданному графу (принцип «граф как единица конфигурации», ARCH-07).

## 3. Математическая модель

### 3.1. Базовая структура (уровень L1)

Модель Л1 — **упрощённая физическая модель** динамики установки, описываемая системой обыкновенных дифференциальных уравнений (ODE):

```
dx/dt = f(x, u, d, t)
y = g(x, u, d)
```

где:
- `x` — вектор состояний (давления, температуры, уровни в ёмкостях/колоннах);
- `u` — вектор управляющих воздействий (положения клапанов, уставки регуляторов, команды оператора);
- `d` — вектор возмущений/неисправностей (`inject_fault`);
- `y` — вектор наблюдаемых тегов (PV, производные, алармы).

Каждое оборудование вносит вклад в `f(x, u, d)`: балансы массы и энергии для колонн/ёмкостей, характеристики насосов, теплопередача в печах, гидравлическое сопротивление.

Цель Л1 — **качественно и детерминированно** воспроизводить динамику, достаточную для тренажёра (тренды, аварии, реакции оператора), при гарантируемой частоте ≥1 Гц даже для графа до 200 узлов.

### 3.2. Точка расширения L1→L3

Тот же `Model API` (и тот же внутренний интерфейс решателя) допускает подключение **внешнего строгого solver'а** (например, термодинамическая надстройка DWSIM) для уровня Л3 без изменения контрактов (`ARCH-01`). Внутренний интерфейс движка отделён от конкретной численной схемы, поэтому Л3 подключается заменой реализации `solver` без касания тегов/алармов/Model API.

## 4. Численное интегрирование ODE

### 4.1. Выбор схемы

- **Метод:** жёстко-устойчивый семейство (например, BDF/`odeint`-класс SciPy или явная схема с адаптивным шагом) — выбор согласуется с технологом (полуоткрытый вопрос №2 в `sim_worker.md`).
- **Детерминированный фиксированный набор параметров схемы** (порядок, допуски, макс. подшагов) в одном инстансе и между инстансами — чтобы один и тот же вход давал один и тот же выход (см. раздел 5).

### 4.2. Тик-цикл и подшаги

Основной цикл движка работает на **модельном времени**:

- базовый тик = **1 с** модельного времени (телеметрия 1 Гц);
- физ.time (стена) ускоряется через `set_speed`: `0.1×–10×`:
  - `speed = 1.0` → 1 шаг за 1 реальную секунду;
  - `speed = 10.0` → фиктивно проходим 10 с модельного времени за 1 реальную секунду, выполняя **внутренние подшаги** численного интегратора;
  - `speed = 0.1` → пауза/замедление (шаг интегрирования разреженнее).
- на каждый `step()` движок продвигает модельное время на `1 с` (или кратно скорости) и возвращает полное состояние/телеметрию.

**Под-шаги важны для детерминизма:** сколько бы реального времени ни прошло, при `speed=10` движок делает ровно такое же количество математических под-шагов между тиками, чтобы результат не зависел от нагрузки CPU.

### 4.3. Целевые показатели

- Частота ≥1 Гц модельного времени устойчиво, при `10×` — суммарный бюджет CPU в пределах `guaranteed QoS` инстанса (`Node Pool sim`).
- Граф до 200 узлов укладывается в один шаг за реальное время тика (≤1 с).

## 5. Детерминизм — ключевое свойство

Детерминизм означает: **при одинаковом входе (состояние + команды + неисправности + последовательность step) движок воспроизводит одинаковую траекторию** — в рамках одного инстанса и после restore из снапшота.

### 5.1. Источники детерминизма и их контроль

| Источник | Мера контроля |
|---|---|
| ГПСЧ (шум, дрейф, вероятностные события, если используются) | Единый генератор с **явным seed**, seed сохраняется в снапшот; порядок вытягивания случайностей детерминирован |
| Численный метод | Фиксированные параметры схемы (порядок, допуски, шаг) |
| Параллелизм | Исключён в точке принятия решения по состоянию: шаг выполняется последовательно, без гонок |
| Порядок обработки команд | FIFO с временной меткой; одинаковый порядок → одинаковый результат |
| Окружение (BLAS/FPU) | Техника фиксированного набора библиотек и ассемблерной точности; допускается минимальный конфигурационный допуск (зазор сравнения) |

### 5.2. Детерминизм при restore

Снапшот содержит (совместно с `snapshot.md`):
- вектор состояний `x`;
- текущее модельное время;
- **seed ГПСЧ** и состояние генератора;
- конфигурацию схемы интегрирования;
- метаданные (версия схемы, SHA-256).

После `set_state(snapshot)` движок продолжает численно **идентично** прерванному запуску (обрыв ≤3 мин → restore ≤15 с без потери прогресса). Это же свойство позволяет **replay** сессии (разбор/пересмотр) с воспроизведением тех же значений.

### 5.3. Алармы и сигнализации

Теги/алармы генерируются **как функции состояния** (не извне), поэтому детерминированы:

- уровни сигнализации `HH/H/L/LL`, ПАЗ (ПАЗ-защита по превышению), ППК (предохранительные клапаны);
- события алармов пишутся в append-only журнал (Picodata) с временной меткой модельного времени.

## 6. Порождение тегов и потока данных

1. `step()` продвигает модель → новое `x`, затем `y = g(x,u,d)`.
2. Формируется полный срез тегов/алармов (все PV/SP/OUT, статусы), который:
   - возвращается в ответе `step()`/`get_state()`;
   - кэшируется в Radix оркестратором (горячее состояние);
   - пушится клиентам по WS 1 Гц;
   - используется `assessment` для оценки.
3. Журнал действий/алармов — append-only в Picodata.

## 7. Снапшоты и restore

Взаимодействие (см. `snapshot.md`, `sim_worker.md`):
- `snapshot` слабо связан с движком: `orchestrator` запрашивает `get_state()` (полный срез + seed) → payload в S3, метаданные в Picodata + SHA-256.
- При обрыве/падении: `sim-manager` пересоздаёт инстанс (ensure), `orchestrator` зовёт `set_state(snapshot)`.
- **Движок сам ничего не пишет в S3** — сериализует/десериализует состояние по требованию `orchestrator`.
- Антифрод в экзамене: restore ученику **запрещён** (`snapshot.md`).

## 8. Метрики и мониторинг

- **`tick-lag`** — главная real-time-метрика: отставание реального исполнения тика от модельного графика (должно ≈0 на 1 Гц; >0 при перегрузке/10×).
- Время одного `step`/`get_state`/`set_state`.
- CPU/RAM инстанса, число под-шагов на тик.
- Счётчики событий алармов/исключений.

## 9. Открытые вопросы (по согласованию с технологом и на случай load-test)

1. Точный численный метод и фиксированный размер/допуски шага (тема `sim_worker.md` №2).
2. Батч-шаги: `step` по одному на тик vs пачка (влияет на `10×`, тема `sim_worker.md` №3).
3. Политика под-шагов при высокой скорости и то решение «сколько внутренних итераций между тиками» — в конфиг движка.
4. Точность плавающей точки кросс-платформенно (Docker локально vs K8s-под) — допустимый допуск сравнения для детерминизма.

# Преимущества подхода

## 1. Детерминированность = доверие к результату

Единый цикл «фиксированная схема + контроль ГПСЧ + seed в снапшоте + отсутствие гонок» гарантирует **воспроизводимость**:

- одинаковый ход занятия у разных операторов при одинаковых действиях;
- честность экзамена: restore запрещён (`антифрод`), а итог — проверяем;
- **replay/разбор**: можно пересмотреть сессию и показать «как было» — сильный аргумент для комитета и учебного аудита;
- повторяемость для тестирования: юнит-тесты математики стабильны без флаки.

## 2. Изоляция per-session = масштабируемость и устойчивость

«1 сессия = 1 инстанс» даёт:

- сбой одной сессии не роняет другие (до 50 параллельно);
- изолированный CPU-бюджет → гарантия 1 Гц не «крадётся» соседом;
- добавление сессий линейно масштабирует вычислительный слой (Node Pool `sim`).

## 3. Граф как единица конфигурации (ARCH-07)

Движок строит модель из **переданного графа**, а не из жёсткой схемы. Это делает систему **low-code платформой**: инструктор собирает установку без программирования, и движок подхватывает новую топологию без пересборки. Это отличает проект от классического «фиксированного» КТК.

## 4. Расширяемость модели L1→L3 без переписывания

Отделение интерфейса решателя от движка и общий `Model API` позволяют поднять точность (DWSIM и т.п.) **без изменения контрактов, HMI, ИИ и оценки** (ARCH-01). Прототип на Л1 — быстро, целевое — на Л3.

## 5. Развязка «математика ↔ инфраструктура» (Pathway 1/RuntimeProvider)

Движок (`sim-worker`) не управляет своим жизненным циклом и не знает, где крутится (Docker локально или K8s-под). Это же свойство усиливает сильный дизайн управления инстансами (`sim-manager`):

- один и тот же математический код для локального прототипа и целевого K8s;
- разработка и демонстрация быстро локально, презентация — на целевой инфраструктуре;
- фокус ответственности: математика — в движке, контроль среды — в sim-manager.

## 6. Соответствие требованиям безопасности

- Все теги рождает только движок (`FR-ISO-03`), нет объединения с реальными АСУ ТП/OT-сетью — типология «OT отдельно» соблюдена.
- Append-only журнал алармов/действий + SHA-256 снапшотов + запрет restore в экзамене — целостность и аудируемость.

## 7. Соответствие принципам и подходит для защиты

- ARCH-01 (модульность движка), ARCH-02 (server-authoritative — движок источник истины), ARCH-04 (gRPC Model API), ARCH-06 (отечественный стек/упрощение локально), ARCH-07 (граф), ARCH-08 (per-session).

Итог: подход совмещает **детерминизм для честного учёта**, **масштабируемость до 50 сессий через изоляцию**, **low-code через граф**, **расширяемость модели** и **единый код для прототипа и целевого развёртывания** — что делает его и инженерно корректным, и убедительным при защите решения перед комитетом.
