# Архитектура КТК ЭЛОУ-АВТ (Kubernetes + микросервисы)

> Версия: 0.1 (черновик для обсуждения)
> Дата: 2026-08-05
> Статус: предлагаемая целевая архитектура

---

## 1. Цель и задачи документа

Документ описывает целевую архитектуру компьютерного тренажёрного комплекса (КТК) для обучения операторов установки ЭЛОУ-АВТ. КТК — это **веб-приложение** (браузерный тренажёр операторского типа, OTS/Intelligent OTS), разворачиваемое на **Kubernetes** в микросервисной архитектуре.

Документ опирается на требования:
- `требования/ФТ_КТК.md`, `требования/НФТ_КТК.md` — функциональные и нефункциональные требования;
- `требования/SRD-КТК-ЭЛОУ-АВТ.md` — SRD (MVP-версия, блок ЭЛОУ);
- `требования/Требования_ИБ.md`, `требования/Ответ_на_замечания_Требования_ИБ.md` — требования ИБ/ФСТЭК;
- `требования/Сценарии_использования_КТК.md`, `требования/Сценарии_использования_ИИ.md` — сценарии.

Решения, зафиксированные ранее по ИБ (согласованные технические решения):
- платформа виртуализации — **ВК Cloud** (допустимы Zvirt, Yadro);
- аутентификация — **LDAP/AD** для всех ролей, 2FA для инструктора/администратора, отечественный PAM;
- SIEM — **Kaspersky KUMA**; хранение аудита 1 год;
- ОС серверов — **Astra Linux SE 1.8** (для категорированных КИИ — обязательно);
- СУБД и кэш — **Picodata** (СУБД) + **Radix** (Redis-совместимый кэш); кластер Picodata на Raft, без Patroni;
- Антивирус/EDR, Kaspersky Threat Intelligence / Anti-APT, ГОСТ-подписи + SHA-256.

## 2. Требования, определяющие архитектуру

### 2.1. Ключевые нефункциональные требования (НФТ)

| ID | Параметр | Значение |
|----|----------|----------|
| PERF-01 | Время отклика UI (действие → изменение на мнемосхеме) | ≤ 500 мс (целевое 300 мс) |
| PERF-02 | Частота телеметрии цифрового двойника | ≥ 1 Гц модельного времени |
| PERF-03 | Загрузка сценария / снапшота | ≤ 15 сек |
| PERF-04 | Пиковая нагрузка | 10–50 одновременных активных сессий |
| PERF-05 | Генерация PDF-отчёта | ≤ 20 сек |
| SCL-01 | Горизонтальное масштабирование сервисов | без миграции БД |
| REL-01 | SLA | 98% во время учебных смен |
| REL-02 | Обрыв связи ≤ 3 мин | прогресс сессии не теряется |
| REL-03 | Отказоустойчивость БД | failover < 30 сек |
| MAIN-02 | Rolling Update / Blue-Green | без даунтайма |
| AI (PERF-AI-xx) | Анализ сессии, параллелизм, память | ≤10 c/сессию, до 50 запросов, ≤2 ГБ |

> **СУБД и кэш — Picodata.** В качестве СУБД используется **Picodata** (распределённая СУБД, PostgreSQL-совместимый wire-протокол, сертификат ФСТЭК УД 4, входит в РРПО), а в качестве кэша — **Radix** (Redis-совместимый плагин Picodata, сертифицирован ФСТЭК как замена Redis). Кластер Picodata использует собственную Raft-репликацию (внешний Patroni не требуется). Это закрывает и требование отечественного ПО, и функции БД + кэша одним продуктом.

### 2.2. Специфические свойства микросервисной модели

- **Изоляция сессии/модели:** каждая активная сессия обучения выполняет свой экземпляр Simulation Engine (процесс OTS), чтобы сбой одной сессии не влиял на остальные.
- **Реальное время:** телеметрия → WebSocket (push), 1 Гц; управляющие команды → REST.
- **Тяжёлые задачи:** PDF-отчёты и ИИ-расчёты — асинхронно через очередь задач, не блокируют сессию (INT-03).
- **Server authoritative state:** клиент — «тонкий», не считает «истину»; единственный источник состояния — сервер.
- **Изоляция OT:** нет интеграций с реальной АСУ ТП/OPC/Modbus; теги порождаются только Simulation Engine.
- **Deployment:** Rolling Update без даунтайма; Blue-Green для критичных обновлений.

## 3. Принципы архитектуры (ArchiMate / ADR — резюме)

1. **Микросервисная архитектура** с независимо масштабируемыми сервисами (на основе НФТ 1.2 «Предпочтительна микросервисная архитектура»).
2. **Оркестрация — Kubernetes** (управляемый K8s ВК Cloud в целевой конфигурации; для прототипа допустим Docker Compose → Swarm с тем же контрактом).
3. **Event-driven для асинхронности:** очередь/брокер сообщений для отчётов, ИИ-расчётов, событий.
4. **Server authoritative state** — сервер является единственным источником истины (клиент не считает оценку/телеметрию).
5. **Изолированные контуры:** сегмент КТК полностью изолирован от OT-сети; компоненты на отдельных ВМ/IP по политике ФС.
6. **Модульность приложения (Plug-and-Play):** замена подмоделей (ЭЛОУ/Атмосфера/Вакуум/ГДМ) без пересборки; стабильный Model API.
7. **Security by design:** RBAC, mTLS между сервисами, ГОСТ-крипто, аудит, SIEM.
8. **Доверенный контур обновлений:** без прямого доступа в интернет из сегмента КТК.

## 4. Целевой стек (фокус на K8s и веб)

### 4.1. Контейнеризация и оркестрация
- **Kubernetes** — платформа оркестрации целевой конфигурации (управляемый **Managed Kubernetes ВК Cloud** или **Deckhouse**).
- **Docker** — контейнеризация всех сервисов; **Helm** — управление релизами.
- Для прототипа допускается **Docker Compose → Swarm** с тем же составом сервисов и контрактами API (лёгкий переход на K8s).

### 4.2. Прикладные сервисы (микросервисы)
| Сервис | Назначение | Технология |
|--------|-----------|------------|
| **Frontend (Web-HMI)** | Мнемосхема, тренды, алармы, faceplate-узлы, экраны ролей | React + TypeScript, Vite, WebSocket, uPlot/Konva |
| **API Gateway / BFF** | Единая точка входа HTTPS/TLS, маршрутизация, CSP, rate-limit, аутентификация | Nginx→(Angie) / Backend-for-Frontend |
| **Auth / Session Service** | LDAP/AD, JWT, RBAC, 2FA/PAM, управление сессиями | Python/FastAPI или Go |
| **Session Orchestrator** | Создание/запуск/пауза/стоп сессий, скорости, чекпоинты, WebSocket-телеметрия | Python/FastAPI, WebSocket |
| **Simulation Engine** | Цифровой двойник ЭЛОУ-АВТ, тик 1 Гц, Model API | Python + NumPy/SciPy (узлы по сессиям) |
| **Assessment Engine** | Эталон, штрафы, критические ошибки, оценка | Python-сервис |
| **AI Service** | Explain, Predict(physics/behaviour), Adaptive, риск | Обособленный GPU-модуль, vLLM/Ollama, PyTorch/scikit-learn |
| **Snapshot Service** | Save/restore состояния, метаданные+payload | Python, S3 SDK |
| **Reporting** | PDF-отчёты и протоколы экзамена (асинхронно) | Python, WeasyPrint |
| **Scenario/Catalog Service** | Библиотека сценариев, Low-Code-конструктор, шаблоны | Python/FastAPI |
| **Monitoring/Health** | /healthz, метрики, алерты | /healthz + метрики |

|-----------|------|-----------|

## 5. Логическая диаграмма компонентов (текстовая сводка)

```
Браузер (Ученик/Инструктор/Админ/Наблюдатель)
   │ HTTPS/TLS 1.2+ (WebSocket для телеметрии 1 Гц)
   ▼
API Gateway / BFF (Auth, JWT, RBAC, rate-limit, CSP)
   │
   ├──────► Auth/Session Service ──► LDAP/AD
   ├──────► Session Orchestrator ──► WebSocket-телеметрия
   │            │
   │            ├──► Simulation Engine (per-session, Model API)
   │            ├──► Assessment Engine
   │            ├──► Snapshot Service ──► Object Storage (S3)
   │            └──► Event Broker (асинхронные задачи)
   ├──────► Scenario/Catalog Service
   ├──────► Reporting (асинхронно) ──► PDF ──► Object Storage
   └──────► AI Service (GPU) ──► Explain/Predict/Adaptive

Общая инфраструктура:
   Picodata (СУБД, PG-совместимый) + Radix (кэш, Redis-совместимый), MinIO/S3,
   Astra Monitoring (метрики+логи), KUMA (SIEM/аудит ИБ),
   K8s (Managed ВК Cloud / Deckhouse) на Astra Linux SE 1.8
```

## 6. Особенности развёртывания на Kubernetes

### 6.1. Один кластер, несколько сегментов (Namespaces)
Сегментация по Namespace + NetworkPolicies:
- `ktc-app` — прикладные сервисы (frontend, gateway, sessions, assessment, reporting, scenario).
- `ktc-sim` — Simulation Engine-узлы (с повышенными требованиями к CPU/детерминизму).
- `ktc-ai` — ИИ-сервис (GPU).
- `ktc-data` — СУБД/кэш/хранилище (Picodata + Radix, в отдельном доверенном сегменте).
- `ktc-observability` — мониторинг/логи (Astra Monitoring) и SIEM-агенты (KUMA).
- `ktc-security` — PAM/секреты (Vault), антивирус/EDR-агенты.

Межсегментный трафик — по политике м/сетевого экрана (Istio/Calico NetworkPolicy), извне доступен только Gateway.

### 6.2. Топология по зонам
По требованиям ИБ компоненты разносятся по **отдельным ВМ с отдельными IP** в изолированных сегментах. В K8s это достигается:
- **Node Pool / taint+label** для зон: `app`, `db` (Picodata/Radix), `ai` (GPU), `monitoring`.
- Под по Simulation Engine планируется на узлах с большим CPU (dedicated nodes) для гарантии 1 Гц.
- AI-сервис — на **GPU-узлах** с `nodeSelector`/`taint`.
- СУБД/кэш (Picodata + Radix) — на узлах/несколько ВМ на **разных гипервизорах** (анти-аффинити, `podAntiAffinity`), кластер с Raft.

### 6.3. Отказоустойчивость
- **App-сервисы:** `ReplicaSet` N≥2, `PodDisruptionBudget`, HPA.
- **БД:** кластер **Picodata** (Raft-консенсус, встроенная репликация primary+follower) — автоматический failover < 30 сек через сервисное имя/VIP кластера; кэш **Radix** — на репликах Radix с ролью Sentinel.
- **Simulation:** per-session процесс; при падении — автоматический перезапуск с восстановлением из последнего чекпоинта/снапшота (≤15 сек), без потери прогресса (обрыв ≤3 мин).
- **ИИ:** fallback — недоступность ИИ не останавливает симуляцию и rule-based оценку.
- **Rolling Update / Blue-Green:** `Deployment.strategy=RollingUpdate`; readiness/healthz для безопасного переключения.

### 6.4. Масштабирование
- HPA по CPU/памяти для stateless-сервисов (gateway, auth, reporting, scenario).
- Simulation Engine — масштабирование по числу сессий (горизонтально: N активных сессий = N экземпляров движка; target до 50).
- AI-сервис — первые GPU-квоты, очередь инференса; масштабирование по числу запросов.
- Объём снапшотов — не менее 10 000 сохранённых состояний (object storage, SCL-02).

## 8. Аутентификация, авторизация и безопасность в K8s

- **Единая аутентификация:** LDAP/AD для всех ролей (ученик, инструктор, администратор, наблюдатель); токены JWT с коротким TTL.
- **2FA:** инструктор/администратор (TOTP); привилегированный доступ — через отечественный PAM.
- **RBAC:** разделение прав на уровне бэкенда при каждом запросе; наблюдатель — read-only.
- **Транспорт:** TLS 1.2+, запрет слабых шифров, ГОСТ-криптопровайдеры; SRI для статических ресурсов.
- **Rate limiting:** авторизация ≤10/мин, API ≤50/мин на endpoint.
- **Секреты:** Kubernetes Secrets + Vault (или Ansible Vault); секреты вне образов/репозитория.
- **Целостность:** SHA-256 для снапшотов/моделей; подписи ГОСТ для обновлений; контроль целостности таблиц БД.
- **Аудит/SIEM:** все события ИБ стекаются в **Kaspersky KUMA**, хранение аудита 1 год.
- **Доверенный репозиторий:** образы/артефакты из отечественного registry (GitFlic/внутреннее зеркало); SBOM; обновления без прямого доступа в интернет.
- **Политика безопасности пода:** `securityContext`, `seccomp`/`AppArmor`, `NetworkPolicy`, без root.

## 9. Проектирование под требования ИБ/ФСТЭК (У3, категория 3 КИИ при отнесении)

- Уровень защищённости **У3** (Приказ ФСТЭК №17), при отнесении к КИИ — консервативная **категория 3** (ПП №127).
- Сегментация сети: изолированные сегменты компонентов, доступ между ними по политике ФС (NetworkPolicy / межсетевой экран).
- Разнесение БД на 2+ ВМ на **разных гипервизорах** (анти-аффинити на уровне K8s).
- Физическое/логическое разделение сервера приложений и хранилища шаблонов (DEP-03/SEC2-02).
- Контроль целостности моделей/сценариев при загрузке и обновлении.
- Всё на **Astra Linux SE 1.8** для категорированных КИИ.

## 10. Прототип vs Целевая архитектура

| Аспект | Прототип (MVP) | Целевая |
|--------|----------------|---------|
| Оркестрация | Docker Compose → Swarm | **Kubernetes** (Managed ВК Cloud / Deckhouse) |
| Состав сервисов | укрупнённый (backend + Sim + AI) | полная микросервисная декомпозиция (см. §4.2) |
| БД | один Picodata-инстанс (допустимо) | кластер Picodata (Raft) failover <30 сек |
| Кэш | локальный кэш процесса | Radix (Redis-совместимый) кластер |
| ИИ | локальный GPU-инференс | выделенный GPU-пул + очередь, mTLS |
| Сеть/ИБ | базовое RBAC | полная сегментация K8s, mTLS, SIEM, PAM |
| Масштаб | 1–5 сессий | до 50 сессий |

**Важно:** декомпозиция на микросервисы и контракты API выполняется так, что переход «прототип → K8s» не требует переписывания сервисов, только изменения схемы развёртывания.

## 10a. Обоснование выбора каждого микросервиса

Ниже — почему каждый сервис выделен отдельно и почему его нельзя просто «вложить» в соседний. Ключевые критерии выделения: **разные ресурсы**, **разное масштабирование**, **разные требования к надёжности/изоляции**, **разный жизненный цикл** и **разные права на данные** (безопасность).

### Frontend (Web-HMI SPA)
- **Зачем:** браузерное приложение (React) — мнемосхема, тренды, алармы, экраны всех ролей.
- **Почему отдельно:** тяжёлая клиентская визуализация (мнемосхема, 8 трендов, 1 Гц WebSocket) отделена от бизнес-логики; статика раздаётся как SPA и кэшируется, масштабируется независимо от бэкенда (CDN/статика). Обновление UI не перезапускает серверные сервисы.

### API Gateway / BFF
- **Зачем:** единая точка входа HTTPS/TLS, аутентификация (JWT), rate-limit, CSP, маршрутизация на микросервисы, проксирование WebSocket.
- **Почему отдельно:** сквозная роль (edge/секьюрити) — должна быть единственной открытой наружу; изолируется от бизнес-логики, даёт единое место для защиты от атак (SQLi/XSS/CSRF) и версионирования API. Если вложить в какой-то сервис — потеряется единая точка защиты.

### Auth / Session Service
- **Зачем:** LDAP/AD, JWT, RBAC, 2FA/PAM, управление сессиями.
- **Почему отдельно:** специфическая интеграция с корпоративным каталогом и ИБ-инструментами (PAM, 2FA); чувствителен к правам, выносится в изолированный сегмент и масштабируется отдельно. Объединение с оркестратором привело бы к смешению «превращения доступа» и «ведения сессии», усложнило аудит и разграничение прав.

### Session Orchestrator
- **Зачем:** создание/запуск/пауза/стоп сессий, модельное время (0.1×–10×), чекпоинты, WebSocket-телеметрия 1 Гц.
- **Почему отдельно:** это «мозг» реального времени — критичен к задержке (PERF-02) и должен переживать отказы движка/ИИ (деградация). Выделяется для обеспечения плавности WebSocket и изоляции от «тяжёлых» сервисов (отчёты, ИИ).

### Simulation Engine (по сессии)
- **Зачем:** цифровой двойник ЭЛОУ-АВТ (Model API: step/get_state/set_state/inject_fault/set_speed), тик 1 Гц.
- **Почему отдельно:** **самый ресурсоёмкий и детерминированный** сервис (CPU, гарантия 1 Гц); запускается per-session, чтобы сбой одной сессии не влиял на остальные; требует выделенного Node Pool (Node 'sim') и своих limit/requests. Объединение с оркестратором нарушило бы детерминизм и изоляцию сбоев (авария в одной сессии уронила бы все).

### Assessment Engine
- **Зачем:** эталон, штрафы, критические ошибки, итоговая оценка, переопределение инструктором.
- **Почему отдельно:** логика «правильности» и данные оценки требовательны к целостности и аудиту (HMAC-подпись, append-only); должна работать даже при недоступности ИИ (rule-based фолбэк). Отделяется для контроля прав (только инструктор/админ могут переопределять) и масштабируемости оценки.

### AI Service (GPU)
- **Зачем:** Explain / Predict(physics/behaviour) / Adaptive / риск.
- **Почему отдельно:** **требует GPU** (обособленный GPU-хост, Node Pool 'ai'), изолированный сервисный аккаунт, без сетевого доступа вовне; **должен деградировать** (его падение не останавливает симуляцию и правил-based оценку). Вложить в другой сервис — значит затащить GPU и ML-цикл в критичный real-time контур.

### Snapshot Service
- **Зачем:** save/restore полного состояния сессии (метаданные в БД + payload в S3, SHA-256).
- **Почему отдельно:** работает с объектным хранилищем и тяжёлой сериализацией; выполняет barrier на границе тика; должен быть доступен при обслуживании (backup/restore). Отделение упрощает управление объектным хранилищем и политики целостности (SHA-256/HMAC).

### Reporting
- **Зачем:** генерация PDF-отчётов и протоколов экзамена.
- **Почему отдельно:** **тяжёлая асинхронная задача** (PERF-05 ≤ 20 сек), не должна блокировать сессию (INT-03); выполняется через очередь (брокер). Объединение с интерактивными сервисами замедлило бы real-time контур и усложнило бы масштабирование под всплески генерации.

### Scenario / Catalog Service
- **Зачем:** библиотека сценариев, Low-Code конструктор, шаблоны техпроцесса.
- **Почему отдельно:** управление «коммерческой тайной» (сценарии/модели), чёткое RBAC (инструктор правит только свои копии), физическое разделение хранилища шаблонов (DEP-03). Отделяется как доверенный компонент с ограниченным набором прав записи.

### Брокер сообщений (RabbitMQ/Kafka/NATS)
- **Зачем:** асинхронные задачи (отчёты, ИИ), события сессий, развязка сервисов.
- **Почему отдельно:** инфраструктурный компонент-«шина»; вынесен, чтобы сервисы не зависели друг от друга напрямую и асинхронная обработка не блокировала интерактив.

## 10b. Доставка метрик и логов в Astra Monitoring

В КТК используются **два разных канала** и **два разных компонента-сборщика** для двух типов данных observability (в дополнение к SIEM KUMA, который собирает события ИБ). **SNMP не используется** — метрики передаются исключительно в формате Prometheus (PromQL).

### А. Сбор метрик — компонент «Сбор метрик (Prometheus-совместимый)»

**Формат:** только Prometheus (PromQL). Протокол SNMP для передачи метрик **не применяется**.

**Что именно собирает и откуда:**
| Компонент-источник | Экспортер/агент | Что отдаёт |
|---|---|---|
| Каждый микросервис (Frontend, Gateway, Auth, Orchestrator, Sim, Assessment, AI, Snapshot, Reporting, Scenario) | встроенный `/metrics` (prometheus-client) | свои метрики: tick-lag модели, WebSocket-нагрузка, число сессий, latency, ошибки ИИ, время restore |
| Узлы K8s (Node Pool 'app'/'sim'/'ai'/'db') | **node-exporter** (DaemonSet) | CPU, RAM, диск, сеть |
| Simulation Engine (обособленные потоки) | `/metrics` движка | tick-lag, гарантия 1 Гц, число активных сессий |
| СУБД/кэш Picodata + Radix | **пикодата-экспортер** (аналог PG-экспортера; состояние Raft-кластера) | connections, lag/role узлов, failover-статус, состояние кэша |
| AI GPU-хост | **DCGM-экспортер / nvidia-exporter** + `/metrics` | GPU utilization, VRAM, температуру, очередь инференса |
| Веб-сервер/Gateway | nginx-exporter/Kong-метрики | HTTP-коды, rate-limit, WS-соединения |

**Как собирается:** в кластере деплоится **Prometheus-совместимый агент (kube-prometheus-стек)** с **ServiceMonitor/PodMonitor**, который по `ServiceMonitor`-критериям выборочно забирает `/metrics` со всех перечисленных источников по HTTP **scrape** (PromQL).

**Доставка в Astra Monitoring:** Prometheus-агент передаёт метрики в Astra Monitoring **по HTTP (endpoint, совместимый с PromQL / remote-write)**, без SNMP.

### Б. Сбор логов — компонент «Сбор логов (Fluent Bit DaemonSet)»

**Что собирает:** только логи (журналы) приложений.

**Компоненты-источники логов:** каждый микросервис (stdout/stderr, 12-factor), веб-сервер (Nginx access/error), СУБД/кэш (Picodata + Radix error-журналы через агента), Fluent Bit также может подхватывать системные журналы узлов (systemd-journal), если требуется.

**Как собирается:** **Fluent Bit (DaemonSet)** — один под на каждом узле K8s, забирает логи из контейнерного рантайма (`/var/log/containers`) и systemd-journal по всем узлам.

**Доставка в Astra Monitoring:** Fluent Bit передаёт логи в Astra Monitoring по **HTTP/Syslog-выходу** (без SNMP).

### В. Аудит и SIEM ИБ (Kaspersky KUMA)

- **Ключевое разделение:** Astra Monitoring — это **мониторинг и логи** (observability), но он **не является SIEM** по функциям корреляции событий ИБ и реагирования.
- **Аудит ИБ** (write-once журнал действий, входы, изменение сценариев/моделей, действия администратора, ошибки авторизации, выгрузка данных) стекается в **Kaspersky KUMA**:
  - **Fluent Bit** дополнительно направляет выбранные события ИБ в KUMA (события LDAP/AD, приложений, веб-сервера, СУБД, ОС, антивируса/EDR, межсетевого экрана, PAM);
  - KUMA коррелирует события, выявляет инциденты и инициирует реагирование (§5.3 Требования_ИБ), хранит аудит 1 год.

### Сводная схема потока observability

```
Микросервисы (stdout/stderr, /metrics, /healthz)
   │
   ├── метрики  ──►  [Сбор метрик: Prometheus-совм. агент (ServiceMonitor/PodMonitor,
   │                  node-exporter, пикодата/radix/dcgm-экспортеры)]
   │                        │ HTTP / remote-write (PromQL)
   │                        ▼
   │                  Astra Monitoring (метрики + дашборды)
   │
   └── логи ────►  [Сбор логов: Fluent Bit DaemonSet (stdout/stderr, systemd)]
                        │ HTTP/Syslog
                        ├──►  Astra Monitoring (логи)
                        └──►  Kaspersky KUMA (события ИБ, аудит, корреляция, реагирование)
```

**Итог по компонентам-сборщикам:**
- **Метрики** собирает **Prometheus-совместимый агент** (kube-prometheus-stack: ServiceMonitor/PodMonitor + node-exporter + экспортеры Picodata/Radix/GPU) → `Astra Monitoring` (PromQL, без SNMP).
- **Логи** собирает **Fluent Bit (DaemonSet)** → `Astra Monitoring` (HTTP/Syslog).
- **События ИБ / аудит** — **Fluent Bit** → `Kaspersky KUMA`.

## 11. Открытые вопросы (для обсуждения)

1. Выбор брокера сообщений: RabbitMQ / Kafka / NATS (для событий и очередей).
2. Внедрение сервисной сетки (Istio) на MVP или только взаимные mTLS-сертификаты.
3. Управляемый Managed Kubernetes ВК Cloud против Deckhouse (самохостинг).
4. Схема «физического» разделения СУБД на уровне K8s при использовании одного кластера (Node pool / отдельный кластер для данных).
5. Объём мультиарендности и проблема запуска per-session Simulation-процессов в подах (limit/requests, гарантия 1 Гц).
6. Подход к доставке logging/audit внутри кластера (даймонсет-агенты **Fluent Bit** → Astra Monitoring для логов, → KUMA для событий ИБ).
7. Соответствие требования «компоненты на отдельных ВМ с отдельными IP» жёсткой модели подов K8s — возможен гибрид (K8s для прикладного слоя + классические ВМ для БД-хостов).
