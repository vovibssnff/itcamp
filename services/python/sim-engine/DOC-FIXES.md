## 1. Live-инъекция неисправностей инструктором

### 1.1. В чём проблема

`ARCHITECTURE-2.md` в одном документе и **запрещает**, и **разрешает** инструктору
инжектить неисправности во время сессии.

**Запрет** (§3 «Роли и пользователи», строка 80) — это нормативное требование:

> Примечание: инструктор не инжектит неисправности в реальном времени — они срабатывают только автоматически из сценария (`FR-ROLE-04`).

Ему же соответствуют:

- §3, строка 77 — права инструктора: «настройка сценариев с **автоинъекцией** неисправностей», «подключение к любой сессии для наблюдения **read-only**»;
- `session_orchestrator.md` §2 — в списке функций **только** «Автоматическая инъекция неисправностей из сценария (по времени/условию)»; live-инъекции нет;
- `frontend.md` §2, модуль «Наблюдение» — «Просмотр телеметрии, трендов, алармов **без возможности вмешательства**».

**Разрешение** появляется в трёх местах и противоречит `FR-ROLE-04`.

### 1.2. Правка A — §1 «Что это за система», строка 35

**Было:**

```markdown
- **проводит** тренировки/экзамены с живым наблюдением и динамической «инъекцией» неисправностей.
```

**Надо:**

```markdown
- **проводит** тренировки/экзамены с живым наблюдением; неисправности вводятся автоматически
  по триггерам сценария (по модельному времени или по условию на теге).
```

**Почему:** формулировка «динамическая инъекция» читается как действие инструктора в реальном
времени. На деле динамика есть — но она задана заранее триггером по условию, а не рукой человека.

### 1.3. Правка B — §6.6 «Session Orchestrator», строка 235

**Было:**

```markdown
- **Автоматическая инъекция** неисправностей из сценария (по триггеру) → `sim.inject_fault`.
- **Live-инъекция** от инструктора в реальном времени.
- **Чекпоинты** и координация save/restore (через `snapshot`).
```

**Надо:**

```markdown
- **Автоматическая инъекция** неисправностей из сценария (по триггеру) → `sim.inject_fault`.
  Это **единственный** источник вызова `inject_fault`: внешнего маршрута к нему нет ни у `fe`,
  ни у `gw`, ни у инструктора (`FR-ROLE-04`).
- **Чекпоинты** и координация save/restore (через `snapshot`).
```

**Почему:** строка 235 удаляется целиком, вместо неё — явная фиксация инварианта.
Формулировка «единственный источник» важнее простого удаления: она не даёт вернуть
функцию при следующей итерации документа.

### 1.4. Правка C — §9 «Сквозной сценарий», этап 3, пункт 5, строка 429

**Было:**

```markdown
5. **Неисправности**:
   - *Автоматически*: планировщик событий в `orchestrator` проверяет триггеры сценария → `sim.inject_fault`.
   - *Live*: инструктор в реальном времени инжектит неисправность в компонент → `sim.inject_fault`.
```

**Надо:**

```markdown
5. **Неисправности** (только автоматически, `FR-ROLE-04`):
   - *По модельному времени*: планировщик событий в `orchestrator` проверяет
     `model_time_s ≥ trigger.at_s` → `sim.inject_fault`.
   - *По условию*: планировщик проверяет предикат на теге
     (например, `PRSA 204 ≥ 4.0`) → `sim.inject_fault`.

   Инструктор наблюдает срабатывание на таймлайне, но не инициирует его.
   Вариативность сценария обеспечивается триггером по условию, а не ручным вмешательством.
```

**Почему:** заодно раскрывается, что «автоматически» — это два разных типа триггера.
Сейчас читатель может решить, что автоматика = только расписание, и поэтому live-инъекция
нужна «для гибкости». Она не нужна: условный триггер даёт ту же гибкость.

## 2. Эффекты ПАЗ по сценариям 5.1 и 5.2

### 2.1. В чём проблема

Документация описывает эффекты блокировок мягче и по-другому, чем реализовано
в `sim_engine/physics/interlocks.py: INTERLOCK_EFFECTS`. Код здесь — источник истины
(он определяет, что реально произойдёт с моделью и что увидит обучаемый).

**Фактическая карта эффектов из кода:**

```python
INTERLOCK_EFFECTS = {
    "PRSA 204":       lambda n: _cut_furnace_fuel(n) + _cut_k2_steam(n),
    "PRSA 213":       lambda n: _cut_furnace_fuel(n) + _cut_k2_steam(n),
    "LRCA 641":       _elou_voltage_trip("LRCA 641"),
    "LRCA 640":       _elou_voltage_trip("LRCA 640"),
    "LRCA 639":       _elou_voltage_trip("LRCA 639"),
    "LRCA 606":       _safe_hold("LRCA 606"),
    "LRCA 4002-1":    _safe_hold("LRCA 4002-1"),
    "PRCA 220":       _k4_relief,
    "TR 1011":        _catalyst_cooldown,
}
```

### 2.2. Правка A — `sim-engine/README.md`, таблица «Соответствие сценариям», строка 129

**Было:**

```markdown
| 5.2 | `FLT-K31-LEVEL-LOW` | LRCA 606 < 15 % → trip Н-14 |
```

**Надо:**

```markdown
| 5.2 | `FLT-K31-LEVEL-LOW` | LRCA 606 < 15 % → `safe_hold` контура (соответствует останову откачки Н-14) |
```

**Почему:** в коде нет объекта «насос Н-14» с операцией trip — есть `_safe_hold("LRCA 606")`,
переводящий контур в безопасное положение. Формулировка «trip Н-14» заставляет искать
в модели то, чего в ней нет, и создаёт ложное ожидание у технолога при приёмке.
Правильная связка: технологический смысл (останов откачки) ← реализация (`safe_hold`).

## 3. Метка времени действия оператора: модельная, не астрономическая

### 3.1. В чём проблема

Это **не противоречие, а пробел** — самый опасный тип расхождения, потому что его
не видно при вычитке. Ни один документ не говорит, в каком времени фиксируется
действие оператора, при том что в системе времени **два**.

Что есть сейчас:

| Документ | Формулировка | Чего не хватает |
|---|---|---|
| `ARCHITECTURE-2.md` §6.6, стр. 238 | «Фиксация действий оператора и событий (журнал в Picodata)» | В каком времени |
| `session_orchestrator.md` §2 | «Фиксация действий оператора и событий (журнал в Picodata)» | То же |
| `ARCHITECTURE-2.md` §6.6, стр. 232 | «Управление **модельным временем** (0.1×–10×) через `sim`» | Не связано с журналом |
| `assessment.md` §2 | «Сравнение действий с эталоном сценария», «начисление штрафов» | Относительно какого времени считается норматив |
| `ARCHITECTURE-2.md` §10 | Сущность `OperatorAction` в перечне | Нет атрибутов |

### 3.2. Почему это критично

При `set_speed(10×)` одна секунда реального времени = десять секунд модельного.
Эталон сценария задан в **модельных** секундах:

```json
{"step":1,"action":"ACK_ALARM","target":"PRSA-204","within_s":60}
```

Если журнал пишет **астрономическое** время, а норматив задан в модельном, происходит следующее:

| Скорость | Реально прошло | Модельно прошло | Норматив `within_s: 60` | Итог при астрономической метке |
|---|---|---|---|---|
| 1× | 50 с | 50 с | уложился | верно |
| 10× | 50 с | 500 с | **не уложился** | ошибочно засчитан успех |
| 0.1× | 50 с | 5 с | уложился с запасом | ошибочно засчитан провал |

Последствия по цепочке: неверное время реакции → неверный балл → **невоспроизводимый балл**
(та же сессия, проигранная на другой скорости, даст другой результат) → рушится
`test_score_identical_with_and_without_llm` по смыслу и теряет силу HMAC-протокол экзамена.

Косвенное подтверждение, что реализация уже опирается на модельное время —
контракт `ai-service`, где журнал действий описан полем `model_time_s`:

```json
"actions": [{"model_time_s":95,"type":"ACK_ALARM","target":"PRSA 204"}]
```

То есть код прав, а документация просто молчит.
