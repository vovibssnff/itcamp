# Вопросы эксперту по инфраструктуре

> Пакет открытых вопросов для консультации с экспертом по инфраструктуре.
> Вопросы сгруппированы по темам, каждому присвоен приоритет:
> **Критично** — блокирует реализацию/аттестацию; **Важно** — влияет на архитектуру и ёмкость; **Желательно** — уточнение/оптимизация.
> К большинству вопросов дан **предлагаемый вариант ответа** — эксперт может подтвердить или скорректировать.

---

## 1. Масштаб и нагрузка

### Q1. 50 vs 10 одновременных сессий (Критично)
В SRD зафиксировано до **50** сессий (`NFR-PERF-03`), в сводном документе рабочая нагрузка — **10** (`p. 1.8`, зафиксировано). От чего считать ёмкость кластера для реального развёртывания — от 50 (пик) или от 10 (штат)?

**Предлагаем:** ёмкость проектировать под 50 сессий (пик), рабочую конфигурацию — под 10–15. Кластер (HPA, пулы) должен выдерживать 50 без перепроектирования.

### Q2. «1 сессия = 1 sim-worker» на 1 Гц (Критично)
Реально ли выдерживать **50 одновременных ODE-симуляций** на частоте ≥1 Гц на заявленной конфигурации, и как сильно нагрузка зависит от размера графа (до 200 узлов) и глубины модели (L1)?

**Предлагаем:** заложить маржу на 60–70% загрузки узла `sim`; проверить нагрузочным тестом (TEST-06) на 50 сессий.

## 2. Облачная платформа и гипервизор

### Q3. ВК Cloud vs On-premise как целевая площадка (Критично)
Какой режим является **целевым для аттестации по ФСТЭК** — ВК Cloud (облако) или собственная площадка (учебный класс предприятия)? Меняется ли класс защищённости (У3 / категория 3 КИИ) в зависимости от площадки?

**Предлагаем:** целевая площадка — собственный ЦОД/учебный класс с ВК Cloud-совместимым гипервизором; облако — как резервная/удалённая площадка для инструкторов.

### Q4. Управляемый Deckhouse vs self-managed (Важно)
На чём развёрнут K8s: **управляемый Deckhouse (SaaS)** на ВК Cloud или **self-managed** на Astra Linux SE 1.8 + Deckhouse? Кто отвечает за обновление control-plane, и как это влияет на отказоустойчивость и аттестацию?

**Предлагаем:** self-managed Deckhouse на Astra Linux SE 1.8 (полный контроль и соответствие ИБ), уточнить вариант лицензии (community/enterprise).

---

## 3. GPU и ИИ-модуль

### Q5. Доступность GPU в ВК Cloud (Критично)
Какие GPU реально доступны в ВК Cloud (отечественные или NVIDIA), какой объём VRAM и какая квота нужна под vLLM/Ollama + PyTorch? Достаточно ли **одного GPU-узла** на 50 сессий, или требуется пул?

**Предлагаем:** минимум 1 GPU-узел (8–16 ГБ VRAM) с возможностью горизонтального масштабирования пула; квоту заложить заранее.

### Q6. Fallback без GPU (Важно)
Если GPU недоступны — допустим ли **fallback на внешний отечественный LLM API**? Сохраняются ли при этом критерий «обособленные ресурсы ИИ» и изоляция egress (сейчас у ИИ egress полностью запрещён)?

**Предлагаем:** основной путь — локальный GPU; fallback на внешний отечественный LLM API только при явном разрешении egress и с контролем ПДн (псевдонимизация).

## 4. Сеть и firewall

### Q7. Firewall-плашка ВК Cloud (Критично)
Как правильно организовать сегментацию через **firewall между ВМ на ВК Cloud**: одна firewall-VM или распределённые? Ставить плашку только на периметр или также между подсетями кластера и слоя данных?

**Предлагаем:** одна пограничная firewall-VM (периметр перед Istio Ingress + контроль egress к LDAP/AD/PAM); внутри кластера — Istio mTLS + NetworkPolicy.

### Q8. Ограничения по задержкам (Важно)
Достижима ли гарантия **≤500 мс** отклика UI при разнесении клиентов (учебный класс) и сервера (ВК Cloud) по разным сетям? Нужно ли резервировать канал/полосу под WebSocket-телеметрию 1 Гц?

**Предлагаем:** зафиксировать требование к каналу (задержка RTT ≤ 100 мс, потеря пакетов ≤ 0,1%) и подтвердить его выполнимость между площадками.

### Q9. Istio + NetworkPolicy достаточно? (Важно)
Достаточен ли стек **Istio mTLS + Kubernetes NetworkPolicy** для сегментации внутри кластера (namespace `app`/`sim`/`ai`/`data`), или для аттестации требуется дополнительный сетевой firewall между namespace?

**Предлагаем:** достаточно Istio + NetworkPolicy для внутренней изоляции; firewall ВК Cloud покрывает только сетевой периметр.

## 5. Хранение и БД

### Q10. Лицензия и возможности Picodata (Критично)
Подтверждена ли **лицензия/trial Picodata**? Реально ли обеспечить Raft-failover **<30 с** и PG-совместимость для наших миграций (**raw SQL без ORM-reflection**, т.к. pg_catalog реализован частично)?

**Предлагаем:** подтвердить лицензию и заранее проверить совместимость raw SQL/query builder с Picodata на пилотном наборе миграций.

### Q11. Radix как кэш (Важно)
Подтверждено ли использование **Radix** (Redis-плагин Picodata) как кэша, или предпочесть отдельный Redis? Какие TTL и объём горячего состояния нужны под 50 сессий?

**Предлагаем:** Radix в составе Picodata для горячего состояния; уточнить объём (ориентир 1–2 ГБ) и TTL (например 15 мин для кэша ИИ, по INT-04).

## 6. Отказоустойчивость и георезервирование

### Q12. Георезервирование: RPO/RTO (Критично)
Достаточна ли схема **«HaProxy на отдельной ВМ + Picodata Master/slave»** для заявленных целевых показателей? Каков реальный **RTO** при переключении на резервный кластер и **RPO** для снапшотов/БД?

**Предлагаем:** RTO ≤ 5 мин (переключение HaProxy + Picodata failover), RPO ≤ 3 мин (синхронизация чекпоинтов); подтвердить/скорректировать.

### Q13. Восстановление сессий при геопереключении (Важно)
При переключении на резервный кластер — **восстанавливаются ли активные сессии** (через чекпоинты) или сбрасываются? Нужна ли **синхронизация S3-снапшотов** между ЦОД?

**Предлагаем:** восстанавливать активные сессии из чекпоинтов (≤15 с); снапшоты реплицировать в off-site S3.

## 7. Безопасность и аттестация

### Q14. Уровень защищённости (Критично)
Достаточен ли **У3** (по ФСТЭК №17) для КТК как обучающей системы (не АСУ ТП), или категорирование по **КИИ (категория 3)** потребуется при внедрении на предприятии?

**Предлагаем:** консервативно — не ниже У3 и готовность к категории 3 КИИ при формальном категорировании.

### Q15. Антивирус и SIEM (Важно)
Совместимы ли выбранные **Kaspersky Endpoint Security / Dr.Web** (антивирус) и **MaxPatrol SIEM** (Positive Technologies) с контейнерной средой Deckhouse/K8s и Astra Linux? Как собирать события из контейнеров (Fluent Bit → SIEM)?

**Предлагаем:** антивирус на узлах кластера и АРМ; SIEM-коннекторы через сбор логов кластера (Fluent Bit) без установки агентов в каждый под.

### Q16. Секреты (Желательно)
Достаточно ли **Kubernetes Secrets + Vault** без внешнего HSM, учитывая требование ГОСТ-крипто для UI-трафика (TLS)? Нужен ли отдельный СКЗИ-модуль?

**Предлагаем:** для прототипа — Secrets + Vault; вопрос СКЗИ/HSM вынести отдельно на этап аттестации.

## 8. Прочее / организационное

### Q17. Лимит объёма снапшота (Важно)
Точный лимит объёма снапшота не зафиксирован (в сводном документе «подлежит уточнению»). Каков реалистичный размер payload на сессию? (исходно предлагалось «не более 50 Мб»)

**Предлагаем:** подтвердить лимит ≤ 50 МБ на снапшот либо дать целевое значение; оценить общий объём при 10 000 снапшотов (`NFR-SCL-03`).

### Q18. Размещение NATS (Желательно)
Где размещать брокер — в **`ktc-infra`** (целевой) или **`ktc-app`** (прототип)? Влияет ли размещение на latency real-time контура?

**Предлагаем:** целевое размещение — отдельный сегмент `ktc-infra`; в прототипе допустимо `ktc-app` (брокер не хранит критичные данные).
