## 1. Введение

### 1.1. Назначение документа

Настоящий Software Requirements Document (SRD) фиксирует функциональные и нефукциональные требования к разработке **веб-ориентированного компьютерного тренажёрного комплекса** для обучения и оценки квалификации оперативного персонала на блоке **ЭЛОУ** (электрообессоливание / обезвоживание) установки первичной переработки нефти ЭЛОУ-АВТ.

Документ служит:

- единым согласованным источником требований для команды разработки;
- основой архитектурных и инфраструктурных решений;
- трассировочной базой к критериям оценки кейса чемпионата;
- заделом под оформление ТЗ на АС по ГОСТ 34.602-2020 / стадийности ГОСТ Р 59793-2021.

### 1.2. Цели системы

1. Безопасно отрабатывать нормальные и аварийные режимы блока ЭЛОУ без риска для реального объекта.
2. Фиксировать действия обучаемого, оценивать квалификацию, формировать защищённый протокол экзамена.
3. С помощью модуля ИИ объяснять ошибки (причина → следствие → рекомендация), прогнозировать риски (физика процесса и поведение оператора) и генерировать адаптивные сценарии.
4. Обеспечить внедряемость на отечественном стеке в контуре **VK Cloud** без подключения к реальным системам управления производством.

### 1.3. Заинтересованные стороны


| Роль                                                | Интерес                                                  |
| --------------------------------------------------- | -------------------------------------------------------- |
| Заказчик кейса (ПАО «Газпром нефть» / организаторы) | Работоспособный прототип + проектная документация        |
| Оператор-ученик                                     | Реалистичный HMI, обратная связь                         |
| Инструктор                                          | Управление сценариями, инъекция отказов, разбор, экзамен |
| Администратор КТК                                   | Учётки, доступность, журналы                             |
| Команда разработки                                  | Чёткие Must/Should, ограничение scope на 2 недели MVP    |
| Инженер-технолог команды                            | Валидация модели и эталонных действий                    |


### 1.4. Область применения и границы

**Входит в MVP:** консольный оператор блока ЭЛОУ; web-HMI; серверная модель; сессии; снапшоты; ≥3 аварии; экзамен; ИИ на отдельном GPU-хосте; кластер БД Tantor; мониторинг Пульт/Графиня.

**Не входит (Won’t / Could):** полевой оператор, VR/3D, онлайн-интеграция с АСУ ТП / SCADA / OPC / Modbus, LDAP/Active Directory на MVP, полная модель атмосферного и вакуумного блоков АВТ, имитация всего сырьевого парка Р-10…Р-15 как самостоятельной игры.

## 2. Обзор системы

### 2.1. Концепция

КТК — **интеллектуальный операторский тренажёр (Intelligent OTS)** с тренировочным цифровым двойником блока ЭЛОУ:

- браузерный интерфейс, имитирующий рабочее место консольного оператора (мнемосхема, теги, тренды, алармы, контуры регулирования);
- серверный Simulation Engine, обновляющий параметры не реже 1 раза в секунду модельного времени;
- Assessment Engine на основе нормативно-описательного сравнения с эталоном;
- AI Module на обособленном GPU-хосте;
- полная изоляция от реального производственного контура (OT).

### 2.2. Позиционирование относительно DeltaSim

Российская платформа DeltaSim — зрелый класс высокоточных КТК с эмуляцией РСУ. Наш продукт **не претендует** на превосходство по глубине физики на этапе MVP. Преимущество формулируется так:


| Ось                | DeltaSim (типично)                 | Наш КТК                                                     |
| ------------------ | ---------------------------------- | ----------------------------------------------------------- |
| Доставка           | Толстый клиент / локальные станции | Web-HMI, быстрый rollout                                    |
| Оценка             | Правила / штрафы                   | Правила + ИИ: explain / dual predict / adaptive generation  |
| Архитектура        | Классический центральный сервер    | Модульный Model API, контейнеры, горизонтальный рост сессий |
| ИБ                 | Не акцент кейса                    | Threat model, RBAC, HMAC-печать протокола, аудит            |
| Отечественный стек | Реестр ПО                          | Tantor, Пульт/Графиня, путь к сертифицированным ОС/СЗИ      |


### 2.3. Контур развёртывания

Целевая площадка MVP: **VK Cloud**.

```text
[Браузер оператора/инструктора]
        | HTTPS
[Балансировщик / вход]
        |
[App: Swarm или Compose] ---- [GPU-ВМ: AI Inference]
        |
[Кластер Tantor + Patroni]    [Object Storage: снапшоты, отчёты]
        |
[Пульт + Графиня]
```

Связь с сетью АСУ ТП / контроллерами / OPC **запрещена**.

### 2.4. Режимы использования


| Режим                      | Описание                                                    | Приоритет |
| -------------------------- | ----------------------------------------------------------- | --------- |
| Тренировка с инструктором  | Инструктор запускает сценарий, может инжектить отказы       | Must      |
| Самостоятельная тренировка | Без инструктора, повтор пройденных сценариев                | Should    |
| Квалификационный экзамен   | Без подсказок ИИ-assist, лимит времени, защищённый протокол | Must      |
| Демонстрация               | Инструктор показывает эталон; ученик наблюдает              | Should    |

### 3.2. Моделирование блока ЭЛОУ

Граница модели MVP (по §3.2–3.3 технологического регламента из вводных данных):

**Н-1*** → подогрев **Т-1…Т-11** (три потока) → смесители **А-19 / А-20** → электродегидраторы **Э-1,3,5 → Э-2,4,6** → **Е-16 / Е-15** → **Н-20***.


| ID        | Требование                                                                                                                                                                              | Приоритет |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| FR-SIM-01 | Simulation Engine рассчитывает динамику тегов ЭЛОУ с периодом обновления **не реже 1 Гц** модельного времени                                                                            | Must      |
| FR-SIM-02 | Модель учитывает: расход/температуру/давление сырья; подачу промывной воды (ориентир 5–10 %); деэмульгатор; уровни раздела фаз; эффективность обессоливания/обезвоживания; состояние HV | Must      |
| FR-SIM-03 | Рабочие якоря: давление в электродегидраторах **4,5–10 кгс/см²**; температура сырья после подогрева **не более 140 °C**                                                                 | Must      |
| FR-SIM-04 | Реализованы блокировки HV: уровень нефтепродукта **< 3500 мм** → снятие/запрет напряжения; для Э-2/4/6 — отключение по току (ориентир **90 А**) и газовой подушке                       | Must      |
| FR-SIM-05 | Регуляторы расхода FRC 404/405/406 и уровни LRCA 639…645 моделируются упрощённо (ПИД/логика достаточная для обучения)                                                                   | Must      |
| FR-SIM-06 | Допускается визуальное схлопывание трёх параллельных потоков в 1–2 на мнемосхеме при сохранении ключевых имён тегов (согласование с технологом)                                         | Should    |
| FR-SIM-07 | Строгий сходящийся материальный баланс всей установки — не требуется; динамика должна быть правдоподобной и принятой технологом                                                         | Must      |
| FR-SIM-08 | Model API: `step`, `get_state`, `set_state`, `inject_fault`, `set_speed` — стабильный контракт для замены движка (L1→L3)                                                                | Must      |


Уровни зрелости модели:

- **L1** — правила и упрощённые ODE/lookup (MVP);
- **L2** — расширенная физика ЭЛОУ;
- **L3** — промышленный solver / внешний модуль через тот же Model API (Target).

### 5.3. АРМ оператора: двухэкранная компоновка (как на реальной консоли)

Рабочее место оператора приближено к реальной операторной РСУ и рассчитано на **два монитора Full HD**. Технически это два полноэкранных окна одного web-приложения, привязанных к одной сессии (`session_id`); оба получают идентичный поток телеметрии по WebSocket, а сервер остаётся единственным источником истины (ARCH-02). Профиль экрана задаётся параметром запуска окна (например, `?screen=overview` и `?screen=control`).

**Экран 1 — обзорный (Process Overview).** Задача — «панорама установки» и раннее обнаружение отклонений:

1. **Строка состояния (общая для обоих экранов):** модельное время, коэффициент скорости, режим (Тренировка/Экзамен/Демо), индикатор связи, счётчики алармов по приоритетам.
2. **Баннер алармов:** самый приоритетный неквитированный аларм + кнопка квитирования.
3. **Полная мнемосхема блока ЭЛОУ** (по `01_Схема КТС.pdf`, §3 регламента):
  - линия сырья: **Н-1/1А/1Б/1В** → блок теплообменников **Т-1…Т-11** (три потока, допускается визуальное упрощение) → регуляторы **FRC-404/405/406**;
  - смесители **А-19/1,3,5** (1-я ступень) и **А-20/2,4,6** (2-я ступень), ввод промывной воды (**Н-82**) и деэмульгатора (**Н-100к**);
  - электродегидраторы 1-й ступени **Э-1, Э-3, Э-5** и 2-й ступени **Э-2, Э-4, Э-6** с индикацией U/I электродов и блокировок HV;
  - ёмкости **Е-16** (солёная вода/улов) и **Е-15** (обессоленная нефть), откачка **Н-20/20А/20Б**;
  - у каждого аппарата — «живые» числовые поля тегов (T, P, F, L, U, I) и статусные значки.

**Экран 2 — рабочий (Control & Trends).** Задача — детальная работа с узлом и динамикой:

1. **Строка состояния** (синхронна с экраном 1).
2. **Тренды** — 4–8 параметров с общим масштабом времени и линиями уставок/границ алармов.
3. **Faceplate управляемого узла** — крупная панель PV/SP/OUT, Auto/Manual, пределы, команды.
4. **Журнал событий/алармов** — прокручиваемый список с модельным временем.
5. **Кнопка ESD** — постоянно доступна (дублируется на обоих экранах), с подтверждением.

Раскладка допускает работу и на одном мониторе (оба блока на одной странице со вкладками) — деградация для АРМ с одним экраном (см. `NFR-INFRA-03`).

## 7. Архитектура системы

### 7.1. Стиль архитектуры

Система строится как **модульное клиент-серверное веб-приложение** с сервис-ориентированным разделением на несколько независимо развёртываемых контейнеров и авторитетным серверным состоянием. Обмен телеметрией — по WebSocket (push модели), управляющие операции — по REST. Такой стиль выбран сознательно вместо «толстого клиента»: он даёт быстрый rollout web-HMI (отличие от DeltaSim), горизонтальный рост по числу сессий и чёткую границу изоляции от OT-контура.

### 7.3. Технологический стек по слоям

#### 7.3.1. Фронтенд (Web-HMI)

- Язык и фреймворк: **TypeScript + React**, сборка **Vite**.
- Управление состоянием: Redux Toolkit или Zustand (фиксируется в начале разработки).
- Мнемосхема: **SVG** с привязкой графических примитивов к `Tag ID`; обновление значений реактивно.
- Тренды: лёгкая канвас-библиотека визуализации временных рядов (например, uPlot) для отрисовки 4–8 серий при 1 Гц без деградации.
- Реальное время: нативный **WebSocket**-клиент с авто-переподключением и индикатором «нет данных».
- Интернационализация: словари ru/eng (i18n), переключение без перезагрузки.
- HTTP-клиент: fetch/Axios к REST API; авторизация — токен в заголовке.

#### 7.3.2. Бэкенд (прикладные сервисы)

- Язык: **Python 3.12+** (единый стек с моделью и ИИ снижает интеграционные издержки в 2-недельном MVP; команда сильна в web/Python).
- Веб-фреймворк: **FastAPI** (ASGI), сервер **Uvicorn**; WebSocket через Starlette.
- Доступ к БД: **SQLAlchemy (async)** + драйвер **asyncpg** к Tantor (PostgreSQL-совместимость); миграции — **Alembic**.
- Валидация/конфигурация: **pydantic**, `pydantic-settings` (лимиты, параметры БД/хранилища, ключи — из окружения/секретов).
- Кэш / шина событий (Should): in-process на MVP; для роста — совместимая in-memory СУБД (рассматривается отечественный **Tarantool** как кэш/брокер сессий, либо Redis-совместимое решение).
- Объектное хранилище: **S3-совместимое** (VK Cloud Object Storage; для локальной разработки — MinIO) для payload снапшотов и отчётов.

#### 7.3.3. Simulation Engine (цифровой двойник)

- Реализация на Python с **NumPy/SciPy** для интегрирования упрощённой динамики (уровни раздела фаз, тепловой и расходный баланс, эффективность обессоливания) и логики блокировок HV.
- Тик-цикл ≥ 1 Гц модельного времени; управление скоростью 0.1×…10× (FR-SIM-01, FR-SESS-02).
- **Model API** (стабильный контракт): `step`, `get_state`, `set_state`, `inject_fault`, `set_speed`. Это точка расширения L1→L2→L3: движок заменяется (вплоть до внешнего промышленного solver) без изменений HMI/ИИ (ARCH-01).

#### 7.3.4. AI Service

- Развёртывание на **отдельной GPU-ВМ**; вызовы — по внутреннему AI API (`explain`, `predict_physics`, `predict_behaviour`, `generate_scenario`); транспорт защищён (mTLS).
- LLM-инференс локально (например, через **vLLM** или **Ollama**), с приоритетом отечественных/открытых весов (например, семейство GigaChat/Qwen — выбор фиксируется отдельно); генерация объяснений и адаптивных сценариев.
- Predict(physics): экстраполяция трендов/использование модели для прогноза достижения уставок; Predict(behaviour): классификатор риска ошибочного действия (scikit-learn/PyTorch) по фичам сессии.
- Деградация: недоступность ИИ не останавливает симуляцию и rule-based оценку (FR-AI-01, NFR-REL-04).

#### 7.3.5. Данные и хранение

- Реляционное ядро: **кластер Tantor Ordinary + Patroni** (primary + ≥1 replica, авто-failover через сервисное имя/прокси — NFR-REL-01/02).
- В БД: справочник тегов (версионируемый), сессии, журналы действий/алармов, оценки, метаданные снапшотов, протоколы экзамена.
- В объектном хранилище: бинарный payload снапшотов и PDF-отчёты; целостность — checksum, для протокола — HMAC.
- Время: серверные метки NTP/chrony на узлах (DATA-02).

#### 7.3.6. Развёртывание, сеть и оркестрация

- Контейнеризация всех сервисов (**Docker**); оркестрация **Docker Compose → Swarm** (Target: Deckhouse / Managed K8s VK Cloud).
- Обратный прокси и TLS-терминация: **Nginx** (рассматривается отечественный форк **Angie** для усиления «отечественности» контура), маршрутизация к API и статике фронтенда, проксирование WebSocket.
- Площадка: **VK Cloud**; логические роли ВМ — App(Swarm), DB(Patroni), AI(GPU), Object Storage, Monitoring (NFR-INFRA-02).
- Изоляция сети: сегмент КТК не имеет маршрутов в OT-сеть; исходящие промышленные протоколы (OPC/Modbus) запрещены на уровне сети и приложения (FR-ISO-*, ARCH-03).

#### 7.3.7. API и контракты

- Внешний **REST API** (OpenAPI/Swagger): аутентификация, управление сессией, сценарии, снапшоты, оценки, протоколы.
- **WebSocket**-канал: поток значений тегов, событий алармов, статусов узлов от сервера к клиенту.
- Внутренние контракты: **Model API** (движок) и **AI API** (инференс) — версионируются; **HMAC seal API** для подписи/проверки протокола экзамена.

#### 7.3.8. CI/CD и качество

- Репозиторий: **monorepo** (фронт, бэкенд, модель, ИИ, инфра-манифесты, Ansible-плейбуки).
- Пайплайн (GitLab CI / Gitea Actions): `lint → test → SAST → build → publish → deploy`.
- Тесты: **pytest** (+ testcontainers для реального PostgreSQL/MinIO), тесты фронтенда (Vitest/RTL).
- Безопасность кода: SAST (**Bandit/Semgrep**), проверка зависимостей; реестр иностранных OSS-библиотек с обоснованием (NFR-COMP-03).
- Артефакты: образы контейнеров публикуются в реестр (registry) с тегом версии/коммита; фронтенд собирается в статику.

#### 7.3.9. Автоматизированное развёртывание и обновление (Ansible)

Развёртывание и обновление стенда **полностью автоматизированы** и не выполняются вручную в штатном режиме. Инструмент — **Ansible** (агентless, по SSH), плейбуки и роли хранятся в monorepo и версионируются вместе с кодом (Infrastructure as Code).

- **Инвентарь и роли узлов:** описываются группы `app` (Swarm-узлы), `db` (Tantor + Patroni), `ai` (GPU-ВМ), `monitoring` (Пульт/Графиня), `proxy` (Nginx/Angie). Параметры окружений (dev/stage/prod-демо) — в inventory + group_vars.
- **Роли Ansible (примерный состав):** `common` (базовая настройка ОС, NTP/chrony, пользователи, firewall/сегментация OT-изоляции), `docker` (движок + Swarm init/join), `tantor_patroni` (кластер СУБД, etcd/консенсус, VIP/сервисное имя), `objectstorage` (доступ к S3-хранилищу/секреты), `app_stack` (развёртывание стека сервисов), `proxy` (Nginx/Angie, TLS, маршруты WS), `monitoring` (агенты Пульт, дашборды Графиня), `ai_host` (драйверы GPU, среда инференса).
- **Секреты:** через **Ansible Vault** (пароли БД, ключ HMAC протокола, токены реестра); в образы и репозиторий секреты не попадают (трассируется на NFR-SEC-07, NFR-SEC-02).
- **Обновление приложения (rolling update):** пайплайн после `publish` вызывает Ansible, который последовательно обновляет сервисы Swarm (`docker service update` с `--update-parallelism`/`--update-delay`), применяет миграции БД **Alembic** до переключения трафика и выполняет health-проверку `/healthz`; при неуспехе — автоматический откат на предыдущий тег образа.
- **Идемпотентность и повторяемость:** повторный прогон плейбука не ломает уже настроенный стенд; полный стенд поднимается «с нуля» одной командой (важно для быстрого восстановления демо и для оценки «внедряемости» в кейсе).
- **Целевое (Target):** при переходе на Deckhouse/K8s роль деплоя заменяется на манифесты/Helm, при сохранении того же CI-контракта `build → publish → deploy`.

### 7.8. Механика снапшотов (полное состояние системы)

Снапшот — это **сохранённый слепок всей сессии**, позволяющий позже точно вернуть тренажёр в тот же момент и продолжить с идентичной динамикой. Это ключевая для обучения функция (Must): инструктор ставит группу в «интересную» точку (например, перед аварией), сохраняет и повторно раздаёт её ученикам.

#### 7.8.1. Что входит в «полное состояние»

Единица снапшота — состояние сессии, собираемое из трёх источников:

1. **Состояние Simulation Engine (ядро):**
  - все теги: PV/SP/OUT по справочнику (приложение A);
  - внутреннее состояние динамики: значения интеграторов ODE, аккумуляторы ПИД-регуляторов (FRC-404/405/406, LRCA-*), фильтры;
  - положение арматуры и статусы узлов: насосы (run/stop/fault), HV электродегидраторов (U/I, on/off/trip, активные блокировки);
  - активные аварии и стадия их развития; отложенные события планировщика аварий;
  - **модельное время** и коэффициент скорости;
  - **состояние ГПСЧ** (seed/внутреннее состояние) модели и планировщика — для детерминированного продолжения (FR-SNAP-06).
2. **Состояние сессии/оценки:** активный сценарий и его прогресс, выполненные шаги эталона, накопленные штрафы/отметки критических ошибок, состояние алармов (raised/ack), таймеры, режим (Тренировка/Экзамен/Демо).
3. **UI-контекст (для удобства, не влияет на физику):** открытый faceplate, выбранный набор трендов, раскладка экранов АРМ.

> Состояние AI Service в снапшот **не** входит: ИИ stateless относительно сессии и восстанавливается из журнала при необходимости (упрощает MVP и снимает зависимость от GPU-хоста при restore).

#### 7.8.2. Формат хранения

- Основной формат — **канонический JSON** с версией схемы (`schema_version`) — человекочитаемо, легко валидируется, напрямую ложится на контракт `get_state()/set_state()` Model API.
- Числовые массивы большого размера (при росте до L2/L3) допускается хранить в бинарном виде (MessagePack или `.npz`) внутри того же контейнера — без смены внешнего контракта.
- Payload **сжимается** (gzip/zstd); типичный размер L1 — единицы МБ, ограничение — ≤ 50 МБ (DATA-05).

Пример структуры (сокращённо):

```json

  "tag_dictionary_version": "2026.07",
  "session_id": "3f2a...uuid",
  "model_time_s": 5400.0,
  "speed": 1.0,
  "rng_state": { "model": "…", "fault_scheduler": "…" },
  "engine": {
    "tags": { "TR-41-2": 138.4, "LRCA-639": 3620, "HV-E1_I": 42.0, "…": "…" },
    "controllers": { "FRC-404": { "mode": "AUTO", "sp": 300, "i_acc": 12.7 } },
```

#### 7.8.3. Где и как хранится

- **Метаданные** — в Tantor (сущность `TagSnapshot`, §6.1): `id`, `session_id`, имя, `model_time`, автор, `schema_version`, `tag_dictionary_version`, размер, **SHA-256** payload, ключ объекта в хранилище, признак «пресет».
- **Payload** — в **S3-совместимом object storage** (VK Cloud Object Storage; в разработке — MinIO), объект **иммутабельный**, ключ = UUID снапшота. Разделение «метаданные в БД / payload в объектном хранилище» разгружает СУБД и совпадает с NFR-INFRA-04.
- **Стартовые пресеты** (≥3) — это те же снапшоты с флагом `is_preset`, доступные только на чтение.

#### 7.8.4. Процедура сохранения (save)

1. Клиент/инструктор шлёт `POST /sessions/{id}/snapshots` (имя, флаги).
2. Оркестратор сессии выставляет **барьер на границе тика**: текущий тик достаётся, следующий не запускается (FR-SNAP-05).
3. `engine.get_state()` + сборка состояния сессии/оценки + UI-контекст → единый объект.
4. Сериализация → сжатие → расчёт **SHA-256** → PUT в object storage → запись метаданных в Tantor.
5. Барьер снимается, симуляция продолжается. Целевое время операции ≤ 15 с (NFR-PERF-05); барьер держится минимально (только на сериализацию ядра).

#### 7.8.5. Процедура загрузки (load/restore)

1. `POST /sessions/{id}/restore` с `snapshot_id`.
2. Проверка совместимости `schema_version` и `tag_dictionary_version`; при несовпадении — отказ с сообщением (FR-SNAP-07). При необходимости — миграция схемы снапшота.
3. GET payload из object storage → проверка **SHA-256** (при рассинхроне — ошибка целостности, восстановление отклоняется).
4. Пауза тик-цикла → `engine.set_state()` → восстановление контроллеров, арматуры, активных аварий, ГПСЧ → восстановление состояния сессии/оценки и алармов.
5. **Рассылка полного свежего состояния** всем подключённым клиентам по WebSocket (оба экрана АРМ, инструктор) — FR-SNAP-08.
6. Снятие паузы → детерминированное продолжение.

#### 7.8.6. Целостность, безопасность и связь с оценкой

- Целостность payload — SHA-256; для снапшотов, приложенных к протоколу экзамена, дополнительно применяется **HMAC** (согласуется с NFR-SEC-02/10).
- Доступ к сохранению/восстановлению регулируется ролью (RBAC): в экзамене восстановление ученику запрещено; операции пишутся в append-only аудит.
- Восстановление во время экзамена помечается в протоколе (антифрод), т.к. влияет на трассируемость действий.


| ID      | Требование                                                                                                              | Приоритет |
| ------- | ----------------------------------------------------------------------------------------------------------------------- | --------- |
| ARCH-11 | Снапшот = метаданные (Tantor) + иммутабельный сжатый payload (object storage), целостность SHA-256                      | Must      |
| ARCH-12 | Save/restore идут через барьер тика и `get_state()/set_state()` Model API; движок заменяем без смены контракта снапшота | Must      |

## 10. Допущения и ограничения

### 10.1. Допущения

- Срок MVP ≈ **2 недели**.
- Команда сильнее в web-разработке, чем в классическом gamedev / Aspen-классе.
- В команде есть технолог для валидации.
- GPU-ВМ в VK Cloud будет выделена до интеграции ИИ.
- Регламент во `docs/IT-Camp/Вводные данные` — достаточный источник для тегов и аварий ЭЛОУ.

### 10.2. Ограничения

- Нет полевого оператора, VR, 3D.
- Нет online OT-интеграций.
- Нет LDAP на MVP.
- Физика L1; «лучше DeltaSim» только по cognitive/web/ИБ/API.
- Криптопротокола на MVP — HMAC, не СКЗИ.
- Редакция СУБД на MVP — **Tantor Ordinary** (не Certified).
- Иностранные библиотеки — только по списку исключений.

### 10.3. Зависимости

- Доступ в проект VK Cloud, квоты на GPU.
- Лицензии/trial Пульт и Графиня (уточнить у вендора).
- Дистрибутив Tantor Ordinary.

## Приложение B. Аварии и эталонные действия (черновик для технолога)

### B.1. FR-AV-01 — КЗ / пробой электродов

**Триггер:** инструктор / сценарий.  
**Симптомы:** рост тока HV, trip, падение QUAL-*, возможные алармы.  
**Эталон (укрупнённо):** зафиксировать аларм → снять/подтвердить HV trip → снизить нагрузку/проверить уровень → не включать HV до нормализации → доклад инструктору.  
**Критические ошибки:** повторные включения HV при активном КЗ; игнор аларма > T_lim.

### B.2. FR-AV-02 — Срыв уровня раздела фаз / обводнение

**Симптомы:** LRCA min/max, рост воды в продукте, риск блокировки HV по уровню.  
**Эталон:** квитировать → корректировать LRCA/дренаж в Е-16 → проверить воду на смешение → не допускать уноса → при блокировке HV действовать по регламенту включения.  
**Критические ошибки:** увеличение подачи сырья при аварийном уровне; принудительный обход блокировки.

### B.3. FR-AV-03 — Отказ Н-1 / потеря расхода

**Симптомы:** падение FR/PRA-351, увод T, дисбаланс потоков.  
**Эталон:** обнаружить → перейти на резервный насос (если смоделирован) / снизить нагрузку → стабилизировать FRC → проверить последствия на Э-* → доклад.  
**Критические ошибки:** продолжение работы без расхода с нагревом/осушением уровней.

Детализация шагов эталона уточняется технологом до заморозки сценариев экзамена.
