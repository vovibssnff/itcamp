# ИИ-модуль Конструктора КТК

Микросервис ИИ для компьютерного тренажёрного комплекса установки **ЭЛОУ-АВТ**.
Реализует требования FR-AI-01…FR-AI-07 и FR-ASSESS-01…04 из SRD «Конструктор КТК» v2.1.

## Что делает сервис

| Возможность | Как реализовано | Требование |
| ----------- | --------------- | ---------- |
| Анализ действий обучаемого | Выравнивание журнала действий с эталоном сценария (LCS) | FR-ASSESS-02 |
| Оценка времени реакции | Разность модельных меток времени, норматив квитирования | FR-ASSESS-01 |
| Оценка последовательности команд | Различение «вовремя / не по порядку / пропущено / просрочено» | FR-ASSESS-02, 03 |
| Объяснение (Explain) | LLM + RAG по регламенту, формат «причина → следствие → рекомендация» | FR-AI-02 |
| Прогноз выхода на уставку | Взвешенная линейная регрессия по тренду, без LLM | FR-AI-03 |
| Оценка риска действия | Правиловый движок по каталогу опасных действий + формулировка LLM | FR-AI-04 |
| Чат-бот обучаемого | Справочник по регламенту, без доступа к телеметрии | — |
| Разбор сессии | LLM с деградацией до структурного разбора | FR-ASSESS-06/07 |

## Ключевые архитектурные решения

### ADR-001. ИИ не считает балл, а аннотирует его

Время реакции — это вычитание меток времени. Сравнение с эталоном — алгоритм
выравнивания последовательностей. Ни то, ни другое не требует языковой модели,
зато требует **воспроизводимости**: один и тот же журнал обязан давать один и тот же
балл, иначе протокол экзамена с HMAC-подписью теряет смысл, а падение GPU-узла
обрушивает аттестацию (это прямо запрещено NFR-REL-03 и ARCH-02).

Поэтому:

```
Детерминированный слой (авторитетный)          ИИ-слой (совещательный)
├── reaction_time.py   время реакции           ├── распознавание эквивалентных стратегий
├── sequence.py        сравнение с эталоном     ├── интерпретация паттернов ошибок
├── scoring.py         итоговый балл    ──────► └── текст разбора и объяснений
└── результат неизменяем                            влияет только на текст, не на балл
```

`AnnotationService.annotate()` возвращает новый объект, где поле `assessment` —
исходный, неизменённый результат. Максимум, что может ИИ, — предложить инструктору
снять штраф (`suggested_score_delta`); применяет это решение человек (FR-ASSESS-05).

Свойство закреплено тестом `test_score_identical_with_and_without_llm`.

**Где ИИ действительно нужен.** Оператор может достичь цели допустимым, но не
эталонным способом — например, снять давление в К-1 не восстановлением орошения,
а снижением нагрева печи П-3 через TRC 3. Правила скажут «шаг пропущен».
ИИ распознаёт эквивалентную стратегию и выносит её на решение инструктора.

### ADR-002. Чат-бот не видит телеметрию

Если бот имеет доступ к текущим значениям тегов, он превращается в канал подсказок
в обход всей методики: «какое сейчас давление в К-1 и что делать» — и обучаемый
получает готовое решение. Поэтому бот отвечает **только** по регламенту и карточкам
оборудования.

Следствие: подсказать решение он физически не может, поэтому на экзамене его можно
не отключать — он работает как открытый справочник, что соответствует практике
реальной аттестации. Поведение переключается флагом `KTK_CHAT_IN_EXAM`.

Дополнительно бот отказывается раскрывать эталонные действия и критерии оценки.
Это **фильтр на входе** (`_SOLUTION_SEEKING`), а не инструкция в промпте: инструкции
обходятся переформулировкой.

### ADR-003. Галлюцинации по тегам отсекаются машинно

Языковая модель охотно «вспоминает» позиции приборов, которых в собранной установке
нет, и уставки, которых нет в модели. Обучаемый принимает это за истину.

`TagGuard` сверяет каждый упомянутый тег со словарём шаблона и **бракует ответ
целиком**, а не правит его. Забракованный ответ заменяется детерминированным
резервом. Инструкция «не выдумывай теги» в промпте тоже есть, но она снижает
вероятность, а гарантию даёт проверка.

### ADR-004. Деградация — обязательная часть каждого сценария

Каждый вызов LLM защищён предохранителем и имеет резерв:

| Сценарий | Резерв при отказе GPU |
| -------- | --------------------- |
| Explain | Карточка уставок и блокировок из словаря тегов |
| Чат-бот | Прямая цитата наиболее релевантного фрагмента регламента |
| Оценка риска | Заголовок сработавшего правила (суть предупреждения сохраняется) |
| Разбор сессии | Структурный разбор из фактов журнала |
| Балл | Не зависит от ИИ вообще |
| Прогноз уставки | Не использует LLM вообще |

## Быстрый старт

```bash
# 1. Тесты — работают без установки чего-либо (только Python 3.10+)
make test

# 2. Демонстрация сквозного сценария без GPU
PYTHONPATH=src python3 scripts/demo.py

# 3. Полный запуск с моделью
docker compose up --build
docker compose exec ollama ollama pull qwen2.5:14b-instruct
curl http://localhost:8080/readyz
```

## Структура

```
src/ai_service/
├── analysis/          детерминированное ядро (баллов касается только оно)
│   ├── normalize.py   единая форма позиций: «FRC 408» == «FRC-408»
│   ├── reaction_time.py
│   ├── sequence.py    выравнивание с эталоном
│   ├── scoring.py     авторитетный балл
│   └── profile.py     профиль ошибок обучаемого
├── services/          прикладные сценарии
│   ├── explain.py     FR-AI-02
│   ├── predict_physics.py    FR-AI-03 (без LLM)
│   ├── predict_behaviour.py  FR-AI-04
│   ├── chat.py        справочный чат-бот
│   ├── annotate.py    ИИ-аннотация поверх оценки
│   ├── debrief.py     разбор сессии
│   └── pipeline.py    сквозной разбор: журнал → балл → аннотации → текст
├── rag/               поиск по регламенту (BM25 + русский стемминг)
├── llm/               абстракция провайдера (Ollama / заглушка)
├── validation/        tag guard, формат ответа, контроль ПДн
├── resilience/        предохранитель
├── storage/           AIInsight: in-memory и Picodata
└── api/               REST (FastAPI) и gRPC
```

## API

Внутри кластера основной транспорт — **gRPC** (`proto/ktk/ai/v1/ai_service.proto`),
mTLS обеспечивает Istio sidecar. REST оставлен для BFF Angie и отладки.

| Эндпоинт | Назначение |
| -------- | ---------- |
| `POST /v1/session/review` | Анализ действий: время реакции, последовательность, балл, аннотации, разбор |
| `POST /v1/explain` | Объяснение аларма (в экзамене — `403 EXAM_MODE_BLOCKED`) |
| `POST /v1/predict/physics` | Прогноз выхода параметра на уставку |
| `POST /v1/predict/behaviour` | Оценка риска действия до подтверждения |
| `POST /v1/chat` | Справочный чат-бот |
| `GET /healthz`, `/readyz`, `/metrics` | Служебные |

Пример:

```bash
curl -s localhost:8080/v1/session/review -H 'Content-Type: application/json' -d '{
  "scenario_name": "Рост давления в К-1",
  "alarms":  [{"tag_id":"PRSA 204","priority":"HH","raised_at_s":0,"value":4.6,"limit":4.5}],
  "actions": [{"model_time_s":95,"type":"ACK_ALARM","target":"PRSA 204"},
              {"model_time_s":200,"type":"SET_SP","target":"FRC 408","value_from":18,"value_to":42}],
  "reference":[{"step":1,"action":"ACK_ALARM","target":"PRSA-204","within_s":60},
               {"step":2,"action":"START","target":"PUMP-N6A","within_s":90},
               {"step":3,"action":"SET_SP","target":"FRC-408","within_s":150,"value":42}],
  "criteria": {"pass_score":70,"ack_deadline_s":60}
}' | python3 -m json.tool
```

## Конфигурация

| Переменная | По умолчанию | Назначение |
| ---------- | ------------ | ---------- |
| `KTK_LLM_PROVIDER` | `stub` | `ollama` или `stub` (работа без GPU) |
| `KTK_LLM_MODEL` | `qwen2.5:14b-instruct` | Модель в Ollama |
| `KTK_OLLAMA_URL` | `http://localhost:11434` | Адрес Ollama |
| `KTK_DOCS_DIR` | `data/regulation` | Справочные материалы для чат-бота |
| `KTK_CHAT_IN_EXAM` | `true` | Работает ли справочник на экзамене (ADR-002) |
| `KTK_BREAKER_FAILURES` | `5` | Порог срабатывания предохранителя |
| `KTK_EXPLAIN_DEADLINE_S` | `12` | Дедлайн вызова Explain |

Секреты передаются через Kubernetes Secrets и в образ не попадают (NFR-SEC-07).

## Данные

* `data/tags_demo.json` — словарь тегов демо-шаблона с уставками и блокировками
  из регламента (65 тегов процесса + 11 команд оборудования).
* `data/risk_rules.json` — каталог опасных действий с привязкой к пунктам регламента.
* `data/regulation/` — текст разделов регламента для чат-бота.

Добавление недостающих разделов (пуск и остановка объекта, нормы технологического
режима, возможные неполадки) не требует правки кода: положите файл в
`data/regulation/` и выполните `make index`.

## Ограничения текущей версии

* **Поиск лексический (BM25) со стеммингом, без эмбеддингов.** Для корпуса в один
  регламент это работает — запросы почти всегда содержат позицию прибора или номер
  аппарата, и точное совпадение важнее семантической близости. Если понадобится
  отвечать на формулировки «своими словами», рядом встраивается векторный индекс:
  интерфейс `KnowledgeBase.search` менять не придётся.
* **Оценка риска действия — правиловая.** Интерфейс `RiskModel` готов под замену на
  обученный классификатор, как только накопится размеченный набор действий.
* **Генерация сценариев (FR-AI-05) вынесена в отдельную задачу** — она требует
  доступа к графу установки от Constructor Service и dry-run в Simulation Engine;
  контракт `GenerateScenario` в proto уже описан.
* **Corpus регламента неполон** — см. раздел «Данные».

## Тесты

```bash
make test   # 84 теста, ~0,05 с, без внешних зависимостей и без GPU
```

Покрыты: нормализация позиций приборов, время реакции, выравнивание
последовательности (включая различение «не по порядку» и «пропущено»), скоринг
и приоритет критических ошибок, прогноз уставок, отсев галлюцинаций, контроль ПДн,
защита чат-бота от выманивания решения и prompt injection, деградация при отказе
LLM, предохранитель, токенизация и чанкинг регламента.
