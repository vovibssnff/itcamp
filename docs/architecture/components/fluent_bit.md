# Компонент: Fluent Bit — сбор и маршрутизация логов

> Слой: Observability — `ktc-obs` / `ktc-infra` | Это: агент сбора логов (DaemonSet) | Протокол: stdout/stderr → Forward/HTTP (Пульт) + SIEM

## 1. Назначение

**Fluent Bit — «санитар логов».** Запускается на каждом узле кластера как
`DaemonSet` и собирает **stdout/stderr** всех контейнеров, нормализует, обогащает
и доставляет логи в центральный контур наблюдаемости (**Пульт**) и в **SIEM
(Kaspersky KUMA)** для аудита ИБ. Работает по принципу: контейнеры пишут в
stdout/stderr, а их доставку берёт на себя Fluent Bit — приложению не нужно думать
о файлах и хранилище логов.

## 2. Почему именно Fluent Bit (обоснование выбора)

| Требование | Как закрывает Fluent Bit |
|---|---|
| **Совместимость со стеком наблюдаемости** | лёгкий Linux-агент, нативно под K8s (DaemonSet), доставляется в Пульт |
| **Низкое потребление** | написан на C, малый footprint — безопасен на каждом узле |
| **K8s-нативный** | автообнаружение подов, подстановка метаданных (namespace, pod, label) |
| **Маршрутизация** | несколько выходов: Пульт (наблюдаемость) + KUMA (аудит ИБ) |
| **Отечественность** | нативный элемент контура Пульт+Графиня (см. ARCH-06) |

## 3. Как интегрирован с приложениями (использование в коде)

Приложения **пишут логи в stdout/stderr в структурированном JSON** — их собирает
Fluent Bit. Примеры из кода:

- **Go-сервисы** (`orchestrator`, `auth`, …): логгер `slog.NewJSONHandler(os.Stdout, …)`
  — структурированные JSON-записи уровня info/error прямо в stdout.
  (`services/go/orchestrator/cmd/orchestrator/main.go`)
- **Аудит**: общий пакет `services/go/shared/audit` эмитит события (audit.Emit)
  как JSON-логи для последующего сбора сторонней системой (SIEM/fluent).
  В `auth` модуль аудита публикует события входов, ошибок авторизации
  (**Fluent Bit → KUMA**).
- **Python-сервисы** (`sim-engine`): тот же принцип — логи и события в stdout с
  UTC-меткой (`wall_clock_utc`) для корреляции с инфраструктурными событиями.

**Потоки логов:**

| Источник (лог) | Назначение | Потребитель |
|---|---|---|
| Логи сервисов (app/sim/ai) | наблюдение, ошибки, производительность | **Пульт / Графиня** |
| События аудита (входы, авторизация, админ-действия) | аудит ИБ | **KUMA (SIEM)** |
| Логи инфраструктуры (Picodata, Radix, NATS, MinIO) | состояние компонентов | **Пульт / Графиня** |

## 4. Размещение

- `DaemonSet fluent-bit` в namespace `ktc-obs` — по **одному поду на узел**
  (собирает логи всех контейнеров на узле).
- Изолированный контур наблюдаемости `ktc-obs`/`ktc-infra`: Пульт, Графиня,
  Fluent Bit, NATS.
- Egress в KUMA — контролируемый через Egress Gateway.

## 5. Объекты Kubernetes

| Объект | Описание |
|---|---|
| DaemonSet `fluent-bit` | агент на каждом узле (сбор stdout/stderr) |
| ServiceAccount | права на чтение токенов подов/лог-файлов |
| ConfigMap | конфиги input/parser/output (Пульт, KUMA) |
| (Опц.) StatefulSet — агрегатор | при высоком объёме логов перед Пультом |

## 6. Метрики (в Пульт + Графиня)

- Объём собранных/доставленных логов (bytes/сек, events/сек).
- Ошибки разбора (parser fails), записи на сброс (buffer drop).
- Задержка доставки до Пульт и KUMA.
- Число подов/узлов без агента (gap в сборе).

## 7. Отказоустойчивость / масштабирование

- DaemonSet автоматически ставит агента на новые узлы (K8s).
- Буферизация на диске (backpressure) — при недоступности Пульт/KUMA логи не теряются.
- Retry + очередь доставки; при большом объёме — вынос агрегатора.

## 8. Связь с компонентами наблюдаемости

См. [pult_graphinya.md](pult_graphinya.md) — контур наблюдаемости целиком
(Пульт сбор метрик, Графиня дашборды, Fluent Bit логи). Разделение ролей:

| Инструмент | Что делает |
|---|---|
| **Пульт** | сбор метрик (Prometheus-совместимый) |
| **Графиня** | дашборды/алертинг |
| **Fluent Bit** | сбор/доставка **логов** (не метрик) |
| **KUMA** | SIEM — аудит ИБ |
