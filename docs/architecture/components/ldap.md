# Компонент: LDAP / Active Directory — внешняя идентификация

> Слой: Внешний (за пределами кластера) | Это: внешняя система учётных записей | Протокол: LDAP (3379) / LDAPS

## 1. Назначение

**LDAP/AD — «единый справочник пользователей».** Является **единственным
источником учётных записей и паролей** для платформы. Стандарт предприятия/площадки:
все сотрудники уже заведены в корпоративном каталоге, и тренажёр использует его
вместо собственного хранилища логинов/паролей.

## 2. Почему используется именно LDAP/AD (обоснование)

| Требование | Как закрывает LDAP/AD |
|---|---|
| **FR-AUTH-02** | учётные записи ведутся во **внешнем LDAP/AD** сторонним сервисом; платформа только проверяет учётные данные и ведёт **read-only** просмотр пользователей |
| **Безопасность** | паролей в БД платформы **нет** — их владельцем является AD (обычный для корпораций процесс) |
| **Единая учётная запись** | операторы/инструкторы входят той же учёткой, что и в остальные системы предприятия |
| **CRUD вне платформы** | создание/удаление/смена ролей — во внешнем AD, платформа не выполняет CRUD учёток (FR-AUTH-02, FR-ROLE-02) |

## 3. Использование в коде

Реализация — `services/go/auth/internal/security/ldap.go` (клиент
`github.com/go-ldap/ldap/v3`), конфиг — `LDAPConfig`.

**Как проходит вход:**
1. `auth` подключается к LDAP/AD (service bind).
2. Находит пользователя по `login` (`findUser`), выполняет `Bind` пользователя
   с введённым паролем (проверка пароля — в AD).
3. Считывает группы (`Groups`), маппит их в роли платформы (`MapRoles`: Администратор /
   Инструктор / Оператор).
4. Выдаёт **JWT** (access 15 мин, refresh 24 ч); **2FA (TOTP)** для инструктора/админа.

**Ключевое:** платформа **не хранит пароли** (в Picodata — только read-only профили/
роли). Вход возможен только через проверку в LDAP/AD.

## 4. Модель ролей (RBAC)

| Роль | Источник | Кто назначает |
|---|---|---|
| Администратор | группа в AD | внешний AD (вне платформы) |
| Инструктор | группа в AD | внешний AD |
| Оператор | группа в AD | внешний AD |

Роли маппятся из групп AD в RBAC платформы; просмотр пользователей/ролей —
read-only (FR-ROLE-02). Полномочия внутри платформы применяет `gw` (RBAC) по
заголовкам `X-User-ID`, `X-Roles`.

## 5. Размещение (почему во внешнем контуре)

- LDAP/AD — **внешняя** система предприятия, вне кластера (за Firewall VKCloud).
- Доступ только из `auth` (и `gw`); **единственная точка** обращения к внешнему
  каталогу. Egress — контролируемый через Egress Gateway (LDAP/AD, PAM).
- Privileged-доступ системного администратора — через отечественный **PAM**
  (вне RBAC платформы).

## 6. Безопасность

- Транспорт: LDAPS/TLS (в `DialTLS`), сервисный bind минимальных прав.
- Пароль нигде в платформе не сохраняется; аутентификация — только Bind к AD.
- Аудит входов → KUMA (SIEM), интенсивно в `auth`/`gw`.
- При недоступности LDAP — `ErrLDAPUnavailable` (деградация входа, не влияет на
  уже открытые сессии).

## 7. Объекты Kubernetes

| Объект | Описание |
|---|---|
| ExternalService / Egress | контролируемый доступ к внешнему LDAP/AD |
| Secret | учётные данные service bind, TLS-цепочки |
| (auth: Deployment/Service) | сервис, выполняющий Bind |

## 8. Метрики (в Пульт + Графиня)

- Успешные/неуспешные входы, latency LDAP-запроса.
- Отказы (LDAP unavailable), время Bind.
- (Аудит → KUMA для ИБ.)

## 9. Отказоустойчивость

- Недоступность AD — деградация входа (refresh/активные сессии продолжаются).
- read-only просмотр пользователей не блокирует работу тренажёра.

## 10. Открытые вопросы

1. Настройка групп AD и сопоставление их с ролями (MapRoles) под контур площадки.
2. Политика TOTP/2FA и её включение на проде.
3. Резервирование LDAP (несколько серверов/доменов).
