## 1. Что это за система

**Конструктор КТК** — платформа для визуального проектирования, сборки и эксплуатации **компьютерных тренажёрных комплексов (КТК)** нефтеперерабатывающих установок.

Главное отличие от классического КТК (где тренажёр «фиксирован» под одну установку): **это не тренажёр, а платформа**. Инструктор сам, без программирования (low-code):

- **собирает** установку на canvas из библиотеки типовых компонентов (насосы, колонны, печи, электродегидраторы, регуляторы…);
- **сохраняет** её как «шаблон установки» (можно копировать/редактировать/удалять);
- **генерирует или создаёт** учебные и экзаменационные сценарии (в т.ч. аварийные);
- **проводит** тренировки/экзамены с живым наблюдением и динамической «инъекцией» неисправностей.

Базовая библиотека покрывает **всю схему КТС установки ЭЛОУ-АВТ** (нефтепереработка): блок ЭЛОУ (обессоливание), атмосферный блок (ректификация, колонны К-1/К-2, печи), блок ГДМ (гидроочистка) и общеустановочные системы. Демо-стенд — фрагмент этой схемы.

**Контекст:** кейс IT-чемпионата нефтяной отрасли «КТК с цифровыми двойниками». Прототип/целевое решение, документ SRD v2.1.

## 2. Ключевая идея: граф как единица конфигурации

Вся система строится вокруг одного понятия — **графа установки**.

```
Граф установки (JSON)
│
├── Узлы (nodes) — экземпляры компонентов с параметрами (насос Н-2, колонна К-1…)
├── Рёбра (edges) — потоковые связи между портами (жидкость/газ/сигнал/электричество)
└── Layout — координаты мнемосхемы для отображения
```

Граф — это **единый источник конфигурации**, который питает все остальные части:

| Потребитель графа | Что делает с графом |
|---|---|
| **Simulation Engine** | По топологии (связям) динамически строит систему уравнений и запускает тик-цикл |
| **Рендерер мнемосхемы** | Отображает установку в HMI (или по ручной раскладке) |
| **Генератор сценариев** | Находит «уязвимые точки» графа для построения неисправностей |
| **Валидатор** | Проверяет корректность связей, отсутствие «висящих» портов |

Этот принцип (ARCH-07 «Граф как единица конфигурации») — то, что отличает «Конструктор» от классического КТК: **топология определяет всё**.

## 3. Роли и пользователи

Три роли (RBAC). Консолидированы в v2.1 — полномочия прежних дополнительных ролей собраны у Инструктора.

Роль **Администратор** относится к управлению **тренажёрным комплексом (КТК)**, а не к IT-инфраструктуре. Инфраструктурное администрирование (Deckhouse, VKCloud, СУБД, мониторинг кластера) **не входит** в ролевую модель платформы и вынесено за её рамки.

| Роль | Кратко | Права |
|---|---|---|
| **Администратор** | Управляет тренажёрным комплексом | Просмотр пользователей (учётки и роли ведутся в LDAP/AD сторонним сервисом, CRUD вне платформы); глобальный контроль учебной библиотеки; **жёсткое удаление** шаблонов/сценариев/типов компонентов; настройка политики оценки и экзаменационных правил; контроль качества обучения и учебный аудит |
| **Инструктор** | «Автор и судья» | Полный CRUD **своих** шаблонов/сценариев и компонентов; ведение каталога неисправностей; создание и управление **сессиями**; видимость **всех** сессий (не только своих); подключение к любой сессии для наблюдения **read-only**; настройка сценариев с автоинъекцией неисправностей; **экзамен**; **переопределение оценок** |
| **Оператор (обучаемый)** | Проходит обучение | Прохождение сессий, управление HMI, просмотр своей истории/оценок |

> Примечание: инструктор не инжектит неисправности в реальном времени — они срабатывают только автоматически из сценария (`FR-ROLE-04`).

**Экраны (карта интерфейса):** Вход → Каталог шаблонов → Конструктор (canvas) → Библиотека компонентов → Редактор сценариев → Консоль инструктора → АРМ оператора → Экран экзамена → Разбор/Replay+ИИ → Администрирование.

## 5. Слои и namespace'ы

Система физически разделена на слои — каждый в своём namespace Kubernetes (изоляция + разграничение прав):

| Namespace | Назначение | Сервисы |
|---|---|---|
| `ktc-app` | Прикладной слой (stateless сервисы) | `gw`, `auth`, `constructor`, `scenario`, `orchestrator`, `assessment`, `report`, `snapshot`, `fe` |
| `ktc-sim` | Вычислительный слой (Simulation Engine) | `sim-manager`, `sim-worker-*` |
| `ktc-ai` | Машинное обучение (GPU) | `ai` |
| `ktc-data` | Слой данных (персистентность) | Picodata, Radix, S3/MinIO |
| `ktc-obs` / `ktc-infra` | Observability + инфраструктура | Пульт, Графиня, Fluent Bit, NATS |

*(В SRD §7.9 namespace называется `ktk-*`, в сервисных доках — `ktc-*`. Это расхождение стоит унифицировать.)*

## 6. Модули системы (подробно)

### 6.1. Frontend — `fe`
**Что это:** SPA (React + TypeScript, Vite, Konva для canvas, uPlot для трендов, Ant Design).

**Тонкий клиент.** Никакой «истины» не считает — только отображает серверное состояние и отправляет команды (принцип **server-authoritative**). Состояние клиента (Zustand) — лишь кэш отображения.

**Модули FE:**
- **Конструктор** (инструктор): canvas drag-and-drop, палитра компонентов с фильтрацией по категориям, ручное соединение портов с проверкой типов, панель свойств, автосохранение каждые 30 с.
- **HMI оператора**: рендер мнемосхемы из layout, обновление по телеметрии 1 Гц (WS), тренды (до 8 серий), алармы HH/H/L/LL, faceplate-узлы (PV/SP/OUT, Auto/Manual), кнопка ESD.
- **Наблюдение** (инструктор): read-only подключение к любой сессии.
- **Администрирование** (админ): просмотр пользователей/ролей (учётки ведутся в LDAP/AD), политика оценки, учебный аудит, контроль учебного контента.

**Общается только через `gw`** — никогда напрямую с sim/db/auth/assessment/constructor.

---

### 6.2. API Gateway / BFF — `gw`
**Что это:** «ворота для бизнеса» — прикладной контрактный слой между клиентом и микросервисами.

**Важно различать:**
- **Istio Ingress Gateway** = *сетевой* вход: TLS, маршрутизация по host/path, балансировка, mTLS внутрь.
- **API Gateway / BFF (`gw`)** = *прикладной* вход: JWT/RBAC, агрегация (BFF-паттерн), версии API, rate-limit на уровне сессии, защита от SQLi/XSS/CSRF.

**Функции:** проверка JWT + применение RBAC; агрегация запросов из нескольких сервисов в один ответ клиенту; версионирование API; rate-limit (auth ≤10/мин, API ≤50/мин на endpoint); CSP/защитные заголовки; проксирование WebSocket-телеметрии; раздача статики FE; логирование → аудит/KUMA.

**Технология:** Angie (отечественный форк nginx) или BFF на Go/Python.

**Данные:** не хранит бизнес-данные, только кэш (JWT validation cache).

**Принцип:** никогда не ходит в `sim`/`db`/`s3` напрямую.

---

### 6.3. Auth / Session Service — `auth`
**Что это:** идентификация и управление доступом.

**Функции:**
- Проверка учётных данных в **LDAP/AD** (единственный способ входа; локальных учёток и паролей в БД нет).
- Выдача/проверка **JWT** (access TTL 15 мин, refresh 24 ч).
- **RBAC** (роли/права).
- **2FA (TOTP)** для инструктора/админа (роль Администратор КТК). Привилегированный доступ **системного администратора** (операционная роль, вне RBAC — эксплуатация кластера/сервера/БД) — через отечественный **PAM**.
- Сессии, логаут, аудит входов → KUMA.

**API:** `POST /login`, `/logout`, `/mfa/verify`, `GET /me`, `/refresh`, `POST /introspect`.

**Данные:** пользователи, роли, профили (в Picodata). Пароли не хранит (их хранит LDAP).

---

### 6.4. Constructor Service — `constructor`
**Что это:** «ядро конструктора» — библиотека компонентов и шаблоны установок.

**Функции:**
- **CRUD библиотеки компонентов** (`component_types`): типы оборудования (насос, колонна, печь, электродегидратор, реактор…) с портами, параметрами, категориями (ЭЛОУ/Атмосфера/ГДМ/Общие), иконками.
- **CRUD шаблонов установок** (`installation_templates`): граф (узлы+рёбра+параметры+layout).
- **Валидация графа**: типы связей (жидкость↔жидкость, сигнал↔сигнал), связность, наличие источника и стока, отсутствие «висячих» портов.
- **Копирование шаблонов** (deep clone).
- **Экспорт**: генерация init-конфигурации для Simulation Engine (Model API `set_state`).

**Общается с:** `gw` (CRUD), `scenario` (привязка сценария к шаблону), `orchestrator` (отдаёт init state при старте сессии).

**Технология:** Python/FastAPI. Данные в Picodata (JSONB для графов), иконки в S3.

---

### 6.5. Scenario / Catalog Service — `scenario`
**Что это:** библиотека и каталог учебных сценариев + эталонов оценки + каталог неисправностей.

**Функции:**
- CRUD сценариев (создание/редактирование/удаление/копирование).
- Сценарий привязан к **шаблону установки** (из `constructor`).
- Хранение **каталога неисправностей** (`fault_id`, описание, affected_tags, severity) и **эталонов оценки**.
- **Триггеры** неисправностей: по модельному времени или по условию (значение тега).
- **RBAC**: инструктор правит только свои сценарии.
- Контроль целостности (SHA-256).
- Экзаменационные сценарии: **случайная выдача** оркестратору.

**API:** `GET/POST/PUT/DELETE /scenarios`, `POST /scenarios/{id}/clone`; от orchestrator `GET /scenarios/{id}`, `GET /scenarios/exam`.

---

### 6.6. Session Orchestrator — `orchestrator`
**Что это:** «дирижёр сессии обучения» — мозг real-time контура. Управляет жизненным циклом сессии. Критичен к задержке (PERF-02), должен переживать отказы движка и ИИ (деградация).

**Функции:**
- Создание/запуск/пауза/стоп сессий; управление режимом (Тренировка/Экзамен).
- Получение конфигурации шаблона из `constructor` (init state) при старте.
- Управление **модельным временем** (0.1×–10×) через `sim`.
- Рассылка **телеметрии 1 Гц** клиентам (WebSocket).
- **Автоматическая инъекция** неисправностей из сценария (по триггеру) → `sim.inject_fault`.
- **Live-инъекция** от инструктора в реальном времени.
- **Чекпоинты** и координация save/restore (через `snapshot`).
- Координация Simulation Engine, Assessment, AI, Broker.
- Фиксация действий оператора и событий (журнал в Picodata).
- Подключение инструктора в режиме **read-only** (наблюдение).

**API:** `POST /session/start` `/pause` `/stop`, `GET /session/{id}`, `set_speed`; к клиенту WS (телеметрия); к `sim` gRPC Model API; к `scenario`/`constructor`/`assessment`/`snapshot`/`ai`; к `broker` NATS.

**Данные:** сессии, журналы действий/алармов, чекпоинт-метаданные (Picodata); горячее состояние сессии (Radix).

---

### 6.7. Simulation Engine — `sim`
**Что это:** цифровой двойник техпроцесса. **Единственный источник истины** о технологическом состоянии (все теги порождаются здесь, FR-ISO-03). Самый ресурсоёмкий и **детерминированный** сервис.

**Ключевая особенность — per-session экземпляры:**
- `sim-manager` (диспетчер) создаёт/удаляет `sim-worker-N` поды под сессии.
- **1 сессия = 1 изолированный под** (до 50). Сбой одной сессии не роняет другие.

**Функции:**
- Расчёт динамики установки (ЭЛОУ, колонны К-1/К-2, печи, насосы) по тику **≥1 Гц** модельного времени.
- **Model API**: `step`, `get_state`, `set_state`, `inject_fault`, `set_speed`.
- Порождение тегов/алармов (сигнализации, ПАЗ, ППК).
- Детерминированное исполнение (контроль ГПСЧ).

**Технология:** Python + NumPy/SciPy (численное интегрирование ODE). Модель L1 (упрощённая); точка расширения L1→L3 через тот же Model API.

**Изоляция:** не связан напрямую с фронтом, ИИ, assessment, report — только через `orchestrator`.

---

### 6.8. Assessment Engine — `assessment`
**Что это:** «экзаменатор и судья» — оценивает действия оператора по эталону.

**Функции:**
- Сравнение действий с **эталоном сценария** (берёт из `scenario`/Picodata).
- Начисление **штрафов**, отметка **критических ошибок** (HH/H/L/LL).
- Итоговая **оценка**, **переопределение** инструктором (с записью в аудит).
- **Append-only** журнал оценки с **HMAC-подписью** протокола.
- Пост-экзамен разбор (сбор статистики ошибок для AI).

**Характеристики:** работает **rule-based** (фолбэк при недоступности ИИ); целостность журнала защищена (append-only + HMAC).

---

### 6.9. Snapshot Service — `snapshot`
**Что это:** «сохранение игры» — сохранение и восстановление полного состояния сессии.

**Функции:**
- **save**: полное состояние сессии (модель, контуры, алармы, прогресс оценки, модельное время) → payload в S3 + метаданные в Picodata + SHA-256.
- **restore**: восстановление (≤15 с), детерминированно (включая ГПСЧ).
- Автосохранение (чекпоинт) — защита от обрыва ≤3 мин.
- В **экзамене** restore ученику **запрещён** (антифрод).

**Данные:** метаданные в Picodata, payload в S3 (иммутабельный, целостность SHA-256/HMAC). Объём хранения ≥10 000 снапшотов.

---

### 6.10. Reporting Service — `report`
**Что это:** «секретарь» — генерация отчётных документов и протоколов экзамена.

**Функции:**
- Генерация **PDF-отчётов** о ходе/результатах сессии (асинхронно, ≤20 с).
- Формирование **протокола экзамена** (канонический JSON + PDF) с **HMAC-подписью**.
- Хранение PDF в S3, метаданных/подписи в Picodata.
- Уведомление о готовности на FE.

**Ключевая характеристика:** тяжёлая **асинхронная** задача — выполняется через очередь NATS (`broker`), не блокирует real-time контур.

---

### 6.11. AI Service — `ai`
**Что это:** «умный помощник» на GPU. Изолированный сервис, **должен деградировать** (его падение не останавливает симуляцию и rule-based оценку).

**Функции (Explain / Predict / Adaptive):**
- **Explain** — объяснение решений/отклонений параметров (Smart Hint).
- **Predict (physics)** — прогноз достижения параметром критической уставки (Predictive Alert).
- **Predict (behaviour)** — оценка риска ошибочного действия оператора.
- **Adaptive** — адаптация сложности/личный план тренировок, генерация сценариев.
- **Post-exam разбор** (в экзамене подсказки во время сессии **отключены**, FR-AI-06).

**Технология:** GPU-хост, vLLM/Ollama (LLM), PyTorch/scikit-learn.

**Безопасность:** нет внешнего сетевого доступа (egress запрещён), изолированный serviceAccount, минимизация ПДн (псевдонимизация).

---

### 6.12. Message Broker — `broker`
**Что это:** «почтовая служба» — асинхронная шина и очередь задач. Развязывает сервисы: тяжёлая обработка (отчёты, ИИ) выполняется асинхронно и не мешает real-time контуру.

**Технология:** NATS JetStream (лёгкий, низкий latency <1 мс, гарантированная доставка, персистентность).

**Очереди/топики:**

| Топик | Продюсер → Потребитель |
|---|---|
| `report.tasks` | gw/orchestrator → report |
| `ai.tasks` | orchestrator → ai |
| `session.events` | orchestrator → assessment/инструктор |
| `assessment.events` | assessment → аудит |

**Размещение (спорный вопрос):** идеально — отдельный сегмент `ktc-infra`; в прототипе допустимо `ktc-app`. Брокер — это **не данные**, поэтому он не в слое данных.

## 7. Как сервисы общаются между собой

**Общая схема «gRPC внутри + WS/REST наружу» (ARCH-04):**

| Направление | Протокол | Обоснование |
|---|---|---|
| Браузер ↔ Gateway | REST (HTTPS) + WS | Стандартный веб-стек, OpenAPI |
| Gateway ↔ Сервисы | gRPC (mTLS) | Типизированные контракты (protobuf), низкая латентность |
| Сервис ↔ Сервис | gRPC (mTLS) | Строгие контракты, эффективная сериализация |
| Orchestrator → Frontend | WebSocket | Push-телеметрия 1 Гц |

*(Примечание: сервисные доки частично описывают REST между сервисами, SRD §7 — gRPC. Фактически: hot-path `sim`/`ai` — gRPC, остальное — REST с mTLS. Стоит унифицировать в документации.)*

**Ключевые внутренние контракты:**

| Контракт | Протокол | Методы |
|---|---|---|
| **Model API** (к sim) | gRPC | `step`, `get_state`, `set_state`, `inject_fault`, `set_speed` |
| **AI API** | gRPC + mTLS | `explain`, `predict_physics`, `predict_behaviour`, `generate_scenario`, `analyze` |
| **Template API** | gRPC | CRUD шаблонов, компонентов, версий |
| **HMAC Seal API** | gRPC | Подпись/проверка протокола экзамена |
| **Events (async)** | NATS | Отчёты, ИИ-задачи, уведомления, аудит |

## 8. Модель безопасности (доверительные границы)

Это самая важная часть для понимания того, как устроен доступ.

```
Браузер ──► Istio Ingress Gateway ──► gw (ЕДИНСТВЕННАЯ точка проверки JWT)
                                        │
                                        ▼ authenticated context
                        → auth (introspect: проверка токена + роли)
            заголовки X-User-ID, X-Roles  (JWT дальше НЕ идёт)
                                        ▼
                    ┌───────────────────────────┐
                    │  Внутренние сервисы        │
                    │  НЕ проверяют токен сами,  │
                    │  ключ подписи НЕ знают     │
                    └───────────────────────────┘
```

**Правила:**
1. **Единственная точка проверки JWT/RBAC — `gw`** (внешний вход один — через Istio Ingress).
2. `gw` зовёт `auth` через `POST /introspect` для проверки валидности токена и получения ролей.
3. Проверенный контекст `gw` передаёт внутренним сервисам в заголовках (`X-User-ID`, `X-Roles`), а **сам JWT не рассылается**.
4. Внутренние сервисы токен **не проверяют и ключ подписи не знают**. Доверие = прикладная проверка на `gw` + **mTLS** + **NetworkPolicy «accept only from gw»**.
5. **Защита от подделки**: сервисы обязаны **стирать** входящие `X-User-ID`/`X-Roles` и принимать только от `gw`. Иначе клиент подсунул бы свои роли.
6. **Аудит** — интенсивно в `gw`/`auth` (единственная точка) → KUMA.

**Прочие меры:** HTTPS TLS 1.2+, append-only аудит + HMAC-подпись протокола, server-authoritative state, rate-limiting, mTLS между сервисами, секреты в K8s Secrets + Vault, JSON Schema-валидация, SHA-256 целостности шаблонов/моделей.

**Две границы firewall (сетевой уровень ≠ прикладной уровень):**

| Граница | Чем обеспечивается | Что закрывает |
|---|---|---|
| **Периметр кластера** (внешний сетевой контур) | **Firewall VKCloud** — сегментация VPC/подсетей, доступ к Ingress/Egress, к узлам K8s и API-серверу | Входящий трафик на Ingress Gateway, исходящий (egress) к внешним системам (LDAP/AD, PAM), защита control-plane |
| **Внутри кластера** (между слоями/подми) | **Istio** (istio-proxy sidecar во всех сервисных namespace `ktc-app`/`ktc-sim`/`ktc-ai`; mTLS) + Kubernetes **NetworkPolicy** («accept only from gw») | Трафик между `ktc-app` и `ktc-sim`/`ktc-ai`/`ktc-data`, между сервисами, шифрование mTLS. Egress Gateway присутствует в каждом сервисном namespace (`app`/`sim`/`ai`) для контролируемого исходящего трафика |

Важно: между прикладным слоем и вычислительным/данными отдельный сетевой firewall **не требуется** — эту изоляцию обеспечивает именно Istio + NetworkPolicy. Firewall VKCloud на схеме показывает сетевой периметр кластера (перед Ingress Gateway и на Egress Gateway к внешним системам).

**Изоляция OT (FR-ISO-01/02/03):** запрещены интеграции с реальными АСУ ТП/SCADA/ОПС/Модбас; все теги рождает только Simulation Engine; egress в OT-сеть запрещён.

## 9. Сквозной сценарий: от сборки установки до экзамена

### Этап 1. Сборка установки (инструктор)
1. Инструктор входит через `gw` → `auth` (LDAP + JWT + RBAC).
2. В **конструкторе (FE)** перетаскивает компоненты из библиотеки, соединяет порты.
3. FE шлёт граф в `constructor` (CRUD шаблона). Валидатор проверяет топологию.
4. Шаблон сохраняется (граф + layout + параметры). При необходимости — копируется (fork).

### Этап 2. Создание сценария (инструктор)
1. В **редакторе сценариев** инструктор выбирает шаблон (`scenario` связывает сценарий с шаблоном через `constructor`).
2. Выбирает неисправности из каталога, задаёт триггеры (время/условие), эталонные действия, критерии оценки.
3. Можно сгенерировать сценарий через **AI** (`generate_scenario` на основе графа и профиля ошибок).

### Этап 3. Запуск сессии (инструктор команды, оператор работает)
1. Инструктор создаёт сессию: шаблон + сценарий + оператор(ы) → `orchestrator`.
2. `orchestrator` получает init state из `constructor` (экспорт шаблона) и сценарий из `scenario`.
3. `orchestrator` просит `sim-manager` поднять `sim-worker` для этой сессии; модель инициализируется через `set_state`.
4. Цикл работы (1 Гц):
   - `sim` делает `step()` → новое состояние.
   - `orchestrator` кэширует горячее состояние в Radix и пушит телеметрию клиентам по WS (оператору + инструктору read-only).
   - Команды оператора (клапаны, регуляторы) → `orchestrator` → `sim`.
5. **Неисправности**:
   - *Автоматически*: планировщик событий в `orchestrator` проверяет триггеры сценария → `sim.inject_fault`.
   - *Live*: инструктор в реальном времени инжектит неисправность в компонент → `sim.inject_fault`.
6. **Оценка**: действия/алармы → `assessment` (штрафы, критические ошибки).
7. **Инъекции ИИ** (не в экзамене): `ai` даёт Explain/Predict подсказки.
8. **Периодические чекпоинты**: `snapshot` сохраняет состояние (S3 + Picodata) — защита от обрыва ≤3 мин.

### Этап 4. Завершение и отчёт
1. Сессия останавливается, `assessment` даёт итоговую оценку (может переопределить инструктор с комментарием в аудит).
2. `report` (через очередь NATS) формирует **PDF-отчёт** и **подписанный HMAC протокол экзамена** (canonical JSON + PDF).
3. Доступен **разбор** (Replay + ИИ-объяснения).

## 10. Данные системы

**Три хранилища и их роли:**

| Хранилище | Технология | Что хранит |
|---|---|---|
| **СУБД** | **Picodata** (PG-совместимый wire, Raft-кластер) | Сессии, оценки, журналы (append-only), пользователи, шаблоны/графы (JSONB), сценарии, метаданные снапшотов, протоколы |
| **Кэш** | **Radix** (Redis-совместимый плагин Picodata) | Горячее состояние сессий (мгновенный доступ), JWT-кэш |
| **Объектное хранилище** | **S3 / MinIO** | Снапшоты (payload), PDF-отчёты, иконки/SVG компонентов |

**Основные сущности:** User, Role, ComponentType, InstallationTemplate, TemplateVersion, Scenario, Session, Snapshot, AlarmEvent, OperatorAction, FaultInjection, Assessment, ExamProtocol, AIInsight.

**Граф установки** хранится как JSON (nodes/edges/layout) в JSONB-поле Picodata — пример в SRD §6.2.

**Почему Picodata/Radix:** отечественность (ФСТЭК УД4, РРПО), PG-совместимость (стандартные драйверы), Raft-репликация из коробки (failover <30 с без внешнего Patroni). *Ограничение:* pg_catalog реализован частично — нельзя ORM-reflection (SQLAlchemy), нужен raw SQL / query builder.

## 13. Отказоустойчивость и масштабирование

**Ключевые сценарии отказоустойчивости:**

| Инцидент | Поведение системы |
|---|---|
| Падение `sim` (сессии) | Автоматический перезапуск + restore из чекпоинта ≤15 с; обрыв ≤3 мин прогресс не теряется; другие сессии не страдают (per-session под) |
| Падение AI-хоста | **Деградация**: тренировка и rule-based оценка продолжаются (fallback) |
| Kill Picodata primary | Raft failover <30 с |
| Падение клиента (браузера) | Сессия на сервере продолжается (сервер = источник истины) |
| Обрыв связи ≤3 мин | Прогресс сохраняется (серверный чекпоинт), клиент переподключается |

**Масштабирование:**
- Stateless-сервисы (`gw`, `auth`, `constructor`, `scenario`, `orchestrator`, `assessment`, `report`, `snapshot`) — **HPA** (N≥2).
- Simulation Engine — масштабируется **по числу сессий** (1 сессия = 1 под, до 50).
- AI — GPU-пул.
- Node Pools: `app` (general), `sim` (CPU-intensive, guaranteed QoS для 1 Гц), `ai` (GPU, taint), `db` (SSD, anti-affinity).

**Производительность (главные метрики):** UI-отклик ≤500 мс, телеметрия ≥1 Гц, до 50 одновременных сессий, загрузка шаблона/снапшота ≤15 с, PDF ≤20 с (асинхронно), конструктор ≤200 мс для графа до 200 узлов.

## Известные расхождения в документации

Эти моменты стоит унифицировать:
1. **Namespace**: SRD использует `ktk-*`, сервисные доки — `ktc-*`.
2. **`constructor`**: есть в service-доке `constructor.md` и в SRD, но **отсутствует** как отдельный под в `claude_strelki.drawio` (в диаграмме он «спрятан» в `scenario`).
3. **Межсервисный протокол**: SRD §7 говорит gRPC между всеми сервисами; сервисные доки описывают REST/mTLS (gRPC только для sim/ai).
4. **Брокер**: на диаграмме `RabbitMQ/Kafka/NATS`, зафиксировано — **NATS JetStream**.
5. **Путь телеметрии sim→клиент**: на диаграмме стрелка идёт через broker, по сервисным докам — через `orchestrator` (WS).
