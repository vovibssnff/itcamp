# Компонент: NATS JetStream — брокер сообщений

> Слой: Инфраструктурный (шина/очередь) — `ktc-obs` / `ktc-infra` | Это: асинхронная шина и очередь задач | Протокол: NATS

## 1. Назначение

**NATS — «почтовая служба» системы.** Обеспечивает **асинхронную** связь между
сервисами и очередь задач с гарантированной доставкой. Развязывает real-time контур
(сессии) от тяжёлой неблокирующей обработки (PDF-отчёты, ИИ-расчёты, события сессий):
тяжёлая работа выполняется асинхронно и **не тормозит** тик-цикл сессии.

## 2. Почему именно NATS JetStream (обоснование выбора)

| Требование | Как закрывает NATS |
|---|---|
| **Низкий latency** | pub/sub < 1 мс — подходит для событий сессий |
| **Лёгкий/встраиваемый** | малый расход ресурсов, простой деплой в K8s |
| **Гарантированная доставка** | JetStream — persistent-очереди с retry |
| **Персистентность очередей** | файловое хранилище JetStream |
| **K8s-native** | нативная поддержка, лёгкие кластеры (Raft) |

## 3. Использование в коде

Реализация — `services/go/orchestrator/internal/events/nats.go` (клиент
`github.com/nats-io/nats.go`), используется в `orchestrator` и `report`.

**Топики (субъекты):**

| Топик | Продюсер → Потребитель | Назначение |
|---|---|---|
| `session.events.<session_id>` | `orchestrator` → assessment/инструктор/аудит | события сессии (start/pause/stop, авария, операторское действие) |
| `report.tasks` | `orchestrator`/gw → `report` | тяжёлая генерация PDF (асинхронно) |
| `ai.tasks` | `orchestrator` → `ai` | задачи ИИ (инференс) |

**Ключевое:** события и задачи уходят в NATS **асинхронно** — `orchestrator` не ждёт
результата и не блокирует отправку телеметрии по WS (1 Гц). Это защищает real-time
контур (тик-цикл, PERF-02) от задержек из-за PDF/ИИ.

## 4. Размещение (почему НЕ в слое данных)

- Брокер — **не данные**. Слой `ktc-data` (Picodata/Radix/S3) — персистентность;
  NATS — асинхронный транспорт/очередь (природа другая).
- Брокер «в середине» потоков прикладных сервисов, а не «на конце» (как БД).
- Латентность: производители/потребители рядом — отдельный изолированный сегмент
  добавляет latency без пользы.

**Вывод (Target):** размещать в **отдельном инфра-сегменте `ktc-infra`/`ktc-obs`**;
в прототипе допустимо `ktc-app`.

| Вариант | Где | Оценка |
|---|---|---|
| `ktc-infra` (Target) | отдельный инфра-сегмент | **рекомендуется** |
| `ktc-app` (прототип) | вместе с прикладными | приемлемо на MVP |
| `ktc-data` | к Picodata/Radix/MinIO | смешение «шины» и «хранилища» |

## 5. Объекты Kubernetes

| Объект | Описание |
|---|---|
| StatefulSet `nats` | кластер NATS (N≥3 для отказоустойчивости) |
| Service `broker`/`nats` | ClusterIP |
| PersistentVolume(s) | JetStream file store |
| Secret | nkey/token |
| Pod + sidecar `istio-proxy` | mTLS |

## 6. Метрики (в Пульт + Графиня)

- Длина стримов, rate сообщений, задержка доставки.
- Время обработки задач report/ai.
- Отказы/ретраи, потери сообщений.

## 7. Отказоустойчивость / масштабирование

- Кластер NATS (N≥3): Raft-репликация JetStream, отказ ноды не теряет данные.
- Приоритизация задач, retry упавших.
- Масштабирование потребителей (report/ai) по длине очереди.

## 8. Открытые вопросы

1. JetStream retention policy (limits vs interest vs work queue) для каждого стрима.
2. Поток событий для аудита в KUMA — через broker или напрямую из сервисов.
3. Унификация namespace (`ktk-*` vs `ktc-*`).
