# Компонент: Радикс (Radix) — кэш платформы

> Слой: Данных — `ktc-data` | Это: Redis-совместимый кэш (плагин Picodata) | Доступ: `radix:7379`

## 1. Назначение

**Radix — «быстрая память» платформы.** Хранит актуальное («горячее») состояние сессий
учебного тренажёра, которое меняется каждую секунду и должно быть доступно мгновенно,
не нагружая СУБД. В отличие от Picodata (источник правды для истории), Radix отдаёт
состояние «здесь и сейчас».

## 2. Зачем вообще кэш (обоснование места в архитектуре)

В real-time контуре тренажёра есть три класса данных с разными требованиями:

| Класс данных | Пример | Частота изменения | Требование | Где живёт |
|---|---|---|---|---|
| История / источник правды | сессии, оценки, действия оператора, аварии | редко, но важно | надёжно, навсегда | **Picodata** |
| Горячее состояние | телеметрия (1 Гц), статус сессии | каждая секунда | мгновенный доступ | **Radix** |
| Крупные объекты | снапшоты, PDF, иконки | редко | большой объём | **MinIO/S3** |

Секундную телеметрию писать в СУБД нельзя: это создало бы огромную нагрузку записи
ради данных, которые никому не нужны в истории. Нужен **быстрый кэш in-memory** —
это роль Radix.

## 3. Почему Radix, а не «просто Redis»

| Критерий | «Просто Redis» (свой под) | **Radix (Picodata)** |
|---|---|---|
| Персистентность | только память, настраивать самому | данные в хранилище Picodata, переживают рестарт |
| Администрирование | вы сами (кластер, бэкапы, апгрейды) | **managed-сервис платформы** |
| Отечественность | импортный | **РРПО, ФСТЭК** (решение для контура КИИ) |
| Единый вендор с СУБД | — | один вендор с Picodata → проще поддержка |
| Совместимость | Redis | **Redis-совместимый протокол** — работает со стандартными клиентами (`go-redis`) |

Ключевое: **Radix — это персистентное общее хранилище данных Picodata**, а не
эфемерный in-memory кэш живущего процесса. Поэтому он переживает рестарты сервисов
и доступен из любого экземпляра — это усиливает наш сценарий «догоняющего снимка»
при переподключении клиента.

## 4. Размещение (почему выделенный инстанс)

- Radix — **управляемый сервис данных Picodata**, а не локальный под приложения.
  Вопрос «в namespace приложения или нет» снимается: это общий ресурс платформы.
- В слое данных `ktc-data` Radix **изолирован от Picodata** (отдельная сеть,
  отдельный volume `radix-data` в `compose/data/compose.yaml`, порт `7379`):
  СУБД — источник правды, Radix — горячее состояние. Изоляция защищает БД от
  секундной нагрузки и даёт быстрый слой чтения.
- При горизонтальном масштабировании orchestrator (N≥2) у каждого экземпляра — своя
  память. Локальный `map` не подходит (данные не видны другим экземплярам и теряются
  при рестарте). Общий Radix решает обе проблемы.

> **Оговорка про латентность.** Выделенный инстанс в другом контуре добавляет сетевую
> задержку по сравнению с локальным подом. Для объёмов (запись раз в секунду на сессию)
> это приемлемый управляемый компромисс.

## 5. Использование в коде

Реализация — `services/go/orchestrator/internal/cache/redis.go`, интерфейс —
`internal/service/session_service.go` (`StateStore`). Использует `github.com/redis/go-redis/v9`.

### 5.1. Сценарий A — телеметрия (ключи `telemetry:<session_id>`)

1. В цикле `SessionRunner.tick` (раз в секунду) у `sim` запрашивается состояние и
   собирается `Telemetry` (время модели, датчики, регуляторы, аварии).
2. Снимок пишется в Radix: `SaveTelemetry` → ключ `telemetry:<id>` с **TTL 10 сек**.
3. Тот же снимок рассылается клиентам по WebSocket.
4. При **подключении клиента** по WS ему сразу отдаётся последний снимок из Radix
   (`LatestTelemetry`) — экран «оживает» мгновенно, не дожидаясь следующего тика
   (`handlers.go::handleWS`).
5. При **остановке сессии** ключ удаляется (`DeleteTelemetry`) — Radix не копит мусор.

### 5.2. Сценарий B — кеш метаданных сессии (ключи `session:<session_id>`)

`GetByID` — самый «горячий» read-запрос (GET, start, pause, stop, speed, actuator,
ack, restore). Реализован **read-through кеш**:

- `getSession`: сначала ищет в Radix (`GetSessionState`); при промахе читает из
  Picodata и пишет в Radix (`SaveSessionState`).
- **Инвалидация на записи** — на всех операциях, меняющих таблицу `sessions`
  (Create, SetStarted, UpdateStatus, UpdateSpeed), ключ сбрасывается
  (`invalidateSession`). Это гарантирует актуальность статуса.

### 5.3. Что НЕ кешируем

- `List` (список сессий) — редкий, зависит от `status`+`operator_id`+сортировки,
  операторная фильтрация уже в памяти. Инвалидация дороже пользы.
- Все INSERT/UPDATE (`RecordAction`, `RecordAlarm`, …) — записи не кешируют, они
  сами инвалидируют кеш.

## 6. Зависимости и протоколы

| Взаимодействует с | Тип | Протокол |
|---|---|---|
| Session Orchestrator (`orchestrator`) | микросервис | Redis (`go-redis`, RESP) |
| Picodata (СУБД) | один вендор | общий data-plane `ktc-data` |
| Пульт (коллектор) | observability | метрики Radix |

## 7. Данные

- Только **горячее состояние**: телеметрия (TTL 10 сек) + кеш метаданных сессий.
- **Не** является источником правды истории; вся история — в Picodata.

## 8. Объекты Kubernetes

| Объект | Описание |
|---|---|
| StatefulSet `radix` | инстанс Radix (data-plane) |
| Service `radix` | ClusterIP (`radix:7379`) |
| PersistentVolume `radix-data` | персистентность данных |
| Secret | пароль подключения |

## 9. Метрики (в Пульт + Графиня)

- Key count / hit-miss ratio (`telemetry:*`, `session:*`).
- Размер данных, TTL-протухшие ключи.
- Задержка чтения/записи, число операций в сек.
- Отказы подключений.

## 10. Отказоустойчивость / масштабирование

- Персистентность встроенного хранилища Picodata — переживает рестарт сервиса.
- Единый инстанс в data-plane доступен всем экземплярам orchestrator (N≥2).
- Потеря Radix не фатальна: телеметрия восстановится из `sim` на следующем тике,
  метаданные — из Picodata (read-through при промахе). Radix — не критичная точка
  отказа при правильной конфигурации капсулы.
