# Сервис: Auth / Session Service — `auth`

> Слой: Прикладной | Namespace: `ktc-app` | Под: `auth`
> Смежно: `Реестр_сервисов...`, `Сценарии_экзамен...`, `Архитектура_КТК_K8s.drawio`

## 1. Назначение

**Идентификация и управление доступом**, ведение пользовательских сессий. Интеграция с корпоративным каталогом **LDAP/AD** и ИБ-инструментами (2FA, PAM). Чувствителен к правам — выносится в изолированный сегмент, масштабируется отдельно.

## 2. Основные функции

- Проверка учётных данных в **LDAP/AD** (все роли: Оператор/Инструктор/Админ).
- Выдача и проверка **JWT** (короткий TTL).
- **RBAC** (роли и права).
- **2FA (TOTP)** для инструктора/администратора; привилегированный доступ через отечественный **PAM**.
- Ведение сессий, логаут, аудит входов (→ KUMA).

## 3. Технологии

Python/FastAPI или Go. JWT-библиотека, ldap3/GO-LDAP.

## 4. Внутренняя структура

- Проверка пароля/учётки против LDAP.
- Эмиссия/валидация JWT-токенов (подпись ключом, известным `gw`).
- Хранение профилей/ролей (метаданные в Picodata).
- Модуль аудита, публикация событий (Fluent Bit → KUMA).

## 5. API / контракты

| Направление | Протокол | Методы |
|---|---|---|
| от `gw` | HTTPS/REST | `POST /login`, `POST /logout`, `POST /mfa/verify`, `GET /me`, `POST /refresh` |
| от `gw` | HTTPS/REST | `POST /introspect` (проверка JWT для других сервисов) |

## 6. Модель валидации / доверительная граница (trust boundary)

**Принцип: токен проверяет только `gw`, внутренние сервисы его сами не верифицируют.**

- Внешний вход один — **Istio Ingress Gateway** → **`gw`**. Единственная точка проверки JWT/RBAC — `gw`.
- `gw` при запросе вызывает `auth` через `POST /introspect`, чтобы проверить валидность токена (подпись, срок, активность/отзыв сессии) и получить роли/права.
- **Проверенный контекст** `gw` передаёт внутренним сервисам в виде заголовков (`X-User-ID`, `X-Roles` и др.), а **сам JWT дальше не рассылается**.
- **Внутренние сервисы токен не проверяют и ключ подписи JWT не знают.** Запрос, пришедший от `gw`, считается авторизованным — доверие обеспечивается:
  - подписью/проверкой на `gw` через `auth` (прикладной уровень);
  - **mTLS** и **NetworkPolicy «accept only from gw»** (сетевой уровень).
- **Защита от подделки контекста:** сервисы обязаны **стирать** входящие заголовки `X-User-ID`/`X-Roles` от клиента и принимать их только от `gw`. Иначе клиент мог бы подставить собственные роли. На `gw` эти заголовки от клиента игнорируются/перезаписываются после проверки.
- **Аудит:** поскольку это единственная точка проверки, именно `gw`/`auth` выполняют интенсивный аудит входа, отказа и ошибок 2FA (→ KUMA).

Соотношение с `gw`: прикладная проверка (introspect → valid + роли) лежит на `gw`; хранение ключа подписи и статуса сессий — на `auth`.

## 7. Зависимости и протоколы

| Взаимодействует с | Тип | Протокол |
|---|---|---|
| API Gateway (`gw`) | микросервис | HTTPS/REST, mTLS |
| LDAP/AD (каталог) | внешняя система | LDAP/LDAPS (через Egress Gateway) |
| PAM (отечественный) | внешний ИБ-компонент | HTTPS/REST / локальный протокол 2FA |
| Picodata (`db`) | СУБД | SQL (PostgreSQL-wire), TCP/mTLS |
| istiod / mesh | инфраструктура | mTLS |
| Fluent Bit / KUMA | observability/ИБ | логи, события аудита (входы, ошибки авторизации) |

## 8. Данные

- Пикодата: пользователи, роли, профили, связь ролей с LDAP.
- Не хранит пароли открыто (LDAP хранит сам).

## 9. Объекты Kubernetes (namespace `ktc-app`)

| Объект | Описание |
|---|---|
| Deployment `auth` | N≥2 реплики, HPA |
| Service `auth` | ClusterIP |
| NetworkPolicy | accept только от `gw`; egress к LDAP (через Egress), Picodata, PAM |
| Secret | ключ подписи JWT (из Vault/env secrets) |
| Pod + sidecar `istio-proxy` | mTLS |

## 10. Метрики (в Astra Monitoring)

- Число успешных/неудачных входов.
- Задержки LDAP-запросов, отказов 2FA.
- Число активных сессий/токенов.

## 11. Отказоустойчивость / масштабирование

- Stateless, HPA.
- Память: JWT-валидация кэшируется; сбои LDAP → грациозный фолбэк (сообщение об ошибке).
- Аудит обязателен (без него невозможен аудит ИБ).
