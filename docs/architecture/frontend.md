# Сервис: Frontend / Web-HMI (SPA) — `fe`

> Слой: Прикладной | Namespace: `ktc-app` | Под: `fe`
> Смежно: `Реестр_сервисов...`, `Сценарии_экзамен...`, `Архитектура_КТК_K8s.drawio`

## 1. Назначение

Браузерный интерфейс тренажёра — то, что видит и чем управляет пользователь. Отображает мнемосхему установки ЭЛОУ-АВТ, тренды, алармы, faceplate-узлы и экраны всех ролей (Ученик/Инструктор/Админ/Наблюдатель). Это **тонкий клиент**: никакой «истины» не считает, только отображает серверное состояние и отправляет команды (server-authoritative).

## 2. Основные функции

- Рендер **мнемосхемы** установки (блоки ЭЛОУ, атмосфера, вакуум, печи, насосы).
- Обновление мнемосхемы по **телеметрии 1 Гц** (события по WebSocket).
- Панели **трендов** (до 8 серий), **алармов** (HH/H/L/LL) и **faceplate**-узлов.
- Экраны ролей: управление сессией, конструктор сценариев (инструктор), отчёты, администрирование.
- Управляющие команды оператора (задвижки, клапаны, регуляторы) → сервер.
- Экран экзамена: таймер, режим «экзамен», запрет подсказок (отображается UI-40).

## 3. Технологии

React + TypeScript, Vite, WebSocket-клиент, uPlot/Konva (графика/тренды), Ant Design (UI).

## 4. Внутренняя структура

- Статический SPA (собранные JS/CSS), раздаётся как статика через Gateway/nginx.
- Модули: мнемосхема, тренды, алармы, faceplates, экраны ролей, WebSocket-подсистема.
- Хранение состояния клиента — Redux/Zustand (только кэш отображения, не источник истины).

## 5. API / контракты (клиент → сервер)

| Направление | Протокол | Методы/события |
|---|---|---|
| Получение статики / REST | HTTPS | GET /api/... (сценарии, сессии, отчёты, оценки) |
| Пишующие команды | HTTPS/REST (JSON) | POST /api/session/start|stop|pause, set_actuator... |
| Телеметрия (push) | WebSocket (WSS) | получение тегов/алармов 1 Гц, статусы сессии |

## 6. Зависимости и протоколы

| Взаимодействует с | Тип | Протокол |
|---|---|---|
| Пользователь (браузер АРМ) | клиент | HTTPS (TLS 1.2+), WSS |
| API Gateway / BFF (`gw`) | микросервис | HTTPS/REST (JSON), WSS (через Ingress + mesh) |
| Istio Ingress Gateway | инфраструктура mesh | HTTP, mTLS (внутри сетки) |
| Astra Monitoring / Fluent Bit | observability | `/metrics` (PromQL), логи stdout |

**Никогда** не общается напрямую с `sim`, `db`, `auth`, `assessment` — только через `gw`.

## 7. Данные (что хранит/видит)

- Не хранит бизнес-данные. Хранит только локальное состояние отображения (кэш).
- Персональные данные (ФИО/логин) — только отображение; источник — `auth`/LDAP.

## 8. Объекты Kubernetes (namespace `ktc-app`)

| Объект | Описание |
|---|---|
| Deployment `fe` | N≥2 реплики (статический SPA), RollingUpdate |
| Service `fe` | ClusterIP, доступ из ingress/gateway |
| HorizontalPodAutoscaler | по CPU/памяти/нагрузке WS |
| PodDisruptionBudget | minAvailable для стабильности |
| serviceAccount + NetworkPolicy | только egress к `gw` (внутри mesh) |
| Pod + sidecar `istio-proxy` | mTLS |

## 9. Метрики (в Astra Monitoring)

- Время отклика UI (PERF-01 ≤ 500 мс).
- Число активных WebSocket-соединений.
- Ошибки рендера, latency, число активных сессий на клиенте.

## 10. Отказоустойчивость / масштабирование

- Несколько реплик (stateless), HPA.
- При падении одного клиента сессия на сервере продолжается (сервер = источник истины).
- Обрыв ≤3 мин — прогресс сохраняется (серверный чекпоинт), клиент переподключается.

## 11. Открытые вопросы

1. Точная библиотека графики: uPlot (лёгкая) vs Konva (полноценный canvas) для мнемосхемы.
2. Кэширование статики и CDN/SRI — нужно ли SRI-подписи статики (см. NFR-SEC).
3. Уровень автономии при «офлайн» (чёрный экран переподключения).
