# Сервис: Simulation Engine — `sim`

> Слой: Вычислительный | Namespace: `ktc-sim` (Node Pool `sim`) | Под: `sim-worker-*` (per session) + `sim-manager`
> Подробнее про математику и k8s: `Simulation_Engine_модель_namespace_k8s.md`
> Смежно: `Реестр_сервисов...`, `Сценарии_экзамен...`, `Архитектура_КТК_K8s.drawio`

## 1. Назначение

**Цифровой двойник техпроцесса ЭЛОУ-АВТ** — единственный источник истины о технологическом состоянии (FR-ISO-03). Самый ресурсоёмкий и детерминированный сервис.

## 2. Основные функции

- Расчёт динамики установки (ЭЛОУ, колонны К-1/К-2, вакуум, печи, насосы) по тику **≥1 Гц** модельного времени.
- **Model API**: `step`, `get_state`, `set_state`, `inject_fault`, `set_speed`.
- **Per-session экземпляры** — изоляция сбоев между сессиями.
- Порождение тегов/алармов (сигнализации, ПАЗ, ППК).
- Детерминированное исполнение (контроль ГПСЧ).

## 3. Технологии

Python + NumPy/SciPy (численное интегрирование ODE), собственная OTS-модель ЭЛОУ. Точка расширения L1→L3 (внешний solver, напр. DWSIM) через тот же Model API.

## 4. Внутренняя структура

- **sim-manager** (диспетчер): создаёт/удаляет рабочие поды под сессии.
- **sim-worker** (на сессию): процесс движка, решает шаг ОDE, ведёт теги/алармы, отдаёт `/metrics`.

## 5. API / контракты (Model API)

| Метод | Протокол | Назначение |
|---|---|---|
| `step()` | gRPC/REST | один шаг интегрирования → новое состояние |
| `get_state()` | gRPC/REST | полное состояние (телеметрия/снапшот) |
| `set_state(state)` | gRPC/REST | установить состояние (restore/старт) |
| `inject_fault(fault_id)` | gRPC/REST | внедрить аварию |
| `set_speed(0.1…10)` | gRPC/REST | коэффициент скорости модельного времени |

## 6. Зависимости и протоколы

| Взаимодействует с | Тип | Протокол |
|---|---|---|
| Session Orchestrator (`orchestrator`) | микросервис | Model API (gRPC/REST), mTLS |
| Snapshot Service (через orchestrator) | микросервис | Model API (get_state/set_state) |
| Пикодата (`db`) | СУБД | SQL (журнал аварий/действий) |
| Пульт / Fluent Bit | observability | `/metrics` (tick-lag), stdout |

**Не связан** с фронтом, ИИ, assessment, репортом напрямую (изоляция OT и сети).

## 7. Данные

- Пикодата: журнал аварий/действий (append-only).
- Локальная RAM: состояние модели текущего шага (детерминизм).
- Radix: не используется движком напрямую (состояние сессии кэширует оркестратор).

## 8. Объекты Kubernetes (namespace `ktc-sim`)

| Объект | Описание |
|---|---|
| Namespace `ktc-sim` | выделенный сегмент движков |
| Deployment `sim-manager` | диспетчер (1 реплика) |
| Pod `sim-worker-N` | персональный движок на сессию (до 50) |
| Service `sim` | точка доступа Model API |
| Node Pool `sim` | выделенные CPU-узлы, taint `sim=true` |
| ResourceQuota/LimitRange | жёсткие лимиты |
| NetworkPolicy | только от `orchestrator`/`snapshot` |
| PDB | защита диспетчера |

Подробный жизненный цикл пода, отказоустойчивость, гарантия 1 Гц — в `Simulation_Engine_модель_namespace_k8s.md`.

## 9. Метрики (в Пульт + Графиня)

- **tick-lag** (главная метрика real-time).
- Число активных сессий (под-движков).
- CPU/RAM Node Pool `sim`, время restore.

## 10. Отказоустойчивость / детерминизм

- Per-session под: падение не роняет другие сессии.
- Рестарт + restore из последнего чекпоинта/снапшота (≤15 с, обрыв ≤3 мин).
- Детерминированный численный метод + seed ГПСЧ (в снапшоте) → продолжение идентично.

## 11. Открытые вопросы

1. Реальный «под на сессию» при 50 сессиях vs потоки внутри одного пода (рекомендация: под на сессию в Target).
2. Отдельный `sim-manager` vs создание подов самим оркестратором.
3. CPU-бюджет для гарантии 1 Гц при 10× (внутренние подшаги).
4. Численный метод и размер шага — согласовать с технологом.
