## 1. Введение

### 1.1. Назначение документа

Настоящий SRD фиксирует функциональные и нефункциональные требования к разработке **Конструктора КТК** — платформы для визуального проектирования, сборки и эксплуатации компьютерных тренажёрных комплексов нефтеперерабатывающих установок.

В отличие от классического КТК (фиксированный тренажёр одной установки), Конструктор КТК — это **конфигурируемая платформа**, позволяющая:

- из библиотеки типовых компонентов (насосы, колонны, теплообменники, печи, ёмкости, регуляторы) визуально собрать тренажёр произвольной конфигурации;
- создать, сохранить, скопировать, модифицировать и удалить шаблон установки вместе со сценариями;
- генерировать тренировочные и экзаменационные сценарии для собранной установки;
- проводить сессии обучения с наблюдением инструктором (read-only) в реальном времени.

Базовая библиотека компонентов покрывает **всю схему КТС установки ЭЛОУ-АВТ**: блок ЭЛОУ (электродегидраторы, смесители, ёмкости), атмосферный блок (колонны К-1/К-2, печи, стриппинги), блок ГДМ (реактор К-12/4, колонны К-12/2, К-12/3) и общеустановочные системы (насосы, теплообменники, регуляторы, КИП). Демонстрационный стенд включает **часть** этой схемы (определяется при сборке шаблона); предустановленный демо-шаблон — фрагмент атмосферного блока.

### 1.2. Цели системы

1. Предоставить визуальный конструктор для сборки тренажёрных установок из типовых компонентов без программирования.
2. Обеспечить возможность создания тренировочных и экзаменационных сценариев для собранных установок.
3. Поддержать полный цикл управления шаблонами: создание, копирование, модификация, удаление.
4. Обеспечить инструктору наблюдение за сессиями операторов в реальном времени (read-only).
5. Реализовать масштабируемую микросервисную архитектуру на отечественном стеке (Deckhouse, Picodata, Istio, NATS).

### 1.3. Заинтересованные стороны


| Роль                         | Интерес                                                              |
| ---------------------------- | -------------------------------------------------------------------- |
| Заказчик (ПАО «Газпром нефть» / организаторы) | Работоспособный прототип + проектная документация |
| Инструктор                   | Проектирование установок и сценариев, наблюдение сессий, экзамен     |
| Оператор (обучаемый)         | Реалистичный HMI, обратная связь, тренировка                         |
| Администратор                | Управление тренажёрным комплексом: просмотр пользователей/ролей (учётки ведутся в LDAP/AD), политика оценки, контроль учебного контента и аудит (не инфраструктура) |
| Команда разработки           | Чёткие Must/Should, ограничение scope                                |


### 1.4. Область применения и границы

**Входит:**
- Визуальный конструктор установок (drag-and-drop компонентов, произвольные связи)
- **Полная библиотека компонентов всей схемы КТС ЭЛОУ-АВТ** (ЭЛОУ, Атмосфера, ГДМ, общеустановочные)
- Управление шаблонами установок (CRUD, копирование)
- Создание и управление сценариями (каталог неисправностей + ручное создание + ИИ)
- Тренировочные сессии с HMI оператора
- Наблюдение за сессиями инструктором (read-only); неисправности — только из сценария (автоматически)
- Экзаменационный режим с защищённым протоколом
- Модуль ИИ: Explain / Predict / Adaptive
- Микросервисная архитектура на Deckhouse
- Демонстрационный шаблон — фрагмент ЭЛОУ-АВТ (конкретный объём фиксируется при подготовке демо)

**Не входит (Won't / Could):**
- Полевой оператор, VR/3D
- Online-интеграция с реальной АСУ ТП / SCADA / OPC / Modbus
- LDAP/AD (только JWT)
- Компоненты установок, не входящих в ЭЛОУ-АВТ (в библиотеку могут быть добавлены позже)

### 1.5. Ключевое отличие от классического КТК

| Аспект | Классический КТК (v1 SRD) | Конструктор КТК (данный документ) |
|--------|---------------------------|-----------------------------------|
| Установка | Фиксированная (ЭЛОУ) | Собирается из компонентов |
| Сценарии | Фиксированная библиотека | Генерируемые + шаблоны + ИИ |
| Расширяемость | Требует доработки кода | Новые компоненты добавляются в библиотеку |
| Шаблоны | Нет | Полный CRUD + копирование |
| Топология | Зашита в коде | Определяется пользователем визуально |

## 2. Обзор системы

### 2.1. Концепция «Конструктор КТК»

Конструктор КТК — это **платформа**, а не конечный тренажёр. Платформа предоставляет:

1. **Библиотеку компонентов** — типизированные элементы технологического оборудования с параметризуемыми моделями поведения (насос, ректификационная колонна, теплообменник, печь, ёмкость, клапан/задвижка, ПИД-регулятор, смеситель, КИП-датчик).

2. **Визуальный редактор** — canvas, на котором компоненты соединяются потоковыми связями (труба/поток: жидкость, газ, пар, электрический сигнал, управляющий сигнал). Результат — граф технологической схемы.

3. **Шаблоны установок** — сохранённые конфигурации (граф + параметры + сценарии), которые можно копировать, дорабатывать, удалять, публиковать для использования инструкторами.

4. **Генератор сценариев** — на основе топологии собранной установки и библиотеки типовых неисправностей создаются тренировочные сценарии и экзамены.

5. **Runtime-среда** — серверный Simulation Engine, который по графу установки динамически строит вычислительную модель и выполняет тик-цикл.

### 2.2. Архитектурный принцип: граф как единица конфигурации

Собранная установка хранится как **направленный граф** (DAG с обратными связями для рециклов):
- **Узлы** — экземпляры компонентов из библиотеки с заданными параметрами.
- **Рёбра** — потоковые связи между портами компонентов (вход/выход материального/энергетического/сигнального потока).

Граф является входом для:
- Simulation Engine (строит систему уравнений по связям);
- Рендерера мнемосхемы (автоматическая генерация или ручная раскладка);
- Генератора сценариев (анализ уязвимых точек графа);
- Валидатора (проверка корректности связей, отсутствия «висящих» портов).

### 2.3. Библиотека: полное покрытие схемы КТС

Библиотека компонентов содержит типы для **всех** основных блоков установки ЭЛОУ-АВТ по схеме КТС (`01_Схема КТС.pdf`):

**Блок ЭЛОУ (§3.2–3.3 регламента):**
- Насосы Н-1/1А/1Б/1В (сырьевые), Н-82/82А (промывная вода), Н-100к (деэмульгатор), Н-20/20А/20Б (откачка Е-15)
- Теплообменники Т-1…Т-11 (подогрев 3 потока сырья)
- Смесители А-19/1,3,5 (1 ступень), А-20/2,4,6 (2 ступень)
- Электродегидраторы Э-1, Э-3, Э-5 (1 ступень с ИПМ) и Э-2, Э-4, Э-6 (2 ступень с трансформатором)
- Ёмкости Е-15 (обессоленная нефть), Е-16 (солёная вода / улов)
- Регуляторы FRC-404/405/406, LRCA-639…645, PRC-313

**Атмосферный блок (§3.4–3.5 регламента):**
- Колонна К-1 (отбензинивающая): 26+ тарелок, P верха 1–4,5 кгс/см², T верха ≤150°C, T низа ≤280°C
- Печи П-1, П-2, П-3: нагрев до ≤365°C, многопоточные
- Колонна К-2 (основная ректификационная): фракционирование (бензин, керосин, дизель, мазут)
- Стриппинги К-3/1, К-3/2, К-3/3: отпарка боковых погонов
- Ёмкость Е-1 (рефлюксная), газосепаратор К-7, колонна стабилизации К-4
- Насосы Н-2/2А/2Б, Н-3/3А, Н-6/6А
- Теплообменники Т-17…Т-27, АВЗ-3, Х-1/3..5
- Регуляторы FRC-458/459/460, TRC-2/3/4/9/11/18/21, PRC-221, LRCA-602/603

**Блок ГДМ (§3.6 регламента):**
- Реактор К-12/4 (каталитическая демеркаптанизация, многозонная термопара, ВСГ)
- Стриппинг К-12/2 (альтернативный режим), отпарная колонна К-12/3
- Пароперегреватель (секция П-2), каплеотбойник, линия сброса на факел
- Регуляторы давления/уровня/расхода блока ГДМ

**Общеустановочные системы:**
- Предохранительные клапаны (ППК), запорная арматура, КИП всех типов
- Резервуарный парк (Р-10…Р-15) — как граничные условия

### 2.4. Демонстрационный стенд

Демонстрационный шаблон включает **часть** полной схемы ЭЛОУ-АВТ. Конкретный объём фиксируется при подготовке демо; ориентировочно — фрагмент атмосферного блока (К-1, одна печь, насосная группа, основные регуляторы), достаточный для демонстрации всех возможностей конструктора: сборка, сценарии, инъекции, экзамен.

### 2.5. Режимы использования


| Режим                        | Описание                                                      | Приоритет |
| ---------------------------- | ------------------------------------------------------------- | --------- |
| Проектирование установки     | Инструктор собирает установку в конструкторе                   | Must      |
| Тренировка с инструктором    | Инструктор запускает сценарий, наблюдает за оператором (read-only) | Must   |
| Самостоятельная тренировка   | Без инструктора, повтор пройденных сценариев                  | Should    |
| Квалификационный экзамен     | Без подсказок ИИ, лимит времени, защищённый протокол          | Must      |
| Демонстрация                 | Инструктор показывает эталон; ученик наблюдает                | Should    |
| Генерация сценариев          | Инструктор/ИИ создаёт сценарий на основе установки            | Must      |

### 3.10. Ролевая система

Роль **Администратор** относится к управлению **тренажёрным комплексом (КТК)**, а не к IT-инфраструктуре. Инфраструктурное администрирование (Deckhouse, VKCloud, СУБД, мониторинг кластера) **не входит** в ролевую модель платформы и вынесено за её рамки.

| Роль | Права |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Администратор** | Управление тренажёрным комплексом: просмотр пользователей/ролей (учётки и роли ведутся в LDAP/AD сторонним сервисом, CRUD вне платформы); глобальный контроль учебной библиотеки; **жёсткое удаление** шаблонов/сценариев/типов компонентов; настройка политики оценки и экзаменационных правил; контроль качества обучения и учебный аудит |
| **Инструктор** | Полный CRUD **своих** шаблонов установок и сценариев; ведение библиотеки компонентов и каталога неисправностей; управление пресетами/демо-контентом; запуск сессий; наблюдение (read-only) за сессиями операторов; экзамен; переопределение итоговых оценок |
| **Оператор (обучаемый)** | Прохождение сессий; управление HMI; просмотр своей истории/оценок |

## 7. Архитектура системы

### 7.1. Стиль архитектуры

**Микросервисная архитектура** с оркестрацией на **Deckhouse** (российский дистрибутив Kubernetes). Service Mesh — **Istio** (mTLS между сервисами, Ingress Gateway, traffic policies). Взаимодействие между микросервисами — **HTTPS/REST** (JSON) с mTLS через Istio sidecar; hot-path (Simulation Engine, AI) — **gRPC**. Внешний API для клиентов (браузер) — **REST** (OpenAPI) + **WebSocket** (телеметрия). API Gateway / BFF — **Angie** (отечественный форк nginx) за Istio Ingress Gateway.

### 7.4. Обоснование выбора СУБД и кэша

**Picodata** выбрана как основная СУБД по следующим критериям:
- Сертификат ФСТЭК УД4, входит в РРПО — закрывает требования отечественности.
- PostgreSQL-совместимый wire-протокол (PGPROTO) — подключение стандартными PG-клиентами (asyncpg, psql, драйверы Go/Java).
- Raft-репликация из коробки — не нужен внешний Patroni, упрощает операции.
- Failover < 30 с через сервисное имя кластера.
- Начиная с версии 26.1 (март 2026) — поддержка транзакционного выполнения запросов.

> **Ограничение совместимости (учтено при проектировании):** системные каталоги PostgreSQL в Picodata реализованы частично. ORM-инструменты, использующие интроспекцию `pg_catalog` (reflection в SQLAlchemy), требуют адаптации. Рекомендуется: работа через raw SQL / query builder без reflection, либо использование Picodata SQL напрямую. Миграции схемы — скриптами (не Alembic autogenerate).

**Radix** (Redis-совместимый плагин Picodata) — кэш:
- Единый вендор с СУБД — упрощает поддержку.
- Сертификат ФСТЭК — замена Redis в контуре КИИ.
- Redis-совместимый протокол — работает со стандартными клиентами.

### 7.5. Обоснование Angie как API Gateway

**Angie** (v1.11.6, май 2026) — отечественный форк nginx, развиваемый оригинальной командой разработчиков nginx:
- Полная обратная совместимость с конфигурацией nginx (drop-in replacement).
- BSD-лицензия; включён в РРПО.
- HTTP/3 (QUIC), WebSocket-проксирование, TLS-терминация, rate-limiting.
- Нативные метрики Prometheus (`/status` JSON) — интеграция с Пульт без дополнительных экспортеров.
- Динамическое управление upstream без reload (API) — критично для маршрутизации на session-specific Simulation Engine.
- Автоматическое обнаружение сервисов Docker/K8s (встроенный service discovery).
- Существует Ingress-контроллер Angie для Kubernetes (замена Ingress-nginx).

### 7.6. Коммуникация: gRPC внутри, REST наружу

| Направление | Протокол | Обоснование |
|-------------|----------|-------------|
| Браузер ↔ Gateway | REST (HTTPS) + WebSocket | Стандартный веб-стек, OpenAPI, широкая совместимость |
| Gateway ↔ Сервисы | gRPC (mTLS) | Типизированные контракты (protobuf), низкая латентность, стриминг, кодогенерация |
| Сервис ↔ Сервис | gRPC (mTLS) | Строгие контракты, эффективная сериализация, двунаправленный стриминг |
| Session Orchestrator → Frontend | WebSocket | Push-телеметрия 1 Гц, алармы, статусы |

### 7.9. Развёртывание на Deckhouse

#### Namespace-сегментация:
- `ktk-app` — stateless-сервисы (gateway, auth, template, scenario, orchestrator, reporting)
- `ktk-sim` — Simulation Engine (повышенные CPU-лимиты, dedicated node pool)
- `ktk-ai` — AI Service (GPU node pool)
- `ktk-data` — Picodata + Radix (отдельный node pool, anti-affinity)
- `ktk-obs` — Пульт + Графиня + Fluent Bit

#### Node Pools:
- `app` — general-purpose (HPA по CPU/memory)
- `sim` — CPU-intensive (guaranteed QoS для 1 Гц)
- `ai` — GPU (nodeSelector + taint)
- `db` — storage-optimized (SSD, anti-affinity across hypervisors)

#### Сетевые политики:
- NetworkPolicy: межсервисный трафик только по разрешённым gRPC-портам
- Ingress: только Angie открыт наружу (порты 443)
- Egress к OT-сети: **запрещён** (нет маршрутов)

## 10. Допущения и ограничения

### 10.1. Допущения
- Команда сильнее в web-разработке (Python/TypeScript/Go).
- В команде есть технолог для валидации физики атмосферного блока.
- GPU-ресурсы (VK Cloud) доступны для AI Service.
- Регламент из `docs/IT-Camp/Вводные данные` — достаточный источник для моделирования.

### 10.2. Ограничения
- Нет полевого оператора, VR, 3D.
- Нет online OT-интеграций (OPC/Modbus).
- Нет LDAP — только JWT.
- Физика L1 (упрощённые ODE/lookup); стабильный Model API для замены на L2/L3.
- Криптопротокола — HMAC (не СКЗИ).
- Библиотека компонентов покрывает всю схему КТС (ЭЛОУ + Атмосфера + ГДМ); демо-стенд — фрагмент ЭЛОУ-АВТ.

### 10.3. Зависимости
- Доступ к VK Cloud, квоты на GPU.
- Дистрибутив Deckhouse (community или enterprise).
- Лицензия/trial Picodata.
- Лицензия Пульт + Графиня.
