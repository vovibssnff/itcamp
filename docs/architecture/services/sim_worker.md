# Сервис: Simulation Worker — `sim-worker`

> Слой: Вычислительный | Namespace: `ktc-sim` (Node Pool `sim`) | Под: `sim-worker-N` (per session)
> Смежно: `sim_manager.md` (диспетчер подов), `Simulation_Engine_модель_namespace_k8s.md`, `Реестр_сервисов...`, `Архитектура_КТК_K8s.drawio`

## 1. Назначение

**Цифровой двойник техпроцесса ЭЛОУ-АВТ** — единственный источник истины о технологическом состоянии (FR-ISO-03). Самый ресурсоёмкий и детерминированный компонент системы. На каждую сессию создаётся **изолированный экземпляр** `sim-worker` (1 сессия = 1 под), чтобы сбой одной сессии не ронял другие (ARCH-08, per-session isolation).

## 2. Основные функции

- Расчёт динамики установки (ЭЛОУ, колонны К-1/К-2, вакуум, печи, насосы) по тику **≥1 Гц** модельного времени.
- **Model API**: `step`, `get_state`, `set_state`, `inject_fault`, `set_speed`.
- Порождение тегов/алармов (сигнализации, ПАЗ, ППК).
- Детерминированное исполнение (контроль ГПСЧ).
- Поддержка ускорения модельного времени (0.1×–10×) через внутренние подшаги.

## 3. Технологии

Python + NumPy/SciPy (численное интегрирование ODE), собственная OTS-модель ЭЛОУ. Точка расширения L1→L3 (внешний solver, напр. DWSIM) через тот же Model API без изменения контракта (ARCH-01).

## 4. Внутренняя структура

- Процесс движка: цикл интегрирования, решает шаг ODE.
- Локальная RAM-модель текущего состояния шага (детерминизм).
- Ведение тегов/алармов (сигнализации, ПАЗ, ППК).
- `/metrics` (tick-lag).

## 5. API / контракты (Model API)

Методы, которые `orchestrator` вызывает у `sim-worker` напрямую (hot-path, gRPC):

| Метод | Протокол | Назначение |
|---|---|---|
| `step()` | gRPC | один шаг интегрирования → новое состояние |
| `get_state()` | gRPC | полное состояние (телеметрия/снапшот) |
| `set_state(state)` | gRPC | установить состояние (restore/старт) |
| `inject_fault(fault_id)` | gRPC | внедрить аварию |
| `set_speed(0.1…10)` | gRPC | коэффициент скорости модельного времени |

> Жизненный цикл этого инстанса (создание/удаление) управляется **не** Model API, а `sim-manager` (см. `sim_manager.md`). В target си-worker работает как K8s-под (им управляет оператор sim-manager через CRD `SimWorker` + reconcile), в прототипе — как Docker-контейнер через DockerProvider.

## 6. Зависимости и протоколы

| Взаимодействует с | Тип | Протокол |
|---|---|---|
| Session Orchestrator (`orchestrator`) | микросервис | Model API (gRPC), mTLS |
| Snapshot Service (через orchestrator) | микросервис | Model API (`get_state`/`set_state`) |
| Пикодата (`db`) | СУБД | SQL (журнал аварий/действий, append-only) |
| Пульт / Fluent Bit | observability | `/metrics` (tick-lag), stdout |

**Не связан** с фронтом, ИИ, assessment, репортом напрямую (изоляция OT и сети).

## 7. Данные

- Пикодата: журнал аварий/действий (append-only).
- Локальная RAM: состояние модели текущего шага (детерминизм).
- Radix: не используется движком напрямую (состояние сессии кэширует оркестратор).

## 8. Объекты Kubernetes (namespace `ktc-sim`)

| Объект | Описание |
|---|---|
| Pod `sim-worker-N` | персональный движок на сессию (до 50) |
| Service `sim` | точка доступа Model API |
| Node Pool `sim` | выделенные CPU-узлы, taint `sim=true` |
| ResourceQuota/LimitRange | жёсткие лимиты (guaranteed QoS для 1 Гц) |
| NetworkPolicy | только от `orchestrator`/`snapshot` |

Поды создаёт/удаляет `sim-manager` через K8s API — конфигурация и лимиты пода задаются там (см. `sim_manager.md`). В прототипе (Docker Compose) — контейнер `sim-worker` поднимается через DockerProvider с публикацией порта на localhost.

## 9. Метрики (в Пульт + Графиня)

- **tick-lag** (главная метрика real-time).
- Число активных сессий (под-движков).
- CPU/RAM Node Pool `sim`, время restore.

## 10. Отказоустойчивость / детерминизм

- Per-session под: падение не роняет другие сессии.
- Рестарт + restore из последнего чекпоинта/снапшота (≤15 с, обрыв ≤3 мин).
- Детерминированный численный метод + seed ГПСЧ (в снапшоте) → продолжение идентично.
- Перезапуск инстанса (под/контейнер) инициирует `sim-manager` (ensure/reconcile), а восстановление состояния из снапшота выполняет `orchestrator` через Model API `set_state` после того, как инстанс стал ready.

## 11. Открытые вопросы

1. CPU-бюджет для гарантии 1 Гц при 10× (внутренние подшаги).
2. Численный метод и размер шага — согласовать с технологом.
3. Батч-шаги (`step` по одному на тик vs пачка) — влияние на 10× скорость (совм. с `orchestrator`).
