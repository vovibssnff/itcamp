# Сервис: Брокер сообщений — `broker`

> Слой: Инфраструктурный (шина/очередь) | Namespace: Target — `ktc-infra` (см. §12; прототип — `ktc-app`) | Под: `broker`
> Смежно: `Реестр_сервисов...`, `Сценарии_экзамен...`, `Архитектура_КТК_K8s.drawio`

## 1. Назначение

**«Почтовая служба»** — асинхронная шина и очередь задач. Развязывает сервисы: тяжёлая/неблокирующая обработка (отчёты, ИИ) и события сессий выполняются асинхронно, не мешая real-time контуру.

## 12. Размещение и обоснование (почему НЕ в слое данных)

- **Брокер — это НЕ данные.** Слой `ktc-data` (Picodata/Radix/S3) — персистентность (хранилище). Брокер — **асинхронный транспорт/очередь между сервисами** (временная персистентность очередей), другая природа. Класть его «к данным» концептуально неверно.
- **Брокер обслуживает связи прикладных сервисов** (`orchestrator → report/ai`, `assessment`), т.е. находится «в середине» потоков, а не на «конце» (как БД).
- **Задержка и сеть:** производители/потребители (`orchestrator`, `report`, `ai`, `assessment`) рядом; изолированный сегмент добавляет latency и усложняет сетевые политики без пользы (real-time телеметрия идёт мимо брокера напрямую).

**Вывод (Target):** размещать в **отдельном инфра-сегменте `ktc-infra`**, а не в `ktc-data` (`kubernetes`; отдельно от данных и прикладной логики, независимое масштабирование/обновление). В прототипе для простоты допустим `ktc-app`.

| Вариант | Где | Оценка |
|---|---|---|
| `ktc-infra` (Target) | отдельный инфра-сегмент | **рекомендуется** — чистые слои, изоляция, независ. масштаб |
| `ktc-app` (прототип) | вместе с прикладными | приемлемо на MVP (простота), не для Target |
| `ktc-data` | к Picodata/Radix | ❌ — смешение «шины» и «хранилища» |

## 2. Основные функции

- **Очередь задач**: отчёты, ИИ-расчёты/инференс.
- **События сессий**: старт/стоп/чекпоинт, авария (для наблюдателей/аудита).
- Гарантированная доставка, retry, приоритеты.
- Развязка publisher/subscriber между сервисами.

## 3. Технологии

RabbitMQ / Kafka / NATS (выбор фиксируется — открытый вопрос).

## 4. Внутренняя структура

- Очереди (queue) для задач и топики/стримы (topics) для событий.
- Продюсеры: `orchestrator` (события), `gw`/`fe` (запросы отчёта).
- Потребители: `report` (задачи PDF), `ai` (задачи инференса), `assessment` (события).
- `/metrics` для состояния очередей.

## 5. Контракты/очереди

| Очередь/топик | Продюсер → Потребитель | Протокол |
|---|---|---|
| `report.tasks` | gw/orchestrator → report | AMQP / Kafka / NATS |
| `ai.tasks` | orchestrator → ai | AMQP / Kafka / NATS |
| `session.events` | orchestrator → assessment/наблюдатели | AMQP / Kafka / NATS |
| `assessment.events` | assessment → broker (аудит/задачи) | AMQP / Kafka / NATS |

## 6. Зависимости и протоколы

| Взаимодействует с | Тип | Протокол |
|---|---|---|
| Session Orchestrator (`orchestrator`) | микросервис | producer — AMQP / Kafka / NATS |
| Reporting (`report`) | микросервис | consumer — AMQP / Kafka / NATS |
| AI Service (`ai`) | микросервис | очередь инференса — AMQP / Kafka / NATS |
| Assessment Engine (`assessment`) | микросервис | producer/consumer — AMQP / Kafka / NATS |
| promColl | observability | `/metrics` |

## 7. Данные

- Кратковременное хранилище сообщений в очереди/стримах.
- Не является системой хранения бизнес-данных; события дублируются в Picodata/KUMA.

## 8. Объекты Kubernetes

| Объект | Описание |
|---|---|
| StatefulSet `broker` | кластер брокера (репликация), N≥3 для отказоустойчивости |
| Service `broker` | ClusterIP |
| PersistentVolume(s) | для хранения журнала/очередей (если требуется) |
| Secret | учётные данные доступа |
| Pod + sidecar `istio-proxy` | mTLS (для прикладных сервисов) |

## 9. Метрики (в Astra Monitoring)

- Длина очередей, rate сообщений, задержка доставки.
- Время обработки задач report/ai.
- Отказы/ретраи.

## 10. Отказоустойчивость / масштабирование

- Кластер (N≥3) — отказ одной ноды не теряет данные.
- Приоритизация задач; retry упавших.
- Масштабирование потребителей (report/ai) по длине очереди.

## 11. Открытые вопросы

1. Выбор: **RabbitMQ / Kafka / NATS** — влияет на протокол шины (AMQP vs Kafka binary vs NATS).
2. Расположение: Target — отдельный `ktc-infra` (рекомендация §12); прототип допустимо `ktc-app`. На схеме/в docs сейчас `ktc-app` — подлежит переносу при целевой сборке.
3. Персистентность очередей (PV) и политика хранения (retention).
4. Поток событий для аудита в KUMA — дублирование через broker или напрямую из сервисов.
