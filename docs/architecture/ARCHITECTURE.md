# Архитектура КТК — общий обзор

Единая «карта» системы: что делает проект, из каких сервисов состоит, как они общаются,
как протекает типичный сценарий и почему выбраны те или иные технологии.
Детали каждого сервиса — в `architecture/services/*.md`.

---

## 1. Что это за система

**КТК** — система компьютерных тренажёрных комплексов для нефтеперерабатывающих установок.

Сейчас математическая модель настроена под **одну конкретную установку — ЭЛОУ-АВТ**
(блок ЭЛОУ/обессоливание, атмосферный блок К-1/К-2 и печи, ГДМ/гидроочистка,
общеустановочные системы): `sim-worker` настроен на физику этого демо-шаблона.

Архитектура, однако, **идет в сторону «Конструктора»** — платформы, где инструктор без
программирования собирает установку из типовых компонентов. Часть этого функционала уже
реализована:

- **сборка установки** на canvas из библиотеки компонентов (насосы, колонны, печи, электродегидраторы, регуляторы…);
- **сохранение** шаблона установки (копирование/редактирование/удаление);
- **создание** учебных/экзаменационных сценариев (в т.ч. аварийных) с неисправностями;
- **проведение** тренировок/экзаменов с живым наблюдением и «инъекцией» неисправностей.

**Что реализовано, а что нет:** библиотека компонентов, шаблоны установок, валидация
графа и экспорт init-state — есть (`constructor`). А вот **математическая модель ещё не
является универсальным интерпретатором** произвольного графа: движок пока знает физику
только демо-шаблона ЭЛОУ-АВТ. Универсальный режим «граф → систему уравнений» —
целевая точка развития (архитектурное направление).

---

## 2. Ключевая идея: граф как единица конфигурации

Система строится вокруг понятия **графа установки** — уже сейчас шаблоны, валидация и
export init-state работают с графом:

```
Граф установки (JSON)
├── Узлы (nodes) — экземпляры компонентов с параметрами (Н-2, К-1…)
├── Рёбра (edges) — потоковые связи между портами (жидкость/газ/сигнал/электричество)
└── Layout — координаты мнемосхемы для отображения
```

Потребители графа:

| Потребитель графа | Что делает |
|---|---|
| `constructor` | CRUD шаблонов, валидация, экспорт init-state (работает с графом уже сейчас) |
| Рендерер мнемосхемы | Отображает установку в HMI |
| Генератор/сценарии | Находит «уязвимые точки» для неисправностей |
| Валидатор | Проверяет связи, отсутствие «висячих» портов |

> **Важно:** принцип «граф → систему уравнений» в движке (`sim-worker`) сейчас реализован
> частично — он знает физику только демо-шаблона ЭЛОУ-АВТ. Полностью универсальный
> интерпретатор произвольного графа — **целевое направление** архитектуры (ARCH-07),
> а не текущее состояние.

## 3. Роли и пользователи

Три роли (RBAC). Администратор управляет **тренажёрным комплексом (КТК)**, а не IT-инфраструктурой.

| Роль | Кратко | Ключевые права |
|---|---|---|
| **Администратор** | Управляет КТК | Просмотр пользователей, жёсткое удаление, политика оценки, учебный аудит |
| **Инструктор** | «Автор и судья» | CRUD своих шаблонов/сценариев, ведение сессий, наблюдение read-only, экзамен, переопределение оценок |
| **Оператор (обучаемый)** | Проходит обучение | Прохождение сессий, управление HMI, своя история/оценки |

> Неисправности срабатывают **автоматически** из сценария (по триггерам), а не вручную в реальном времени.

## 4. Общая карта архитектуры

```
        Клиенты (браузеры): АРМ оператора · Консоль инструктора · Admin · Наблюдатель
                                     │  HTTPS (REST) + WebSocket (1 Гц)
                                     ▼
   ┌────────────────────────────────────────────────────────────────────┐
   │   gw (API Gateway / BFF) — единственная точка проверки JWT/RBAC     │
   │   auth · constructor · scenario · orchestrator ·                   │
   │                               assessment · report · snapshot       │
   └───────┬──────────────────────────────┬────────────────────────────┘
           │ gRPC Model API               │ NATS (асинхронно)
           ▼                              ▼
   sim-manager → sim-worker         broker (report.tasks, ai.tasks,
   (детерминированный движок,        session.events)
   1 сессия = 1 инстанс)
           │
   ai-service (LLM + детерминированное ядро оценки; деградирует)
           │
   ┌───────▼──────────────────────────────────────────────────────────┐
   │ Слой данных: Picodata (СУБД) · Radix (кэш) · MinIO (объекты)      │
   └──────────────────────────────────────────────────────────────────┘
```

Все прикладные сервисы — **Go** (go 1.25), Python — только `ai` и `sim-worker`.
У каждого — `api/openapi.yaml` (REST-контракт) и `deploy/config.example.toml`
(конфигурация; путь через флаг `-config`, секреты перекрываются env).

| Сервис | Порт | Роль | Конфигурация |
|---|---|---|---|
| `gw` | 8088 | API Gateway/BFF: JWT/RBAC, rate-limit, прокси REST+WS | TOML: `upstreams`, `routes`, `auth_client` |
| `auth` | 8082 | IAM: LDAP/AD (или stub), JWT, RBAC, TOTP, introspect | TOML: `jwt`, `auth` (mode), `ldap`; env `AUTH_*` |
| `constructor` | 8083 | Библиотека компонентов, шаблоны, валидатор, экспорт init-state | TOML: `db`, `s3`, `seed` |
| `scenario` | 8084 | Сценарии тренировки/экзамена, каталог неисправностей, триггеры | TOML: `db`, `seed` |
| `orchestrator` | 8085 | «Дирижёр»: жизненный цикл сессий, телеметрия 1 Гц (WS), инъекция неисправностей, чекпоинты | TOML: `db`, `redis`, `nats`, `clients`, `telemetry` |
| `assessment` | 8081 | «Экзаменатор»: сравнение с эталоном, штрафы, вердикт, replay | TOML: `db`, `clients.scenario_url` |
| `snapshot` | 8086 | Save/restore состояния сессии (S3 + Picodata + SHA-256), presets | TOML: `db`, `s3` |
| `report` | 8087 | PDF-отчёты/протоколы (асинхронно через NATS, gofpdf) | TOML: `db`, `nats` (`report_tasks_subj`, `queue_group`) |
| `sim-manager` | 8091 | Диспетчер инстансов sim-worker (control-plane), квота 50 | TOML: `provider` (`type` memory/docker/k8s) |
| `sim-worker` | 8092 (+gRPC 50062) | Цифровой двойник, Model API, детерминизм 1 Гц (Python pkg `sim_engine`) | данные: `template_atm_demo.json`, `faults_catalog.json` |

| `frontend` | 8090 | React+TS+Vite SPA (Angie: статика + прокси `/api` → gw) | build-time `VITE_*` |

## 6. Как сервисы общаются

- **Браузер ↔ gw**: HTTPS REST (`/api/v1/*`) + WebSocket (телеметрия 1 Гц).
- **gw ↔ сервисы**: REST, контекст пользователя передаётся заголовками `X-User-ID`/`X-Roles`.
- **orchestrator ↔ sim**: gRPC **Model API** (`step`, `get_state`, `set_state`, `inject_fault`, `set_speed`, `command`).
- **orchestrator ↔ sim-manager**: REST **Control API** (create/stop/status/list инстансов).
- **Асинхронно**: NATS — `report.tasks` (→ report), `ai.tasks` (→ ai), `session.events`.

## 7. Модель безопасности (суть)

Главный принцип — **trust boundary** (см. `architecture/services/auth.md`):

```
Браузер → gw (ЕДИНСТВЕННАЯ точка проверки JWT)
            → auth /introspect (валидность + роли)
            → заголовки X-User-ID / X-Roles (JWT дальше НЕ уходит)
            → внутренние сервисы токен сами не проверяют, ключ не знают
```

- Внутренние сервисы обязаны стирать входящие `X-User-ID`/`X-Roles` (защита от подделки ролей).
- **Server-authoritative**: клиент не считает «истину»; все теги рождает только sim-worker.
- Целостность журналов/протоколов — append-only + HMAC/SHA-256.

## 8. Сквозной сценарий (сборка → экзамен)

1. **Сборка установки**: инструктор в `constructor` собирает граф из компонентов → валидация → шаблон.
2. **Создание сценария**: в `scenario` привязывает сценарий к шаблону, выбирает неисправности и триггеры, задаёт эталон действий и критерии оценки.
3. **Запуск сессии**: `orchestrator` получает init-state из `constructor` и сценарий из `scenario`, поднимает `sim-worker` через `sim-manager`, инициализирует модель (`set_state`).
4. **Цикл 1 Гц**: `sim` делает `step()` → `orchestrator` кэширует в Radix и пушит телеметрию по WS (оператор + инструктор read-only); команды оператора → `sim`.
   - Неисправности по триггерам сценария → `sim.inject_fault`.
   - Действия/алармы → `assessment` (штрафы, критические ошибки).
   - Не в экзамене — подсказки/риски от `ai`.
   - Чекпоинты → `snapshot` (защита от обрыва ≤3 мин).
5. **Завершение**: `assessment` даёт вердикт (инструктор может переопределить) → `report` через NATS формирует PDF-протокол → доступен разбор (replay + ИИ-объяснения).

## 9. Данные

| Хранилище | Что хранит |
|---|---|
| **Picodata** (СУБД, PG-wire) | Сессии, оценки, журналы (append-only), пользователи, шаблоны/графы (JSONB), сценарии, метаданные снапшотов, протоколы |
| **Radix** (кэш, Redis-совместимый) | Горячее состояние сессий (телеметрия 1 Гц) |
| **MinIO** (S3) | payload снапшотов (gzip), PDF-отчёты, иконки/SVG компонентов |

## 11. Архитектурные принципы

| ID | Принцип | Суть |
|---|---|---|
| ARCH-01 | Модульность | Замена Simulation Engine без переписывания HMI/ИИ (стабильный Model API) |
| ARCH-02 | Server-authoritative | Клиент не считает «истину» оценки/телеметрии |
| ARCH-03 | Изоляция OT | Нет промпротоколов и маршрутов в OT-сеть; теги рождает только sim |
| ARCH-07 | Граф как конфигурация | Топология определяет модель, HMI, сценарии |
| ARCH-08 | Per-session isolation | Каждая сессия — изолированный инстанс sim-worker (до 50) |
