## Часть 0. Как читать документ

### 0.1. Четыре «слоя» сценариев

Слово «сценарий» в проекте используется в четырёх разных значениях. Их важно не путать:

| Уровень | Что называется сценарием | Кто «владеет» | Где описан |
|---|---|---|---|
| **Бизнес (UC)** | Что делает пользователь: собрал установку, провёл экзамен | Роли RBAC | Часть A |
| **Технический (flow)** | Последовательность вызовов между микросервисами | `orchestrator` | Часть B |
| **Учебный (Scenario)** | Сущность БД: шаблон + набор неисправностей с триггерами + эталон | `scenario` | Часть C, D |
| **Технологический (fault)** | Конкретная авария процесса: `FLT-K1-PRESSURE-HIGH` | `sim` | Часть C |

Один экзамен = один UC (Часть A) + один технический flow (Часть B) + одна сущность `Scenario`,
которая содержит N неисправностей `fault_id` (Часть C).

### 0.2. Действующие лица (сервисы)

| Сокращение | Сервис | Роль в сценариях |
|---|---|---|
| `fe` | Frontend SPA | Тонкий клиент, ничего не считает |
| `gw` | API Gateway / BFF | Единственная точка проверки JWT/RBAC |
| `auth` | Auth / Session | LDAP, JWT, 2FA, introspect |
| `constructor` | Constructor Service | Компоненты, шаблоны, валидация графа, экспорт init state |
| `scenario` | Scenario / Catalog | Сценарии, каталог неисправностей, эталоны |
| `orchestrator` | Session Orchestrator | Дирижёр real-time контура |
| `sim-manager` | Simulation Manager | Control API: жизнь инстансов worker |
| `sim` / `sim-worker` | Simulation Worker | Единственный источник тегов (FR-ISO-03), Model API |
| `assessment` | Assessment Engine | Авторитетный балл (rule-based) |
| `ai` | AI Service | Explain / Predict / Adaptive; **совещательный** |
| `snapshot` | Snapshot Service | save / restore |
| `report` | Reporting | PDF + подписанный протокол |
| `broker` | NATS JetStream | Асинхронная шина |

### 0.3. Три инварианта, которые действуют во всех сценариях

1. **Server-authoritative (ARCH-02).** Клиент не считает ни телеметрию, ни оценку. Любое значение на экране пришло от `sim` через `orchestrator`.
2. **ИИ не влияет на балл (ADR-001 ai-service).** Балл считает детерминированное ядро `assessment` / `analysis`. ИИ может только *предложить* инструктору снять штраф (`suggested_score_delta`). Тест `test_score_identical_with_and_without_llm` фиксирует это свойство.
3. **Детерминизм (ADR-СЕ-04 sim-worker).** Один `seed` + та же последовательность команд и неисправностей → байт-в-байт те же теги. Без этого невозможны ни HMAC-протокол экзамена, ни restore снапшота.

## Часть A. Бизнес-сценарии по ролям

### A.0. Ролевая модель — источник истины

**Нормативный источник — `ARCHITECTURE-2.md` §3 «Роли и пользователи».** Все права в таблицах ниже
выводятся **только** из него. Если сценарий требует полномочия, которого в §3 нет, — правится §3,
а не матрица сценариев.

| Роль | Кратко | Права (по §3, дословно) |
|---|---|---|
| **Администратор** | Управляет тренажёрным комплексом | Пользователи и роли (создание учёток, назначение/отзыв ролей, блокировка); глобальный контроль учебной библиотеки; **жёсткое удаление** шаблонов/сценариев/типов компонентов; настройка политики оценки и экзаменационных правил; контроль качества обучения и учебный аудит |
| **Инструктор** | «Автор и судья» | Полный CRUD **своих** шаблонов/сценариев и компонентов; ведение каталога неисправностей; создание и управление **сессиями**; видимость **всех** сессий (не только своих); подключение к любой сессии для наблюдения **read-only**; настройка сценариев с автоинъекцией неисправностей; **экзамен**; **переопределение оценок** |
| **Оператор (обучаемый)** | Проходит обучение | Прохождение сессий, управление HMI, просмотр **своей** истории/оценок |

**Три следствия, которые действуют во всех сценариях Части A:**

1. **Роли консолидированы (v2.1).** Полномочия прежних дополнительных ролей собраны у Инструктора.
   Отдельных ролей «методист», «наблюдатель», «экзаменатор» нет — наблюдение и экзамен это режимы
   работы Инструктора, а не роли.
2. **Администратор — это администратор КТК, а не IT.** Deckhouse, VKCloud, Picodata, мониторинг
   кластера **вне ролевой модели**; привилегированный доступ системного администратора идёт через PAM.
3. **Автор ≠ администратор.** Инструктор создаёт контент (шаблоны, сценарии, эталоны) и судит
   результат; Администратор задаёт рамки (учётки, политика оценки) и удаляет контент жёстко.
   Пересечение ровно одно — учебная библиотека: Инструктор ведёт **свою** часть, Администратор
   контролирует **всю**.

**Два права, выведенные не из §3, а из сервисных доков** (помечены в матрице отдельно):

| Право | Роль | Откуда |
|---|---|---|
| Restore состояния в **тренировке** | Оператор | `snapshot.md` §2: «В **экзамене** restore ученику запрещён» → в тренировке разрешён |
| Управление скоростью модели `set_speed` | Инструктор | `session_orchestrator.md` §2 + §5; частный случай «управления сессиями» из §3 |

### UC-01. Вход в систему

**Кто:** любая роль.
**Цель:** получить доступ к платформе с корректным набором прав.

**Основной поток:**

1. Пользователь открывает SPA (статика раздаётся через `gw`), вводит логин/пароль.
2. `gw` → `auth` `POST /login`; `auth` проверяет учётку **в LDAP/AD**. Локальных паролей в БД нет.
3. Для роли **Инструктор** и **Администратор** — второй фактор: `POST /mfa/verify` (TOTP).
4. `auth` выдаёт **JWT** (access TTL 15 мин, refresh 24 ч) и набор ролей.
5. `fe` получает токен, показывает домашний экран по роли:
   - Оператор → АРМ / список назначенных сессий;
   - Инструктор → каталог шаблонов + консоль;
   - Администратор → раздел администрирования.
6. Событие входа уходит в аудит → KUMA.

**Альтернативы и исключения:**

| Ситуация | Поведение |
|---|---|
| Неверный пароль | 401; счётчик неудач; событие в KUMA |
| Превышен rate-limit (≤10 попыток авторизации в минуту) | 429 на `gw` |
| Неверный TOTP | 401 `MFA_FAILED`, событие в KUMA |
| LDAP недоступен | Грациозный отказ: «каталог недоступен», вход невозможен (fallback на локальные пароли отсутствует принципиально) |
| Истёк access-токен | `fe` прозрачно вызывает `POST /refresh`; при истёкшем refresh — редирект на вход |
| Привилегированный доступ сисадмина к БД/кластеру | **Не через платформу** — через отечественный PAM, вне ролевой модели |

### UC-02. Управление пользователями и ролями (Администратор)

1. Админ открывает раздел «Пользователи».
2. `gw` агрегирует список из `auth` (профили + роли из Picodata, идентичности из LDAP).
3. Действия: создание учётной записи (привязка к LDAP-идентичности), назначение/отзыв роли, блокировка.
4. Каждое изменение прав — append-only запись в аудит и событие в KUMA.

**Важно:** админ управляет **тренажёрным комплексом**, а не IT-инфраструктурой. Deckhouse, VKCloud, Picodata, мониторинг кластера — вне ролевой модели платформы.

---

### UC-03. Настройка политики оценки и правил экзамена (Администратор)

1. Админ задаёт глобальные правила: `pass_score`, норматив квитирования `ack_deadline_s`, вес критических ошибок, правила начисления штрафов по типам аварий.
2. `gw` → `assessment` (модуль вердикта и переопределения).
3. Политика применяется ко всем новым сессиям; уже завершённые протоколы **не пересчитываются** (append-only + HMAC).
4. Отдельно настраивается, какие подсказки ИИ разрешены в тренировке и запрещены в экзамене (FR-AI-06), и работает ли справочный чат-бот на экзамене (флаг `KTK_CHAT_IN_EXAM`).

### UC-04. Жёсткое удаление учебного контента (Администратор)

Инструктор может удалять только **свои** шаблоны/сценарии (мягко). Жёсткое удаление типов компонентов, шаблонов, сценариев — исключительно у админа.

**Проверки перед удалением:**

1. Шаблон не используется ни в одном сценарии (`scenario` отвечает списком зависимостей).
2. Сценарий не привязан к активной или незакрытой сессии.
3. Тип компонента не используется ни в одном шаблоне.

При нарушении — 409 со списком зависимых объектов. Удаление логируется в аудит; снапшоты и протоколы завершённых сессий **не удаляются** (иммутабельность).

---

### UC-05. Учебный аудит и контроль качества обучения (Администратор)

1. Админ смотрит агрегаты: доля сдавших, распределение баллов, топ ошибок, средние времена реакции.
2. Данные — из append-only журналов `assessment` (Picodata) + профили ошибок из `ai` (`analysis/profile.py`).
3. Отдельно проверяются **переопределения оценок** инструкторами (кто, когда, с каким обоснованием) — это чувствительное событие ИБ.

### UC-06. Ведение библиотеки компонентов (Инструктор / Администратор)

**Цель:** пополнить палитру типового оборудования (насос, колонна, печь, электродегидратор, реактор, регулятор…).

1. Инструктор создаёт `ComponentType` в `constructor`:
   - **порты**: `{id, name, type: liquid|gas|signal|electric, direction: in|out, required: bool}`;
   - **параметры**: `{id, name, unit, default, min, max, type: float|int|enum}`;
   - **категория**: ЭЛОУ / Атмосфера / ГДМ / Общие;
   - **иконка** (SVG/PNG) → S3 bucket `component-icons`.
2. `POST /components` → запись в Picodata, иконка в S3.
3. Компонент появляется в палитре конструктора с фильтрацией по категориям и полнотекстовым поиском.

**Ограничение текущей версии:** физика конкретной ЭЛОУ-АВТ живёт в коде `sim-engine` (`network.COUPLINGS`, `interlocks.INTERLOCK_EFFECTS`) — ADR-СЕ-03. Новый *визуальный* компонент добавляется без правки движка; новый *физический* тип с собственной динамикой требует расширения модели.

### UC-07. Сборка установки в конструкторе (Инструктор)

**Цель:** без программирования собрать схему установки на canvas.

**Основной поток:**

1. Инструктор открывает конструктор (canvas на Konva).
2. Перетаскивает компоненты из палитры → создаются узлы графа (`nodes`) с параметрами по умолчанию.
3. Соединяет порты мышью → создаются рёбра (`edges`). **Проверка типов в момент соединения**: жидкость↔жидкость, сигнал↔сигнал; несовместимый порт не подсвечивается как валидная цель.
4. В панели свойств правит параметры экземпляра (расход, объём, уставки).
5. Раскладка мнемосхемы (`layout`: координаты, подписи) сохраняется вместе с графом.
6. **Автосохранение каждые 30 с** — черновик уходит в `constructor`.

**NFR:** отклик конструктора ≤200 мс на графе до 200 узлов.

**Исключения:**

| Ситуация | Поведение |
|---|---|
| Обрыв связи во время сборки | Черновик остаётся в локальном состоянии, при восстановлении досылается |
| Одновременное редактирование одного шаблона | Конфликт версий → предложение форкнуть (UC-09) |
| Граф больше лимита узлов/рёбер | Отказ валидации (лимит — открытый вопрос `constructor.md` §11.2) |

### UC-08. Валидация и сохранение шаблона (Инструктор)

`POST /templates/{id}/validate` проверяет:

| Проверка | Смысл |
|---|---|
| Совместимость типов портов | Нельзя завести сигнал в патрубок жидкости |
| Связность графа | Нет изолированных подграфов |
| Наличие источника и стока | Поток должен откуда-то приходить и куда-то уходить |
| Отсутствие «висячих» обязательных портов | `required: true` порт должен быть подключён |

Результат — список ошибок с привязкой к `node_id`/`edge_id`; `fe` подсвечивает проблемные места прямо на canvas. Шаблон с ошибками сохранить **как черновик** можно, **запустить сессию** на нём — нельзя.

---

### UC-09. Копирование / форк шаблона (Инструктор)

`POST /templates/{id}/copy` — deep clone с новым ID, атомарной транзакцией в Picodata. Типовой путь: взять эталонный шаблон ЭЛОУ-АВТ → форкнуть → упростить/усложнить под группу обучаемых.

### UC-10. Создание учебного сценария (Инструктор)

**Цель:** превратить статичный шаблон в учебную ситуацию.

1. Инструктор выбирает **шаблон установки** (`scenario` → `constructor` `GET /templates/{id}`).
2. Выбирает неисправности из **каталога** (`fault_id`, описание, `affected_tags`, `severity`).
3. Для каждой задаёт **триггер**:
   - *по модельному времени*: «на 600-й секунде»;
   - *по условию*: «когда `PRSA 204 ≥ 4.0`».
4. Задаёт **эталон** — ожидаемую последовательность действий:
   ```json
   [{"step":1,"action":"ACK_ALARM","target":"PRSA-204","within_s":60},
    {"step":2,"action":"START","target":"PUMP-N6A","within_s":90},
    {"step":3,"action":"SET_SP","target":"FRC-408","within_s":150,"value":42}]
   ```
5. Задаёт **критерии**: `pass_score`, `ack_deadline_s`, вес критических ошибок.
6. Помечает сценарий как тренировочный или **экзаменационный**.
7. Сохранение → SHA-256 контроль целостности, событие изменения → KUMA.

**RBAC:** инструктор правит только свои сценарии; клонировать чужой — по правилам (открытый вопрос `scenario_catalog.md` §11.3).

### UC-11. Генерация сценария через ИИ (Инструктор)

1. Инструктор нажимает «сгенерировать сценарий», задаёт цель: тип аварии, сложность, целевой профиль ошибок группы.
2. `orchestrator`/`gw` → `ai` `generate_scenario` (контракт в proto описан).
3. ИИ анализирует **граф установки** (из `constructor`) — ищет «уязвимые точки» топологии — и профиль ошибок обучаемых (`analysis/profile.py`).
4. Результат — **черновик** сценария: набор неисправностей, триггеры, предполагаемый эталон.
5. Инструктор проверяет и правит; сохранение — только после его подтверждения.

**Статус:** FR-AI-05 вынесен в отдельную задачу — требует доступа к графу от `constructor` и dry-run в `sim`. Контракт `GenerateScenario` в proto уже описан, реализация — точка роста.

**Деградация:** при недоступности GPU кнопка неактивна; ручное создание сценария (UC-10) не страдает.

### UC-12. Создание и запуск сессии (Инструктор)

1. Инструктор выбирает: шаблон + сценарий + оператор(ы) + режим (**Тренировка** / **Экзамен**).
2. `POST /session/start` → `orchestrator`.
3. `orchestrator` собирает конфигурацию:
   - `constructor` `GET /templates/{id}/export` → init state;
   - `scenario` `GET /scenarios/{id}` → неисправности с триггерами + эталон (в экзамене — `GET /scenarios/exam`, случайная выдача).
4. `orchestrator` → `sim-manager`: поднять `sim-worker` под эту сессию (**1 сессия = 1 под**, до 50).
5. `CreateSession(session_id, seed)` + `SetState(init)` — модель инициализирована, `seed` зафиксирован.
6. Сессия переходит в `RUNNING`, стартует тик-цикл 1 Гц (детали — Часть B.3).
7. Оператор получает уведомление, открывает АРМ.

**Загрузка шаблона/снапшота — ≤15 с (PERF-03).**

### UC-13. Работа оператора в АРМ (Оператор)

**Цель:** вести технологический режим и отрабатывать отклонения.

**Что видит оператор:**

- **Мнемосхема** — рендер из `layout` шаблона, обновление по телеметрии 1 Гц (WebSocket);
- **Тренды** — до 8 серий (uPlot);
- **Панель алармов** — приоритеты HH / H / L / LL;
- **Faceplate-узлы** регуляторов: PV / SP / OUT, режим Auto / Manual;
- **Кнопка ESD** (аварийный останов).

**Что может делать:**

| Действие | Тип в журнале | Пример |
|---|---|---|
| Квитировать аларм | `ACK_ALARM` | `PRSA 204` |
| Изменить уставку | `SET_SP` | `FRC 408: 18 → 42` |
| Переключить режим контура | `SET_MODE` | `LRCA 641 → Manual` |
| Задать выход в ручном | `SET_OUT` | `TRC 3 OUT = 35 %` |
| Пуск/останов оборудования | `START` / `STOP` | `PUMP-N6A` |
| Аварийный останов | `ESD` | вся установка |

**Каждое действие:**

1. `fe` → `gw` → `orchestrator` (WS/REST);
2. **до подтверждения** (в тренировке) `orchestrator` может спросить `ai` `predict_behaviour` — оценку риска; если правило из `data/risk_rules.json` сработало, оператор видит предупреждение и подтверждает осознанно;
3. `orchestrator` → `sim` `Command(...)`;
4. `orchestrator` пишет `OperatorAction` в Picodata с **модельной** меткой времени и шлёт событие в `assessment`.

**Ключевой момент:** метка времени — **модельная**, не астрономическая. Иначе `set_speed(10)` ломает оценку времени реакции.

### UC-14. Наблюдение инструктора (Инструктор, read-only)

1. Инструктор видит **все** сессии (не только свои) и подключается к любой.
2. `orchestrator` открывает **второй WebSocket** к той же сессии в режиме read-only: телеметрия, алармы, лента действий оператора, текущий накопленный балл.
3. Инструктор **не может** инжектить неисправности в реальном времени — они срабатывают **только** автоматически по триггерам сценария (`FR-ROLE-04`).

> **Зафиксировано: live-инъекция неисправностей отсутствует как функция.**
>
> Всё, что происходит в сессии, задано **заранее** — в сценарии (`scenario`), с триггером по модельному
> времени или по условию на теге. `sim.inject_fault` вызывается **исключительно** планировщиком событий
> внутри `orchestrator`. Внешнего маршрута к `inject_fault` (от `fe`, от `gw`, от инструктора) не существует.
>
> **Почему так, а не «разрешить, но с отметкой в протоколе»:**
>
> | Причина | Что ломает live-инъекция |
> |---|---|
> | **Детерминизм** (ADR-СЕ-04) | Ход сессии перестаёт быть функцией `seed` + сценария + журнала оператора. Воспроизвести сессию по протоколу становится невозможно |
> | **Доказуемость протокола** | HMAC подтверждает целостность записи, но не её воспроизводимость. Оспаривание оценки становится неразрешимым: «инструктор добавил аварию, которой не было в сценарии» |
> | **Сопоставимость результатов** | Два обучаемых по одному сценарию получают разные условия → баллы несравнимы, учебная аналитика (UC-05) теряет смысл |
> | **Эталон оценки** | Эталон (`reference`) написан под набор неисправностей сценария. Внеплановая авария не имеет эталона — `assessment` не может её корректно оценить, а не только «оценит строго» |
> | **Разделение ролей** | Инструктор — «автор и судья». Автор работает **до** сессии (UC-10), судья — **после** (UC-18). Вмешательство во время сессии совмещает роли и открывает канал влияния на результат |
>
> **Что делать вместо live-инъекции:** нужную вариативность даёт **триггер по условию**. Вместо «инструктор
> увидел, что оператор справился, и добавил вторую аварию» — в сценарии заранее описывается
> `if PRSA 204 ≤ 3.0 for 120 s → inject FLT-K1-LEVEL-LOW`. Поведение адаптивное, но детерминированное
> и одинаковое для всех обучаемых.
>
> **Требуемые правки документации** — см. `DOC-FIXES.md`, раздел 1.

### UC-15. Управление модельным временем (Инструктор)

`set_speed(0.1 … 10)`:

- **0.1×–1×** — замедление для разбора медленных переходных процессов;
- **1×** — реальное время;
- **до 10×** — «перемотка» длинных участков (прогрев, выход на режим).

Реализация в `sim`: `Step(real_dt_s)` → модельное время = `real_dt_s × speed`; при больших `speed` интегратор **дробит шаг** (numpy) — чтобы численный метод не разошёлся.

**Влияние на оценку:** нормативы (`within_s`, `ack_deadline_s`) считаются в модельном времени, поэтому ускорение сокращает реальное время реакции оператора. Для экзамена скорость фиксируется сценарием.

### UC-16. Сохранение и восстановление состояния (Инструктор / система)

**Ручной save (UC-16a):**

1. Инструктор жмёт «сохранить состояние».
2. `orchestrator` → `snapshot` `POST /snapshot/save`.
3. `snapshot` выполняет **barrier на границе тика** (чтобы состояние было согласованным), забирает `GetState` (включая `internal_state_json` — полный снимок `Network.export_internal` и **seed ГПСЧ**), плюс прогресс оценки и алармы.
4. Payload → S3 (иммутабельный, сжатый), метаданные + SHA-256 → Picodata.

**Автосохранение (UC-16b):** периодический чекпоинт, частота выбрана так, чтобы потеря при обрыве была **≤3 мин**.

**Restore (UC-16c):**

1. Валидация SHA-256 **до** применения; при несовпадении — фолбэк на последний валидный снапшот.
2. `SetState(internal_state_json, model_time_s)` в `sim`.
3. Восстановление ≤15 с; продолжение **детерминированно** — благодаря сохранённому seed.

**Запрет:** в режиме **Экзамен** restore обучаемому запрещён (антифрод). Попытка фиксируется в протоколе и уходит в KUMA.

### UC-18. Оценка и переопределение (Инструктор)

**Автоматическая оценка (в течение сессии):**

1. `orchestrator` шлёт каждое действие и каждый аларм в `assessment` (`POST /assessment/event`).
2. `assessment` сравнивает с эталоном сценария: время реакции, порядок шагов, пропуски.
3. Начисляет штрафы, помечает **критические ошибки** (недопущенный HH, пропущенное ПАЗ-действие).
4. Текущий балл доступен инструктору по WS в реальном времени.

**Финальный вердикт:**

1. По остановке сессии `assessment` считает итог.
2. Разграничение: **`assessment` считает, `orchestrator` финализирует** (рекомендация из `session_orchestrator.md` §11.1).

**Аннотация ИИ (после сессии, совещательно):**

- `ai` `POST /v1/session/review` получает журнал + эталон + уже посчитанный балл;
- распознаёт **эквивалентные стратегии**: например, оператор снял давление в К-1 не восстановлением орошения (`FRC 408`), а снижением нагрева П-3 через `TRC 3` — правила скажут «шаг пропущен», ИИ предложит `suggested_score_delta`;
- поле `assessment` в ответе — **исходный, неизменённый** результат.

**Переопределение (FR-ASSESS-05):**

1. Инструктор видит предложение ИИ (или решает сам), нажимает «переопределить».
2. `POST /assessment/override` с **обязательным комментарием**.
3. Запись append-only: исходный балл, новый балл, автор, обоснование, timestamp.
4. Событие → KUMA (чувствительное: изменение результата аттестации).
5. В протоколе экзамена отражаются **обе** оценки.

### UC-19. Формирование отчёта и протокола

1. По завершении сессии `gw`/`orchestrator` публикует задачу в NATS `report.tasks`.
2. `report` (consumer) собирает данные из Picodata: `OperatorAction`, `AlarmEvent`, `FaultInjection`, `Assessment`, метаданные снапшотов.
3. Генерирует **канонический JSON** + **PDF** (WeasyPrint).
4. Подписывает канонический JSON **HMAC** (ключ из Vault; алгоритм и версия ключа пишутся в Picodata).
5. PDF → S3, метаданные + подпись → Picodata.
6. Уведомление о готовности → `fe`.

**PERF-05: ≤20 с, асинхронно** — генерация не блокирует real-time контур (INT-03).

**Исключения:** упавшая задача ретраится из очереди; при всплеске нагрузки HPA поднимает потребителей по длине очереди.

---

### UC-20. Разбор сессии: Replay + ИИ (Инструктор / Оператор)

1. Открывается запись сессии: таймлайн действий, алармов, инъекций неисправностей.
2. **Replay** воспроизводит ход по журналу (детерминизм гарантирует совпадение с оригиналом).
3. `ai` `POST /v1/session/review` → `pipeline.py` (журнал → балл → аннотации → текст):
   - `reaction_time.py` — время реакции по каждому аларму против норматива квитирования;
   - `sequence.py` — выравнивание с эталоном (LCS), различение «вовремя / не по порядку / пропущено / просрочено»;
   - `scoring.py` — авторитетный балл;
   - `debrief.py` — текст разбора (LLM), `explain.py` — «причина → следствие → рекомендация» со ссылками на регламент (RAG, BM25 + русский стемминг).
4. **TagGuard** сверяет каждый тег из ответа LLM со словарём шаблона (`data/tags_demo.json`, 65 тегов процесса + 11 команд) и **бракует ответ целиком**, если модель упомянула несуществующую позицию. Забракованный ответ заменяется детерминированным резервом.

**Деградация при отказе GPU:** структурный разбор из фактов журнала. Балл не зависит от ИИ вообще.

---

### UC-21. Справочный чат-бот (Оператор / Инструктор)

1. Обучаемый спрашивает: «какая уставка по давлению верха К-1?», «что делать при потере вакуума в К-2?».
2. `ai` `POST /v1/chat` → RAG-поиск по `data/regulation/` (BM25 со стеммингом) → LLM формулирует ответ со ссылкой на раздел регламента.
3. **Бот не имеет доступа к телеметрии** (ADR-002). Он не знает текущее давление в К-1 и потому не может выдать готовое решение — работает как открытый справочник.
4. **Фильтр на входе** (`_SOLUTION_SEEKING`) отсекает попытки выманить эталонные действия и критерии оценки — это входной фильтр, а не инструкция в промпте (инструкции обходятся переформулировкой).
5. Защита от prompt injection покрыта тестами.

**Деградация:** при отказе LLM — прямая цитата наиболее релевантного фрагмента регламента.

---

### UC-22. Адаптивный план тренировок

1. `ai` строит **профиль ошибок** обучаемого (`analysis/profile.py`) по истории сессий.
2. Формирует рекомендацию: какие блоки повторить, какие сценарии пройти, какую сложность выставить.
3. Инструктор видит рекомендацию и назначает сессии; система **не назначает** экзамен автоматически.

## Часть B. Технические потоки

### B.1. Сквозной путь запроса (действует для любого REST-вызова)

```
Браузер
  │ HTTPS
  ▼
Istio Ingress Gateway     ← сетевой вход: TLS-терминация, маршрутизация host/path
  │ mTLS
  ▼
gw (API Gateway / BFF)    ← ЕДИНСТВЕННАЯ точка проверки JWT/RBAC
  │  1. стирает входящие X-User-ID / X-Roles от клиента
  │  2. auth POST /introspect → валиден? роли?
  │  3. RBAC по маршруту, rate-limit (API ≤50/мин на endpoint)
  │  4. подставляет проверенный контекст X-User-ID / X-Roles
  │  JWT дальше НЕ идёт
  ▼ mTLS + NetworkPolicy «accept only from gw»
Внутренний сервис         ← токен не проверяет, ключ подписи не знает
```

**Почему так:** внутренние сервисы не знают ключа подписи JWT. Доверие обеспечивается тремя механизмами сразу: прикладной проверкой на `gw`, mTLS Istio и NetworkPolicy. Обязательное правило — сервис **стирает** входящие заголовки контекста и принимает их только от `gw`; иначе клиент подставил бы себе роль администратора.

### B.3. Поток «жизненный цикл сессии» — центральный сценарий системы

#### Фаза 1. Старт

```
инструктор → gw → orchestrator  POST /session/start {template_id, scenario_id, user_ids, mode}
   │
   ├─► constructor  GET /templates/{id}/export      → init state
   ├─► scenario     GET /scenarios/{id}             → неисправности + триггеры + эталон
   │                (в экзамене: GET /scenarios/exam — случайный)
   ├─► sim-manager                                  → поднять sim-worker под сессию
   ├─► sim          CreateSession(session_id, seed)
   ├─► sim          SetState(init_state)
   ├─► Picodata     запись Session (RUNNING, mode, seed, template_id, scenario_id)
   └─► broker       session.events: SESSION_STARTED
```

#### Фаза 2. Тик-цикл (1 Гц)

```
каждую секунду:
  orchestrator ──► sim  Step(real_dt_s)
                      ◄── StepResponse {
                            state: {tag_values, equipment_states, controller_modes,
                                    active_alarms, active_faults, tripped_interlocks,
                                    model_time_s, speed},
                            new_alarms, cleared_alarms, new_interlocks }
  orchestrator:
    ├─ Radix        кэш горячего состояния сессии
    ├─ WS push      → оператор (RW) и инструкторы-наблюдатели (read-only)
    ├─ Picodata     новые AlarmEvent / InterlockEvent (append-only)
    ├─ assessment   POST /assessment/event  (алармы, срабатывания ПАЗ)
    ├─ планировщик  проверка триггеров сценария (время / условие по тегу)
    └─ метрика      tick-lag → Пульт  ← ГЛАВНАЯ метрика real-time контура
```

*Открытый вопрос (`session_orchestrator.md` §11.2): опрос `sim` по одному `Step` на тик против батча — влияет на поведение при `speed = 10×`.*

#### Фаза 3. Команда оператора

```
оператор → fe → gw → orchestrator (WS/REST)
   │
   ├─ [тренировка] ai  predict_behaviour  → риск действия
   │                    ├ правило из risk_rules.json сработало → предупреждение оператору
   │                    └ отказ ИИ → заголовок правила (суть предупреждения сохраняется)
   │  [экзамен]    пропускается (FR-AI-06)
   │
   ├─► sim  Command(session_id, action, target, value)
   ├─► Picodata  OperatorAction (модельная метка времени!)
   └─► assessment  POST /assessment/event
```

#### Фаза 4. Автоматическая инъекция неисправности

```
планировщик событий в orchestrator (каждый тик):
   триггер по времени:   model_time_s ≥ trigger.at_s
   триггер по условию:   tag_values["PRSA 204"] ≥ 4.0
      │
      ▼
   orchestrator ──► sim  InjectFault(fault_id)
                       ◄── FaultInstanceMsg {fault_id, injected_at_s, magnitude, active, title, docx_ref}
   ├─► Picodata  FaultInjection (append-only)
   ├─► broker    session.events: FAULT_INJECTED  (инструктору + аудит)
   └─► WS        инструктор видит отметку на таймлайне; оператор — НЕ видит
```

**Это единственный источник вызова `InjectFault`.** Ни `fe`, ни `gw`, ни инструктор не имеют маршрута
к `sim.inject_fault` — NetworkPolicy `sim` принимает трафик только от `orchestrator` и `snapshot`,
а сам `orchestrator` вызывает `InjectFault` только из планировщика событий сценария (`FR-ROLE-04`, см. UC-14).

**Механика возмущения (ADR-СЕ-02).** Неисправность не подменяет модель, а действует на ПИ-контур одним из двух способов:

- **суммируется в `disturbance`** — контур *может* отработать, но за время переходного процесса PV пересечёт порог, если оператор не вмешается;
- **режет располагаемую мощность** (`out_max` / `supply_ok`) — контур сам не восстановится, нужны соседние «assist»-точки (АВЗ, оборотная вода, орошение).

Это ровно механика докс-сценариев: ранние признаки → немедленные действия → если ухудшается, ПАЗ.

#### Фаза 5. Алармы и ПАЗ

```
sim (interlocks.evaluate) каждый тик:
   value vs limits (H / HH / L / LL / INTERLOCK из шаблона)
      │
      ├─ пересечение H/HH/L/LL → AlarmEvent (приоритет) → в StepResponse.new_alarms
      └─ пересечение INTERLOCK → InterlockEvent + применение эффекта:
             PRSA 204   → cut_furnace_fuel + cut_k2_steam  (отсечка топлива печей + FRC 421 = 0)
             PRSA 213   → cut_furnace_fuel + cut_k2_steam
             LRCA 639/640/641 → elou_voltage_trip  (снято напряжение ИПМ, дренаж остановлен)
             LRCA 606   → safe_hold  (контур в безопасное положение)
             LRCA 4002-1→ safe_hold
             PRCA 220   → k4_relief  (воздействие на TRC 5, FR 415, PRCA 223)
             TR 1011    → catalyst_cooldown  (охлаждение катализатора ГДМ)
```

Карта эффектов — `sim_engine/physics/interlocks.py: INTERLOCK_EFFECTS`. Это **единственное** место в коде,
знающее физику блокировок разд. 3 / 7.7 регламента; новый тег с блокировкой добавляется правкой шаблона,
если его эффект укладывается в уже определённые действия.

Дополнительно: **пуск насоса блокируется**, если нарушен порог его тега-датчика (карта «насос → тег/направление/порог»
там же) — попытка пуска отклоняется движком, а не интерфейсом.

**ПАЗ срабатывает в модели автоматически** — это не «наказание», а физика защиты. Для оценки важно, *успел* ли оператор предотвратить срабатывание.

#### Фаза 6. Пауза / возобновление / остановка

```
POST /session/pause  → orchestrator останавливает тик-цикл; sim держит состояние в RAM
POST /session/stop   → orchestrator:
   ├─► assessment  финальный расчёт → вердикт
   ├─► snapshot    финальный снапшот
   ├─► sim         DestroySession → sim-manager удаляет под
   ├─► Picodata    Session → FINISHED
   ├─► broker      report.tasks (задача на протокол) + session.events: SESSION_STOPPED
   └─► ai          (async, через ai.tasks) разбор сессии
```

### B.4. Поток «оценка»

```
orchestrator ──► assessment  POST /assessment/event  (каждое действие / аларм)
                    │
                    ├─ эталон сценария (из scenario / Picodata)
                    ├─ время реакции vs ack_deadline_s
                    ├─ порядок шагов vs reference (LCS-выравнивание)
                    ├─ штрафы + отметка критических ошибок
                    └─ append-only журнал в Picodata
                          │
                          ▼
                    итог → orchestrator финализирует
                          │
                          ├─► ai  статистика ошибок (совещательная аннотация)
                          └─► broker  assessment.events → аудит
```

**Разграничение авторитета:**

| Слой | Что делает | Влияет на балл |
|---|---|---|
| `assessment` (rule-based) | Время реакции, сравнение с эталоном, штрафы, вердикт | **Да** |
| `ai` (`analysis/*`) | Те же расчёты воспроизводимо, детерминированно | **Да** (детерминированное ядро) |
| `ai` (LLM: annotate, debrief, explain) | Распознавание эквивалентных стратегий, текст | **Нет** — только `suggested_score_delta` для инструктора |
| Инструктор | Переопределение с обоснованием | **Да**, с аудитом |

### B.5. Асинхронные потоки (NATS JetStream)

| Топик | Продюсер → Потребитель | Содержимое |
|---|---|---|
| `report.tasks` | `gw` / `orchestrator` → `report` | Задача «сформировать отчёт/протокол» |
| `ai.tasks` | `orchestrator` → `ai` | Задачи инференса (разбор, генерация сценария) |
| `session.events` | `orchestrator` → `assessment`, инструктор | Старт/стоп/чекпоинт/инъекция аварии |
| `assessment.events` | `assessment` → аудит | Вердикты, переопределения |

**Зачем:** тяжёлые задачи (PDF ≤20 с, LLM-инференс) не должны стоять в real-time контуре 1 Гц (NFR-PERF-06). Гарантированная доставка + retry — на JetStream; кластер N≥3 с Raft-репликацией.

#### Сценарий 4.1 — критически высокое давление верха К-1 (`FLT-K1-PRESSURE-HIGH`) — эталонный демо-сценарий

| | |
|---|---|

**Это сквозной пример всей документации** (`make demo`, пример в README ai-service). Полный ход:

```

t~40    PRSA 204 растёт, оператор видит тренд
t=0..   AlarmEvent PRSA 204 priority=HH, value=4.6, limit=4.5
        [тренировка] ai predict_physics: «PRSA 204 достигнет 4.8 через ~90 с»
                     ai explain: «причина → следствие → рекомендация» + ссылка на регламент
        [экзамен]    403 EXAM_MODE_BLOCKED — подсказок нет
```

**Эквивалентная стратегия (ключевой кейс для ИИ).** Оператор может снять давление не восстановлением орошения через FRC 408, а снижением нагрева П-3 через **TRC 3**. Правила `sequence.py` зафиксируют «шаг 3 пропущен». ИИ распознаёт допустимую нештатную стратегию и выносит `suggested_score_delta` на решение инструктора — балл при этом **не меняется** автоматически.

## Часть D. Экзаменационный контур и антифрод

### D.1. Полный ход экзамена

```
1.  Инструктор: POST /session/start {mode: EXAM, user_id}
2.  orchestrator ──► scenario  GET /scenarios/exam
                     └ СЛУЧАЙНАЯ выдача экзаменационного сценария
                       (обучаемый не может подготовиться к конкретной аварии)
3.  orchestrator: seed фиксируется и записывается в Session
4.  sim: CreateSession(session_id, seed) + SetState(init)
5.  Режим EXAM включает ограничения:
      ai explain / predict_physics / predict_behaviour  → 403 EXAM_MODE_BLOCKED
      snapshot restore обучаемым                        → запрещён
      set_speed инструктором                            → зафиксирована сценарием
      chat                                              → по флагу KTK_CHAT_IN_EXAM
6.  Тик-цикл 1 Гц; неисправности — только автоматические по триггерам
7.  Каждое действие: OperatorAction (модельное время) → Picodata + assessment
8.  Остановка: assessment → вердикт; orchestrator финализирует
9.  broker report.tasks → report:
      канонический JSON протокола + PDF
      HMAC-подпись (ключ из Vault, алгоритм и версия ключа в Picodata)
      PDF → S3, метаданные + подпись → Picodata
10. ai (async): разбор сессии — уже ПОСЛЕ фиксации балла
11. Инструктор при необходимости: POST /assessment/override с обоснованием
      → обе оценки в протоколе, событие в KUMA
```

### D.2. Меры антифрода

| Угроза | Мера |
|---|---|
| Обучаемый заранее знает сценарий | Случайная выдача `GET /scenarios/exam` |
| Откат к моменту до ошибки | Restore обучаемому запрещён; попытка — в протокол и KUMA |
| Подсказка от ИИ | Explain / Predict отключены (FR-AI-06), `403 EXAM_MODE_BLOCKED` |
| Выманивание решения у чат-бота | Бот не видит телеметрию (ADR-002) + входной фильтр `_SOLUTION_SEEKING` + отказ раскрывать эталон и критерии |
| Подмена оценки в БД | Append-only журнал + HMAC-подпись протокола |
| Подмена результата на клиенте | Server-authoritative: клиент ничего не считает |
| Оспаривание протокола | Детерминизм: воспроизведение по seed + журналу даёт байт-в-байт тот же ход |
| Скрытое переопределение оценки | Обязательное обоснование, обе оценки в протоколе, событие в KUMA |
| Замедление модели для выигрыша времени | Скорость зафиксирована сценарием; нормативы — в модельном времени |

### D.3. Почему протокол доказуем

Три свойства вместе:

1. **Детерминизм модели** (`test_determinism_same_seed`): seed + журнал команд → тот же ход.
2. **Детерминизм оценки** (`test_score_identical_with_and_without_llm`): тот же журнал → тот же балл, независимо от доступности GPU.
3. **HMAC-подпись** канонического JSON: любое изменение обнаруживается.

Убери любое из трёх — протокол перестаёт быть аттестационным документом. Именно поэтому ИИ архитектурно отрезан от балла.

## Часть E. Сценарии отказов и деградации

### E.1. Отказ sim-worker (пода сессии)

```
sim-worker падает
  ├─ orchestrator фиксирует таймаут Step / потерю gRPC-канала
  ├─ WS клиентам: статус RECOVERING (сессия не закрыта!)
  ├─ sim-manager поднимает новый под
  ├─ snapshot: restore последнего валидного чекпоинта
  │    ├ SHA-256 проверяется ДО применения
  │    ├ при несовпадении — фолбэк на предыдущий валидный
  │    └ SetState(internal_state_json + seed + model_time_s)
  ├─ тик-цикл возобновляется, статус RUNNING
  └─ отметка инцидента в журнале сессии и протоколе
```

**Гарантии:** restore ≤15 с (PERF-03); потеря прогресса ≤3 мин (частота чекпоинтов).
**Изоляция:** per-session под (ARCH-08) — другие 49 сессий не затронуты.

### E.2. Отказ AI Service (GPU)

Падение ИИ **не останавливает ничего**. Предохранитель (`resilience/`, порог `KTK_BREAKER_FAILURES=5`) размыкает цепь, каждый сценарий уходит в резерв:

| Сценарий | Резерв при отказе GPU |
|---|---|
| Explain | Карточка уставок и блокировок из словаря тегов |
| Чат-бот | Прямая цитата наиболее релевантного фрагмента регламента |
| Оценка риска действия | Заголовок сработавшего правила (суть предупреждения сохраняется) |
| Разбор сессии | Структурный разбор из фактов журнала |
| **Балл** | **Не зависит от ИИ вообще** |
| Прогноз уставки | Не использует LLM вообще (взвешенная линейная регрессия по тренду) |
| Генерация сценария | Недоступна; ручное создание работает |

Дедлайн вызова Explain — `KTK_EXPLAIN_DEADLINE_S=12`; превышение = отказ, уход в резерв.

### E.3. Отказ LLM-ответа по содержанию (галлюцинация)

Не отказ инфраструктуры, а отказ качества — обрабатывается отдельно:

```
LLM вернул ответ
  └─ TagGuard: каждый упомянутый тег сверяется со словарём шаблона
       ├ все теги существуют → ответ отдаётся
       └ есть выдуманный тег → ответ БРАКУЕТСЯ ЦЕЛИКОМ (не правится!)
            └ подставляется детерминированный резерв
```

Плюс контроль ПДн (`validation/`) — псевдонимизация перед отправкой в модель.

### E.4. Отказ Picodata

Raft-кластер, автоматический failover **<30 с** без внешнего Patroni. В окне переключения `orchestrator` продолжает тик-цикл (горячее состояние в Radix), запись журналов буферизуется и досылается.

### E.5. Отказ клиента / обрыв связи

```
браузер закрылся или сеть пропала
  ├─ сессия на СЕРВЕРЕ продолжается (server-authoritative)
  ├─ модель тикает, неисправности срабатывают по расписанию
  ├─ при переподключении: fe получает полное состояние из Radix и продолжает
  └─ обрыв ≤3 мин — прогресс не теряется (серверный чекпоинт)
```

*Открытый вопрос (`session_orchestrator.md` §11.3): держать ли ленту телеметрии в Radix как буфер на время обрыва.*

### E.6. Отказ Reporting / переполнение очереди

Задачи персистентны в JetStream, упавшие ретраятся. HPA поднимает потребителей `report` по длине очереди. Real-time контур не затронут — это и есть цель асинхронности (INT-03).

### E.7. Отказ `gw`

Единственная точка входа защищается PDB (`minAvailable ≥ 1`), N≥2 репликами и HPA. Rolling / Blue-Green обновление без даунтайма (readiness/healthz).

### E.8. Сводная таблица отказов

| Инцидент | Влияние на сессию | Влияние на другие сессии | Восстановление |
|---|---|---|---|
| `sim-worker` упал | Пауза RECOVERING | Нет | ≤15 с, restore из чекпоинта |
| `ai` упал | Нет подсказок, нет текста разбора | Нет | Автоматически при возврате GPU |
| Picodata primary упал | Буферизация записи | Все — то же | Raft failover <30 с |
| `orchestrator` упал | Реконнект WS | Реплики продолжают | Stateless, состояние в Radix/Picodata |
| `broker` нода упала | Нет | Нет | Raft JetStream, N≥3 |
| Браузер закрылся | Нет (сервер считает) | Нет | Переподключение |
| Обрыв связи ≤3 мин | Прогресс сохранён | Нет | Переподключение |
| LDAP недоступен | Новые входы невозможны | Активные сессии живут | Восстановление LDAP |

## Часть F. Сценарии информационной безопасности

### F.1. Попытка подделки контекста пользователя

```
Клиент шлёт: X-User-ID: admin, X-Roles: ADMIN
  ▼
gw: ИГНОРИРУЕТ/перезаписывает эти заголовки после проверки JWT
  ▼
внутренний сервис: обязан СТИРАТЬ входящие X-User-ID / X-Roles
                   и принимать их только от gw
  ▼
+ NetworkPolicy «accept only from gw» — прямой запрос к сервису не дойдёт
+ mTLS Istio — подделка источника невозможна
```

Три независимых механизма: прикладной (`gw`), сетевой (NetworkPolicy), криптографический (mTLS).

### F.2. Попытка обращения к внутреннему сервису напрямую

NetworkPolicy каждого сервиса разрешает вход только от определённых источников:

| Сервис | Принимает от |
|---|---|
| `auth` | только `gw` |
| `constructor` | `gw`, `scenario`, `orchestrator` |
| `scenario` | `gw`, `orchestrator` |
| `assessment` | `gw`, `orchestrator` |
| `snapshot` | только `orchestrator` |
| `sim` | только `orchestrator` / `snapshot` |
| `ai` | только `orchestrator` / `assessment`; **egress запрещён полностью** |

### F.3. Изоляция OT-сети (FR-ISO-01/02/03)

| Правило | Реализация |
|---|---|
| Нет интеграций с реальными АСУ ТП / SCADA / ОПС / Modbus | Промышленные протоколы не реализованы вообще |
| Все теги порождает только `sim` | FR-ISO-03; нет иных источников телеметрии |
| Egress в OT-сеть запрещён | Firewall VKCloud на периметре + Istio Egress Gateway |

Тренажёр физически не может воздействовать на реальное производство.

### F.4. Утечка данных через ИИ

| Вектор | Мера |
|---|---|
| Модель обращается наружу | **Egress запрещён** для `ktc-ai`; изолированный serviceAccount |
| ПДн уходят в промпт | Псевдонимизация (`validation/`), минимизация ПДн |
| Prompt injection через чат | Входной фильтр + тесты на инъекции |
| Модель раскрывает эталон/критерии | Фильтр `_SOLUTION_SEEKING` на входе, а не инструкция в промпте |
| Подмена весов модели | Модели из доверенного репозитория, версионирование (открытый вопрос `ai_service.md` §11.4) |

### F.5. Rate-limiting и защита прикладного уровня

| Уровень | Лимит |
|---|---|
| Авторизация | ≤10 запросов/мин |
| API-endpoint | ≤50 запросов/мин на пользователя/сессию |

Плюс CSP и защитные заголовки, прикладная защита от SQLi/XSS/CSRF на маршрутах `gw`, JSON Schema-валидация входных данных.

### F.6. Целостность учебного контента

| Объект | Механизм |
|---|---|
| Шаблон установки | SHA-256 |
| Сценарий | SHA-256, событие изменения → KUMA |
| Снапшот | SHA-256, проверка **до** применения; HMAC для экзаменационных |
| Журнал оценки | Append-only + HMAC |
| Протокол экзамена | HMAC-подпись канонического JSON (в Target — ГОСТ/КриптоПро) |

### F.7. Что попадает в KUMA

Вход и отказ входа, ошибки 2FA, изменения ролей, изменения сценариев, операции save/restore (антифрод), переопределения оценок, формирование и подпись протоколов, срабатывания rate-limit, ошибки авторизации.

### G.3. Полный перечень состояний сессии

| Состояние | Переход из | Триггер | Что происходит |
|---|---|---|---|
| `CREATED` | — | `POST /session/start` | Конфигурация собрана, под ещё не поднят |

| `RUNNING` | INITIALIZING, PAUSED, RECOVERING | автоматически / `POST /resume` | Тик-цикл 1 Гц активен |
| `PAUSED` | RUNNING | `POST /session/pause` | Тик остановлен, состояние в RAM `sim` |
| `RECOVERING` | RUNNING | отказ `sim-worker` | Новый под + restore из чекпоинта |
| `FINISHED` | RUNNING, PAUSED | `POST /session/stop` | Вердикт, финальный снапшот, задача на протокол, под удалён |
| `FAILED` | любое | неустранимый сбой | Инцидент в журнал, частичный протокол с отметкой |
