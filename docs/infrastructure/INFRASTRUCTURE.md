## 1. Назначение и место документа

Данный документ описывает **инфраструктуру развёртывания и эксплуатации** платформы «Конструктор КТК» — компьютерного тренажёрного комплекса с цифровым двойником установки ЭЛОУ-АВТ.

Документ является целевым Deliverable по критерию **«Инфраструктура (Проект)»** (вес 0,1) и детализирует инфраструктурные аспекты, заложенные в:

- `architecture/ARCHITECTURE.md` — общая архитектура и слои;
- `SRD-Конструктор-КТК.md` — нефункциональные требования (NFR-PERF/REL/SCL/SEC/COMP), §7.9 «Развёртывание на Deckhouse»;
- `security/Требования_ИБ_v2.md` — требования ИБ к аппаратной/программной части и сетям;
- `Сводный_документ_для_презентации.md` — `Раздел 5. Требования к инфраструктуре`, оценка нагрузки.

**Целевые характеристики (зафиксированы):**
- до **50 одновременных сессий** (пиковая нагрузка, SRD `NFR-PERF-03`);
- расчётная рабочая нагрузка **10 активных сессий** (5–10 обучаемых + до 3 инструкторов);
- телеметрия **≥ 1 Гц**, отклик UI **≤ 500 мс** (целевой 300 мс);
- коэффициент готовности **98%** во время учебных смен (`NFR-REL-04`);
- готовность к развёртыванию **On-premise (учебный класс)** и в **частном облаке ВК Cloud** с возможностью удалённого доступа инструкторов.

## 2. Тип и топология инфраструктуры

### 2.1. Тип инфраструктуры

**Серверная (централизованная) инфраструктура на базе K8s-кластера** в частном облаке **ВК Cloud** (российская платформа виртуализации, гипервизор доверенного типа — ВК Cloud / Zvirt / Arena). Это обосновано:

1. **Server-authoritative** моделью (`ARCH-02`, `NFR-SEC-03`) — источник истины (Simulation Engine, оценка, телеметрия) находится на сервере; клиенты — «тонкие» браузеры.
2. **Отказоустойчивостью** — централизованное резервирование ключевых компонентов (кластер БД, N≥2 реплики stateless-сервисов) невозможно на локальных рабочих местах.
3. **Масштабируемостью** (`NFR-SCL-01/02`) — по числу сессий и пользователей линейно расширяется кластер без переработки.
4. **обособленностью GPU-ресурсов** для ИИ-модуля.

### 2.2. Топология (логическая)

Одна логическая платформа разворачивается на двух уровнях размещения:

```
┌────────────────────────────────────────────────────────────┐
│  ЯДРО ПЛАТФОРМЫ — ВК Cloud (управляемый кластер)            │
│                                                            │
│  K8s-кластер (Deckhouse / Astra Linux SE 1.8)              │
│  ├── Логический кластер A (основной ЦОД)                   │
│  └── Логический кластер B (резервный / георезерв)          │
│                                                            │
│  Внешняя граница: Firewall VKCloud (VPC/подсети),          │
│  Istio Ingress Gateway (TLS 1.2+), Angie (BFF)             │
└────────────────────────────────────────────────────────────┘
        │  HTTPS (443) + WebSocket (1 Гц)
        ▼
┌────────────────────────────────────────────────────────────┐
│  КЛИЕНТСКИЙ СЛОЙ                                            │
│  АРМ оператора (учебный класс / корпоративные ПК)           │
│  Консоль инструктора / Администратора / Наблюдатель         │
└────────────────────────────────────────────────────────────┘
```

### 2.3. Namespace и Node Pool сегментация (из SRD §7.9)

| Namespace | Назначение | Node Pool | QoS / специализация |
|---|---|---|---|
| `ktc-app` | Stateless-сервисы (`gw`, `auth`, `constructor`, `scenario`, `orchestrator`, `assessment`, `report`, `snapshot`, `fe`) | `app` | general purpose, HPA по CPU/memory, N≥2 |
| `ktc-sim` | Simulation Engine (`sim-manager`, `sim-worker-*`) | `sim` | CPU-intensive, guaranteed QoS для 1 Гц |
| `ktc-ai` | AI Service (GPU) | `ai` | GPU, taint + nodeSelector, isolated serviceAccount |
| `ktc-data` | Picodata, Radix, S3/MinIO | `db` | SSD-optimized, anti-affinity across hypervisors |
| `ktc-obs`/`ktc-infra` | Observability + инфраструктура (Пульт, Графиня, Fluent Bit, NATS) | `app` | сквозные |

## 3. Обоснование выбора (локальная vs серверная)

| Критерий | Локальная (на АРМ) | **Серверная (выбранная)** |
|---|---|---|
| Расчёт мат. модели ≥1 Гц | Недостаточно ресурсов на учебном ПК; рассинхронизация сессий | Централизованный `sim`, гарантированные ресурсы |
| Масштабирование до 50 сессий | Неприменимо | Линейное по числу сессий/подов |
| Отказоустойчивость и резервирование | Нет | Кластер БД, HPA, георезерв |
| ИБ (изоляция OT, единый периметр) | Сложно обеспечить | Firewall VKCloud + Istio + NetworkPolicy |
| ИИ-модуль (GPU) | Нет GPU на АРМ | Обособленный GPU-node pool |
| Удалённый доступ инструкторов | Нет | Через ВК Cloud (отечественный) |
| Переносимость на On-premise учебный класс | — | Поддерживается укрупнённой схемой без потери совместимости |

**Вывод:** для КТК выбрана **серверная инфраструктура** с целевой микросервисной архитектурой в K8s (Deckhouse). Для прототипа допустима **укрупнённая схема** (backend + обособленный ИИ-модуль) без потери совместимости с целевой. Возможен вариант развёртывания одного из кластеров On-premise в учебном классе предприятия (см. §10).

## 4. Вычислительные ресурсы

### 4.1. Расчётная оценка нагрузки

Базой является целевая нагрузка **10 активных сессий** (5–10 обучаемых + до 3 инструкторов), пиковая — **50 сессий** (`NFR-PERF-03`). Каждая сессия — изолированный `sim-worker` под (1 сессия = 1 под).

### 4.2. Профили ресурсов по компонентам

| Компонент | vCPU | RAM | Хранилище | Примечание |
|---|---|---|---|---|
| Backend / Orchestrator | 4 | 8 ГБ | SSD | Горизонтальное масштабирование (HPA), N≥2 |
| Simulation Engine (`sim-worker`, 1 под/сессия) | 2 | 4 ГБ | SSD | Deterministic, guaranteed QoS; до 50 подов |
| AI Service | 4 | 8 ГБ (лимит 2 ГБ/анализ) | SSD + GPU VRAM | Обособленный модуль, GPU pool |
| Picodata (СУБД + Radix кэш) | 8 | 32 ГБ | SSD (высокий IOPS) | Raft-кластер N≥3, anti-affinity |
| S3 / MinIO | 4 | 8 ГБ | HDD/SSD (большой объём) | Снапшоты, PDF-отчёты, иконки |
| NATS JetStream | 2 | 4 ГБ | SSD | N≥3, PV |
| Angie (BFF) / Gateway | 2 | 4 ГБ | SSD | Точка входа, WS-прокси |

### 4.3. Node Pools и выделение ресурсов

| Node Pool | Состав | Ресурсы (ориентировочно) | Особенности |
|---|---|---|---|
| `app` | stateless-сервисы | vert: 2 vCPU / 4 ГБ | HPA по CPU/memory |
| `sim` | Simulation Engine | vert: 2 vCPU / 4 ГБ на сессию | guaranteed QoS, taint `sim=true` |
| `ai` | GPU-хост | 1×GPU (сертиф. отечеств. или NVIDIA), 8–16 ГБ VRAM | taint + nodeSelector, egress запрещён |
| `db` | Picodata/Radix/MinIO | vert: SSD, high IOPS | anti-affinity, разные гипервизоры |

**Квоты и лицензии (зависимости):** доступ к ВК Cloud, квоты на GPU (закладываются заранее), дистрибутив Deckhouse (community/enterprise), лицензия Picodata, лицензия Пульт + Графиня.

### 4.4. Хранилища данных

| Хранилище | Технология | Роль | Объём/метрики |
|---|---|---|---|
| СУБД | Picodata (PG-wire, Raft) | Сессии, оценки, журналы, шаблоны (JSONB) | Failover < 30 с |
| Кэш | Radix (Redis-совм.) | Горячее состояние сессий, JWT-кэш | Мгновенный доступ |
| Объектное | S3/MinIO | Снапшоты, PDF, иконки | ≥ 10 000 снапшотов (`NFR-SCL-03`) |

## 5. Требования к рабочим местам

### 5.1. АРМ обучаемого (оператор)

| Параметр | Минимальное требование |
|---|---|
| Платформа | Веб-клиент, браузер Chromium-based (в т.ч. Яндекс.Браузер, `NFR-COMP-01`) |
| Сетевое подключение | Только HTTPS (порт 443) + WebSocket; доступ к ВК Cloud / On-premise |
| ПЗУ | − (тонкий клиент) |
| Видеокарта | Любая современная (мнемосхема рендерится на сервере/CS-модель) |
| Доп. | Двухэкранная конфигурация для АРМ оператора (обзорный + рабочий, `FR-HMI-08`) |
| ИБ | Антивирус (Kaspersky Endpoint Security / Dr.Web), очистка кэша после сессии, блокировка USB-накопителей (по политике) |

### 5.2. Узел управления (инструктор/администратор)

| Параметр | Требование |
|---|---|
| Роль | Создание/редактирование шаблонов и сценариев — только с узла управления |
| Доступ | HTTPS (443); 2FA (TOTP) для инструктора/админа; привилегированный доступ через отечественный PAM |
| АРМ | Полноценный десктоп/браузер для конструктора (canvas) и наблюдения |

### 5.3. Учебный класс (опционально, On-premise)

- Видеонаблюдение, закрытие на ключ в нерабочее время;
- Программная блокировка USB-масс-устройств на учебных ПК;
- Локальная сеть класса подключается к ядру платформы только по HTTPS.

## 6. Сетевое взаимодействие и задержки

### 6.1. Требования по задержкам (исключение рассинхронизации)

Главное требование к сети — **исключение рассинхронизации** телеметрии 1 Гц между моделируемым состоянием и отображением на АРМ.

| Контур | Требование по задержке | Обоснование |
|---|---|---|
| Браузер ↔ Gateway (REST + WS) | ≤ 500 мс отклик UI (цель 300 мс) | `NFR-PERF-01` |
| Telemetry WS (1 Гц) | jitter-устойчивость; буфер 1 сек | `NFR-PERF-02` |
| Gateway ↔ Microservices (gRPC/mTLS) | < 10 мс внутри кластера | совместное размещение node pools |
| Orchestrator ↔ Sim (`step`) | < 10 мс | детерминированность тика |
| Sim ↔ Picodata / Radix | < 5 мс (Radix кэш) | горячее состояние |

**Обеспечение:** совместное размещение node pools в одном ЦОД/локации, RADIX для горячего состояния (без обращения к БД на каждый тик), WebSocket-push с серверным источником истины (`ARCH-02`). Ограничения по задержкам **заданы и проверяются** профилированием трафика WS (`NFR-PERF-02`).

### 6.2. Сетевые сегменты и firewall

```
[ Клиентский слой ] ──HTTPS/WSS 443──► [ Firewall VKCloud: VPC/подсети ]
                                            │
                                           ▼
                              [ Istio Ingress Gateway (TLS 1.2+) ]
                                            │
                                     [ Angie BFF / gw ]
                                            │ mTLS (gRPC/REST)
                              [ Microservices: app │ sim │ ai ]
                                            │ NetworkPolicy
                              [ Picodata │ Radix │ MinIO ]
```

| Граница | Средство | Что закрывает |
|---|---|---|
| Периметр кластера (внешний) | **Firewall VKCloud** (VM между плашками) | Входящий трафик на Ingress (443), egress к LDAP/AD/PAM, защита control-plane K8s |
| Внутри кластера | **Istio** (istio-proxy sidecar, mTLS) + **NetworkPolicy** («accept only from gw») | Трафик между слоями, межсервисный, запрет egress в OT |
| Изоляция OT (`ARCH-03`) | Нет маршрутов/egress в OT-сеть | Связь с АСУ ТП/ПЛК/OPC/Modbus — **запрещена** |

**Требование to_do (VK Cloud):** между виртуальными машинами на ВК Cloud устанавливается **плашка firewall** (сегментация VPC/подсетей), разделяющая внешний (Ingress) и внутренний (Egress к внешним системам) контуры. Межсервисную изоляцию обеспечивают Istio + NetworkPolicy (отдельный сетевой firewall между `ktc-app` и `ktc-sim`/`ktc-ai`/`ktc-data` не требуется).

### 6.3. Сетевые политики K8s

- NetworkPolicy: межсервисный трафик только по разрешённым gRPC-портам;
- Ingress наружу — только Angie (443);
- Egress: разрешён только к LDAP/AD и PAM; к OT-сети — **запрещён**;
- AI Service: egress **полностью запрещён** (изолированный serviceAccount).

## 7. Отказоустойчивость и непрерывность сессий

### 7.1. Матрица отказоустойчивости

| Инцидент | Поведение | Требование |
|---|---|---|
| Падение `sim` (сессии) | Авто-перезапуск + restore из чекпоинта; другие сессии не страдают (per-session под) | `NFR-REL-05` (≤15 с) |
| Kill Picodata primary | Raft failover на реплику | `NFR-REL-01` (< 30 с) |
| Падение AI-хоста | **Деградация**: тренировка и rule-based оценка продолжаются | `NFR-REL-03` |
| Падение клиента (браузера) | Сессия продолжается на сервере (server-authoritative) | `ARCH-02` |
| Обрыв связи ≤ 3 мин | Прогресс сохраняется серверным чекпоинтом, клиент переподключается | `NFR-REL-02` |

### 7.2. Резервирование ключевых компонентов

| Компонент | Резервирование |
|---|---|
| Stateless-сервисы | HPA, N≥2 реплики (Deckhouse) |
| Picodata | Raft-кластер N≥3, реплики на разных гипервизорах/узлах |
| Simulation Engine | Per-session поды; перезапуск + restore ≤15 с |
| СУБД (непрерывность) | Реплика с переключением без остановки (< 30 с), `REL-03` |
| Снапшоты | Автосохранение (чекпоинт) ≤3 мин защита от обрыва; метаданные в Picodata, payload в S3 (SHA-256) |
| Резервное копирование | Ежедневно, хранение 365 дней, off-site копия (ИБ требование) |

### 7.3. Непрерывность сессий

- Периодические серверные чекпоинты состояния (модель, контуры, алармы, прогресс оценки, модельное время);
- Восстановление (restore) ≤ 15 с, детерминированно (включая ГПСЧ);
- Обрыв связи ≤ 3 мин — прогресс не теряется;
- В экзаменационном режиме restore ученику **запрещён** (антифрод).

## 8. Обособленные ресурсы ИИ-модуля

ИИ-модуль вынесен на **отдельные вычислительные ресурсы** (обособленный node pool `ai` с GPU), что соответствует критерию «определены обособленные ресурсы для модуля ИИ»:

- **Обособленность:** отдельный namespace `ktc-ai`, nodeSelector + taint, изолированный serviceAccount, собственные лимиты CPU/RAM/GPU (ResourceQuota/LimitRange);
- **Деградация:** падение ИИ не останавливает симуляцию и rule-based оценку (`NFR-REL-03`);
- **Безопасность:** egress запрещён, контроль целостности модели (SHA-256), версионирование, rollback без остановки, мониторинг дрейфа;
- **Масштабирование:** GPU-пул для Explain/Predict/Adaptive (vLLM/Ollama, PyTorch);
- **ПДн:** минимизация и псевдонимизация данных.

## 9. Мониторинг и аналитика

### 9.1. Сбор метрик и логов

| Функция | Средство | Что контролируется |
|---|---|---|
| Метрики | **Пульт** (Prometheus-совм.), node-exporter, экспортеры | tick-lag, WS-подключения, CPU/GPU, Raft-статус, latency |
| Логи | **Fluent Bit** (DaemonSet) → **Пульт/Графиня** | Логи сервисов, ошибки, аудит |
| Дашборды | **Графиня** (Grafana-совм.) | Дашборды по слоям, алерты |
| SIEM | **Kaspersky KUMA** | Корреляция событий ИБ, аудит |

### 9.2. Аналитика системы

- **Метрики производительности:** отклик UI (≤500 мс), частота телеметрии (≥1 Гц), задержки передачи данных, загрузка CPU/RAM/GPU;
- **Метрики сессий:** активные/завершённые сессии, частота ошибок, время входа в экзамен;
- **Аналитика обучения:** статистика ошибок операторов, качество сценариев (для АI-адаптации);
- **Аудит ИБ:** аутентификация, изменения сценариев/моделей, действия администратора, запуск/остановка сессий, экспорт данных — хранение ≥ 1 года (365 дней), write-once журнал + контрольные хеши.

**Алерты:** аномалии доступности/нагрузки (SNMP-мониторинг), дрейф ИИ-модели → оповещение администратора, события ИБ → KUMA → реагирование на инциденты.

## 10. Георезервирование

Для обеспечения высокой доступности предусмотрено **георезервирование** на уровне двух логических кластеров:

- **HaProxy** устанавливается на **отдельной виртуальной машине** (frontend-балансировщик) и обеспечивает переключение трафика между основным и резервным кластерами;
- **Picodata** обеспечивает **Master/slave** инфраструктуру: при выходе из строя основного узла/ЦОД реплика перехватывает нагрузку (failover < 30 с, `NFR-REL-01`);
- **Отказоустойчивость БД:** реплики на разных гипервизорах/узлах, активная репликация (кластер), автоматический failover без остановки пользователей;
- Снапшоты и резервные копии выкладываются в **off-site** хранилище (другой ЦОД/локация).

> Это реализует пункт 2 планирония (`to_do`): «георезервирование — HaProxy на отдельной ВМ, Picodata обеспечит Master/slave».
