# Компонент: Picodata — система управления базами данных (СУБД)

> Слой: Данных — `ktc-data` | Это: отечественная распределённая СУБД (PG-совместимая) | Доступ: `picodata:<port>` (PG-wire)

## 1. Назначение

**Picodata — «единый источник правды»** для всего, что должно сохраняться навсегда:
учебная библиотека (шаблоны, графы, сценарии, компоненты), сессии, журналы действий
и аварий, оценки, протоколы экзаменов, пользователи, метаданные снапшотов. В отличие
от Radix (горячее состояние) и MinIO (крупные объекты), Picodata хранит **историю и
ядро бизнес-данных** системы.

## 2. Почему именно Picodata (обоснование выбора)

| Требование | Как закрывает Picodata |
|---|---|
| **Отечественность** (ARCH-06) | Сертификат ФСТЭК УД4, входит в РРПО — применима в контуре КИИ |
| **Совместимость** | PostgreSQL-совместимый wire-протокол (PGPROTO) — работают стандартные клиенты (asyncpg, psql, драйверы Go/Java) |
| **Отказоустойчивость из коробки** | Raft-репликация встроена, не нужен внешний Patroni; failover < 30 с через сервисное имя кластера |
| **Операции** | Минимализм администрирования за счёт встроенной репликации |
| **Транзакции** | С версии 26.1 (март 2026) — поддержка транзакционного выполнения запросов |
| **Единый вендор** | С Radix (кэшем) один вендор — упрощает поддержку всего слоя данных |

## 3. Использование в коде

Picodata используется как **PostgreSQL-совместимая БД** — все сервисы подключаются
через стандартный драйвер `pgx/v5` (`github.com/jackc/pgx/v5`) к DSN, например в
`orchestrator` — `internal/repository/postgres.go`, `session_repo.go`.

| Сервис | Что хранит в Picodata |
|---|---|
| `auth` | пользователи, роли, профили (пароли **не** хранятся — они в LDAP) |
| `constructor` | библиотеку компонентов (`component_types`), шаблоны установок (граф в JSONB) |
| `scenario` | сценарии, каталог неисправностей, эталоны оценки |
| `orchestrator` | сессии, журналы действий/аварий/неисправностей (append-only), чекпоинт-метаданные |
| `assessment` | оценки, критические ошибки, переопределения |
| `snapshot` | метаданные снапшотов (payload — в MinIO) |
| `report` | метаданные отчётов и подписи протоколов (PDF — в MinIO) |

## 4. Ключевые сущности (ДАННЫЕ)

| Сущность | Что хранит |
|---|---|
| User / Role | пользователи, роли (учётки/роли из LDAP, read-only) |
| ComponentType | типы оборудования: порты, параметры, модель |
| InstallationTemplate | граф установки (nodes/edges/layout) в **JSONB** |
| Scenario | сценарий + триггеры неисправностей + эталоны |
| Session | метаданные сессии (режим, скорость, статус) |
| AlarmEvent / OperatorAction / FaultEvent | **append-only** журналы аварий и действий |
| Assessment | оценки, штрафы, переопределения |
| ExamProtocol | протокол экзамена (канонический JSON + HMAC-подпись) |
| Snapshot | метаданные снапшотов (payload — в S3) |

## 5. Ограничение совместимости (важно для разработки)

> Системные каталоги PostgreSQL (`pg_catalog`) в Picodata реализованы **частично**.
> ORM-инструменты, использующие интроспекцию (`reflection` в SQLAlchemy), требуют
> адаптации. Рекомендуется: **raw SQL / query builder без reflection**, миграции —
> скриптами (не Alembic autogenerate).

## 6. Размещение

- Отдельный слой данных `ktc-data`, изолированная сеть и node pool (`db`, SSD,
  anti-affinity между репликами).
- Пишут только прикладные сервисы `ktc-app`/`orchestrator`; доступ — mTLS +
  NetworkPolicy «accept only from gw» / внутренние сервисы.

## 7. Объекты Kubernetes

| Объект | Описание |
|---|---|
| StatefulSet `picodata` | кластер СУБД (Raft-репликация) |
| Service `picodata` | ClusterIP (PG-wire) |
| PersistentVolume(s) | данные реплик на SSD |
| Secret | учётные данные admin |

## 8. Метрики (в Пульт + Графиня)

- Статус Raft / failover, лаг репликации.
- Запросы/сек, задержка запросов, число соединений.
- Размер БД, рост таблиц, append-only журналы.
- Загрузка CPU/диска базы.

## 9. Отказоустойчивость / масштабирование

- Raft-репликация из коробки: kill primary → failover < 30 с (NFR-REL-01, TEST-07).
- Масштабирование чтения — реплики; запись — на основном (в рамках Raft).
- Горизонтальное масштабирование stateless-сервисов — HPA (N≥2), БД — по
  согласованной схеме Пикодаты.

## 10. Открытые вопросы

1. Размер кластера Picodata (число реплик) и схема масштабирования записей.
2. Стратегия бэкапов/восстановления БД.
3. Унификация namespace (`ktk-*` в SRD vs `ktc-*` в сервисных доках).
