# Математическая модель sim-engine: учитываемые законы и roadmap усиления

> Документ для комитета. Описывает, какие физические/инженерные законы реально
> учитывает текущая модель (уровень L1), где именно в коде они реализованы, какие
> упрощения приняты, и **дорожную карту** (roadmap) усиления модели до целевого L3.
>
> Смежные документы: `sim_math_model.md` (общее ТР), `sim_worker.md`, `sim_manager.md`.

---

## 1. Важное вступительное уточнение

- **Документация заявляет** полную ODE-модель с балансами массы и энергии
  (`sim_math_model.md` §3.1).
- **Фактический код** (уровень L1) реализует **упрощённую** параметрическую модель
  «ПИ-контур + возмущение», где физика входит как **возмущение/ограничение**, а не
  как явно записанные уравнения балансов.
- Это **осознанное инженерное упрощение уровня L1** (ADR-СЕ-01/02), а не дефект.
  Уровень L3 (строгая термодинамика) — точка расширения через тот же Model API.

Ниже — конкретный перечень законов, которые сейчас действительно учитываются,
с указанием файлов в коде, чтобы комитет мог сверить.

## 2. Законы, учитываемые в текущей модели (L1)

### 2.1. Динамика объекта 1-го порядка (инерция) — `physics/units.py:ControlLoop.step`
```
pv += (target - pv) / tau_s * dt
```
- PV (давление, уровень, температура) **асимптотически стремится** к равновесной
  точке с постоянной времени `tau_s`.
- Моделирует **инерционность реального объекта** (ёмкость, теплообмен, гидравлика).
- Является базовой парадигмой всей модели: любой контур — апериодическое звено.

### 2.2. Закон автоматического регулирования (ПИ-регулятор) — `units.py:_controller_output`
```
error = setpoint - pv
raw   = kp*error + ki*∫error·dt
out   = clamp(raw, out_min, out_max)      // с anti-windup
```
- Пропорционально-интегральный закон управления: удержание PV у уставки.
- Интегральная составляющая **устраняет статическую ошибку** (это и есть условие
  устойчивого номинального режима).
- Anti-windup не даёт накапливать интеграл при насыщенном выходе (реалистичное
  поведение промышленного регулятора).

### 2.3. Тепловой баланс подогревателя (печи) — `units.py:FurnaceLoop.step`
```
COT_цель = base_temp_in + k_duty * fuel_output / max(flow_pv, flow_floor)
```
- Температура на выходе = температура входа + прирост от топлива, **делённый на
  расход сырья**.
- Законы теплопередачи/теплового баланса: при том же топливе и **меньшем расходе**
  температура растёт (физически корректно — сценарии 2.1/3.1).

### 2.4. Гидравлическая (расходная) характеристика насоса — `units.py:Pump`
```
flow = nominal_flow_m3h * flow_multiplier   // 0 при останове/аварии
```
- Линейная характеристика по номинальному расходу.
- Останов/авария насоса → **нулевой расход** (потеря потока).

### 2.5. Потоковый (материальный) баланс на уровне связей — `physics/network.py`
```
disturbance[loop] += Σ gain·(assist - nominal)          // связи assist→контур
LRCA 602 (уровень куба К-1) += -K1_DRAW_COUPLING·(отбор печей - номинал)
```
- Закон **сохранения массы/потока** между узлами: изменение расхода на одном узле
  влияет на уровень/давление соседнего.
- Пример: отбор нефти из куба К-1 в печи снижает уровень К-1 (реальная физика
  разд. 3, а не эффект неисправности).

### 2.6. Внешние энерго/массовые возмущения — `disturbance`
- Всё, что код называет `disturbance`, — это **внешние притоки/оттоки энергии,
  массы, давления**: тепловой приток, недостаточная конденсация, потеря сырья и т.д.
- Это вклад в баланс энергии/массы **без явной записи самих балансов** (упрощение L1).

### 2.7. Закон расхода аварийного запаса (воздух КИП) — `units.py:InstrumentAirBuffer`
```
remaining_s -= dt·consumption_rate    // при потере питания; при 0 → fail-safe
```
- Моделирует «часовой запас» воздуха КИП (А-6) и переход в безопасное состояние
  при его исчерпании.

### 2.8. Пороговая логика сигнализаций и ПАЗ — `physics/interlocks.py`
```
H/HH/L/LL: PV >=/<= порог → событие     // пороги — из шаблона (данные)
INTERLOCK → эффект (отсечка топлива, safe-hold, снятие напряжения ИПМ)
```
- Законы **предохранительной защиты** (ПАЗ/ППК): превышение уставки → сброс/отсечка.
- Логика — инженерно-регламентная (разд. 3, 7.7), пороги — данные, а не код.

### 2.9. Механика неисправностей — `faults/engine.py`
Неисправность **не подменяет модель**, а возмущает существующую физическую сеть:
- **мягкая**: `disturbance` (контур в принципе может отработать, но PV успевает
  пересечь порог — «ранние признаки»);
- **жёсткая**: переопределение параметра (`out_max`/`out_min`/…) — располагаемая
  мощность контура режется, сам он не восстановится (нужны «assist»-точки: АВЗ,
  оборотная вода, орошение, подача сырья).
- Режимы эффектов: `SET` / `MULTIPLY` / `ADD` — с плавным нарастанием `ramp_s`.

## 3. Честная оценка для комитета: что НЕ реализовано на L1

| Заявлено (`sim_math_model.md` §3.1) | В коде L1 | Статус |
|---|---|---|
| Баланс массы колонн/ёмкостей явными ODE | сведён к «контур + возмущение» | упрощено |
| Баланс энергии (теплопередача) | моделируется через `FurnaceLoop` (отношение топливо/расход) | упрощено |
| Гидравлическое сопротивление/характеристики | только линейная характеристика насоса + связи | упрощено |
| Термодинамика фаз (кипение, конденсация, состав) | **отсутствует** на L1 | точка расширения L3 |
| Строгий численный solver (BDF/odeint) | явный Эйлер с под-шагами | упрощено (детерминизм приоритетен) |

**Вывод:** текущая L1 даёт **качественно корректную динамику** (тренды, аварии,
реакции оператора), приоритетно обеспечивая **детерминизм** (идентичный результат
при одинаковом входе — критично для экзамена/replay). Фундаментальная физика
(фазовые равновесия, строгие балансы) — задача следующего уровня L3.

### 3.1. Что реально происходит при запуске «другой установки» (проверка кода)

Прямой ответ на вопрос комитета **«будет ли мат. модель работать для установки,
построенной пользователем в конструкторе»**: на текущем этапе — **нет корректной
интеграции**. Ниже — проверяемые факты по коду, без допущений.

**C1. `orchestrator` защищает передачу графа моком, а не реальным sim-клиентом.**
`SessionService.Create` вызывает `constructor.ExportTemplate(templateID)` → `initState`,
затем `sim.CreateSession(ctx, id, initState, 0)` (`internal/service/session_service.go:146-151`,
`internal/client/interfaces.go:10-11`). Однако в сборке `SimClient` — это
`MockSimClient`, который **игнорирует `initState`**: сигнатура
`CreateSession(_ context.Context, sessionID string, _ []byte, _ int64)`
(`internal/client/mock.go:24`), а `Step` только инкрементирует `ModelTime` без физики
(`mock.go:38-47`). То есть связь orchestrator→sim сегодня — **заглушка**.

**C2. Даже настоящий sim-worker не принимает граф установки на вход.**
`bootstrapper` загружает **единственный фиксированный файл** `settings.template_file`
(= `template_atm_demo.json`) при старте сервиса (`bootstrap.py:61,72`), и все сессии
строят сеть из этой одной загруженной структуры через
`build_network(self.template, seed)`.
Метод `CreateSession` обоих транспортов принимает только `session_id` и `seed`,
**без init_state/шаблона**: `grpc_server.py:87-94`, `rest.py:100`.
Механизм `SetState(tag_overrides=..., internal_state=...)` корректирует только **значения
внутри уже собранной ЭЛОУ-АВТ-сети** (снапшот/уставки), а не строит модель из чужого графа.

**C3. Следствие для «другой установки».**
При текущей связке попытка запустить иную установку из конструктора приводит к
одному из трёх поведений:
1. в связке с моком — «симуляция» просто накапливает модельное время (физики нет);
2. в реальном sim-движке — сохранение формата ЭЛОУ-АВТ даст **физически некорректную
   картину**: новые узлы/контуры не получают связи (`COUPLINGS` захардкожены),
   эффекты ПАЗ привязываются к тегам демо-шаблона (`TRC 5`, `FR 415`…), которых в
   новом графе может не быть;
3. отклонение структуры от формата демо-шаблона — **падает/частично игнорируется**
   (`KeyError` в `build_network`).

**Вывод:** сомнение комитета **обосновано**. На L1 мат. ядро (ПИ-контуры, печи,
насосы) параметризовано и универсально, но **интерпретатор графа не реализован**, а
«мостом» `constructor → sim-engine` служит заглушка. Поэтому **любая недемо-установка
не будет корректно отражена в симуляции**. Это закрывается на **Этапе 1** ниже
(интерпретатор графа + передача графа в `CreateSession`), который является не
«улучшением», а **обязательным первым шагом** для мульти-установочной работы.

## 4. Roadmap усиления математической модели

Дорожная карта разбита на этапы. Каждый этап — измеримый результат, который можно
показать в тестах и графах, не ломая Model API и детерминизм.

### Этап 0 (текущий, done) — Параметрическая модель L1
- [x] ПИ-контуры + инерция 1-го порядка; печи как частный случай.
- [x] Связи assist→контур; механика двух типов неисправностей.
- [x] Детерминизм (seed, фикс. под-шаги, эйлер).
- [x] 10 сценариев из докс + пороги ПАЗ из регламента.
- **Выход:** стабильная база тренажёра для демо-сценариев.

### Этап 1 — Топология из графа (обязательно, закрытие сомнения «одна установка»)
> По фактам §3.1 этот этап — не «опциональное улучшение», а **первый обязательный**
> шаг для мульти-установочной работы: сегодня граф в движок не попадает вовсе (C1)
> и не строится из него сеть (C2–C3).
- [ ] Реальный sim-клиент в orchestrator (замена `MockSimClient`) с передачей графа
      в `CreateSession` вместо игнорирования `initState` (§3.1 C1).
- [ ] Приём графа установки в `CreateSession` sim-worker (`grpc`/`rest`), а не только
      фиксированный `template_atm_demo.json` (§3.1 C2).
- [ ] Универсальный интерпретатор графа: `build_network` собирает контуры/связи
      **из графа Constructor Service** (nodes/edges) вместо захардкоженного `COUPLINGS`.
- [ ] Вынести `COUPLINGS` и `INTERLOCK_EFFECTS` в **данные шаблона** (граф + эффекты).
- [ ] Интеграция с реальным `schema/template_graph.json` / `constructor`.
- **Достижение:** разные установки = разные графы в данных, **код — один** (ARCH-07).
- **Результат для комитета:** демонстрация двух разных топологий на одном коде.

### Этап 2 — Строгие балансы массы и энергии (L2)
- [ ] Явные **материальные балансы** для колонн/ёмкостей (приток/отток/накопление).
- [ ] Явные **энергетические балансы** узлов (теплопередача, тепловые потери).
- [ ] Более реалистичные **гидравлические характеристики** (клапаны, сопротивления)
      вместо линейных контуров.
- [ ] Нелинейная статическая характеристика (взаимовлияние PV при больших возмущениях).
- **Достижение:** качество «уже физика», а не только трендовая динамика.

### Этап 3 — Термодинамика фаз и состав (L3, целевая)
- [ ] Подключение **строгого термодинамического solver** (например, DWSIM) через
      тот же Model API (ARCH-01): кипение, конденсация, составы фаз, кривые разгонки.
- [ ] Замена внутреннего решателя на жёстко-устойчивый (BDF/adaptive) с сохранением
      фиксированного набора параметров для детерминизма.
- [ ] Валидация количественных значений против технологического регламента
      (сравнение стационаров и динамики с реальными данными).
- **Достижение:** полноценный цифровой двойник (уровень тренажёра 3-го поколения).

### Этап 4 — Детерминизм и производительность при L2/L3
- [ ] Контроль детерминизма для нового численного ядра (фикс. допуски, порядок,
      BLAS-фиксация) — тесты `test_determinism_*`.
- [ ] Баланс точность↔производительность на графе до 200 узлов при 10× (≤1 Гц,
      CPU-бюджет инстанса, Node Pool `sim`).
- [ ] Load-test 50 параллельных сессий.

## 5. Метрики отслеживания прогресса (для отчёта перед комитетом)

| Метрика | Этап | Критерий успеха |
|---|---|---|
| Число установок на одном коде | 1 | ≥2 разных шаблона без правки кода |
| Ошибка стационара vs регламент | 2–3 | в пределах заданного допуска |
| Детерминизм | все | байт-в-байт повтор при том же seed |
| 1 Гц / 10× / 50 сессий | 4 | tick-lag ≈ 0, CPU в бюджете |
